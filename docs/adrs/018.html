ADR 17Architecture

18. Usecaseイベントの通知とtoastのComponent化

Status

Accepted

Context

Usecaseの結果をComponentへ伝える経路は、Storeの状態だけである。Usecaseは完了Actionを返し、runnerがそれをStoreへ適用する。ComponentはupdateでStoreを読み、状態の変化を見つけて表示を変える。

この経路には、「一度だけ起きたこと」を伝える手段がない。

  • 競合popupは、AppComponent::updateが毎回Storeの競合情報を読み、同じpopupがまだ開いていなければ開く。「一度だけ開く」ことを、popup stackの検査で保っている。Remote Journalの競合popupは、続行した直後のupdateでまだ消えていない競合情報を読み、開き直すことがある（src/components/app.rsのFIXME）。
  • Issueの新規作成（ANO-183）では、POST /issues.jsonが完了したら、新規作成用ComponentをIssueDetailComponentに差し替えたい。下書きは新規作成用Componentが持ち、Storeには置かない。そのため、「作成が完了した」ことをStoreの状態として残す理由がない。

一時通知も、Storeの状態として扱っている。

  • 一時通知はNoticeAction::PushでNoticeStoreに追加する（ADR 9）。runnerは毎周Dispatcher::update_store(tick)で表示経過時間を渡し、NoticeStoreは5秒を過ぎた通知を捨てる（ADR 10）。
  • Storeは、Actionを適用した結果として決まる情報を持つ場所である。時間の経過で中身が変わるNoticeStoreは、この性質から外れている。
  • Usecaseが通知の文言を組み立てている。upload_issue.rsには、これを設計上の負債とするFIXMEがある。

現在のNoticeAction::Pushの発生元は次のとおりである。

発生元 内容
非同期Usecaseの完了 Issue保存の失敗、Remote・Local・削除済みJournalの保存失敗とPUT後の確認GETの失敗、添付ファイルのupload失敗
runner 外部editorの起動・実行・terminal復帰の失敗
起動処理（entry/native.rs） terminalのピクセル単位の大きさを取得できず、画像を表示しないこと
Component（issue/detail/property） 子Issueから計算される属性は編集できないこと

Usecaseの起動時の同期処理から通知を出している箇所はない。

Decision

UsecaseはUsecaseOutputでイベントを返す

Usecaseが一度だけ起きたことを伝えるUsecaseEvent enumをsrc/usecases/に置く。UsecaseOutputにeventsを加える。 

pub struct UsecaseOutput {
    pub actions: Vec<Action>,
    pub requests: Vec<UsecaseRequest>,
    pub events: Vec<UsecaseEvent>,
}
  • どのUsecaseもイベントを返してよい。
  • イベントを契機にUsecaseを起動しない。後続のUsecaseは、これまでどおりUsecaseOutput::requestsで表す（ADR 15）。
  • イベントはStoreの状態を変えない。再試行に必要な失敗状態など、後から読み直す情報は、これまでどおり完了ActionでStoreに置く。同じ失敗から、Storeの失敗状態を表すActionと、通知のためのイベントを両方返してよい。
  • イベントは何が起きたかで種類を分ける。失敗はUsecaseEvent::Failure(UsecaseFailure)にまとめ、Issue保存の失敗はUsecaseFailure::IssueUpload { id, reason }のように表す。
  • イベントは表示の文言を持たない。reasonはClientのエラーなど外部由来の説明であり、通知の文言ではない。

runnerはイベントをAppComponentへ渡す

受け取るのはAppComponentだけとする。購読者を登録する仕組みは作らず、runnerがAppComponentのメソッドを直接呼ぶ。 

impl AppComponent {
    pub fn handle_usecase_events(&mut self, events: Vec<UsecaseEvent>);
}
  • handle_usecase_eventsはupdateと別のメソッドにする。updateはStoreの状態をComponentへ反映する処理で、Actionを1件消費するたびに呼ばれる。イベントはComponentの生成や破棄を引き起こすため、Storeの反映とは分ける。
  • handle_usecase_eventsはRequestSinkもDispatcherも受け取らない。イベントを受けてできるのは、Componentの生成・破棄・内部状態の変更だけである。今はStoreも受け取らない。Issueの新規作成の完了でIssueComponent::new(store, id)を作るときなど、Storeを読む必要が出たら読み取り専用で渡す。

runnerはcompletionの処理を次の順にする。

move_worker_action:
  for completion in 受理したcompletion:
    output.actionsをdispatchする
    output.requestsをrequest queueに積む
    output.eventsをevent queueに積む
loop:
  move_worker_action()
  app_component.tick(elapsed)
  update()                                        // Actionを1件ずつ消費し、そのたびにupdateする
  app_component.handle_usecase_events(event queueを全部)
  app_component.update(store)
  drain_requests()
  draw()
  • イベントは、同じcompletionのActionをStoreへ適用した後に渡す。イベントを受け取った時点で、Storeには同じcompletionの結果が入っている。
  • 1周で複数のcompletionを受理した場合は、すべてのActionを消費してから、すべてのイベントをcompletionの受理順に渡す。そのため、あるイベントを受け取った時点で、後に受理したcompletionのActionもStoreに入っていることがある。
  • 後続要求は、これまでどおりイベントの処理とupdateの後に起動する。
  • editor中に受理したcompletionは、今と同じくActionだけをStoreへ適用する。イベントはevent queueに残し、editorから戻ってComponentへの入力を再開するときに渡す。

toastはComponentが持つ

NoticeStoreを廃止する。AppComponentが通知を表すtoastを持ち、toastは表示経過時間で自身を破棄する。

  • AppComponentはUsecaseEvent::FailureをToastListComponentに渡す。ToastListComponentが失敗の種類ごとに文言を組み立て、toastを作る。
  • runnerは毎周、表示経過時間をAppComponent::tick(elapsed)で渡す。これは今のDispatcher::update_store(tick)を置き換える。toastはInstantを持たない。
  • editor中は経過時間を渡さず、editorから戻ったときに起点を取り直す。ADR 10の「表示経過時間はeditor中に消費しない」は維持する。
  • 1周の中では、tickをイベントの処理より前に呼ぶ。そのため、その周に届いた通知が表示される前に期限切れになることはない。
  • 表示は今と同じくToastWidgetで行い、AppComponent::renderが通常画面とpopupの後に描画する。toastはfocusを取らない（ADR 9）。

Usecase以外が発する通知は、イベントを経由せずにAppComponentへ伝える。

  • runner: 外部editorの失敗は、runnerがAppComponent::handle_editor_failureに失敗の説明を渡す。AppComponentはeditor contextを解放し、ToastListComponentにtoastを作らせる。
  • 起動処理: 画像を表示しない理由は、entryがrunの引数で渡し、runnerがAppComponentの生成直後にnotify_image_display_unavailableで渡す。
  • Component: 子Issueから計算される属性を編集しようとしたことは、属性のComponentがprocess_eventの結果ComputedPropertyNotEditableとして返し、AppComponentまで伝える。

本ADRで移行する範囲

  • NoticeAction::Pushを発しているUsecaseを、UsecaseEventを返す形に移す。文言の組み立てはToastListComponentに移す。
  • NoticeStore、NoticeAction、NoticeId、Store::get_notices、Dispatcher::update_storeを削除する。
  • 競合popupを開く処理は移行しない。upload中に別のIssueへ移り、戻ってきたときに競合popupを開く挙動は、Storeの競合情報を毎回読むことで成り立っている。イベントに移すと、離れている間に届いたイベントは失われ、Issueは解決する手段のない競合状態のまま残る。移すには、表示から外れたIssueのuploadの状態遷移を見直す必要がある。
  • Issueの新規作成完了は、ANO-183でこの仕組みを使って実装する。

Rationale

一度だけ起きたことをStoreの状態として表すと、Componentは「すでに反応したか」を自分で判定する必要がある。競合popupのpopup stack検査がその例である。イベントとして一度だけ渡せば、この判定は要らない。

イベントをUsecaseOutputに載せるのは、後続要求と同じく、Usecaseの単体テストで返したイベントを検査できるためである。

受け取り手をAppComponentに限り、登録の仕組みを作らないのは、今の受け取り手がAppComponentだけだからである。表示中のComponentの差し替えやtoastの追加は、Componentの木の根にあたるAppComponentが担う。

イベントをActionの消費とupdateの後に渡すのは、イベントを受けたComponentがStoreに入った結果を前提にできるようにするためである。新規作成の完了イベントを受けた時点では、後続のFetchIssueはまだ起動していない。それでもIssueComponent::newは未取得のIssueでも作れるため、Componentを差し替えられる。

イベントからUsecaseを起動しないのは、何を起動するかをUsecaseの戻り値から読み取れるようにするためである。イベントの処理にRequestSinkを渡すと、後続要求と同じことを2つの経路で表せてしまう。

toastを表示経過時間で破棄する処理をComponentに移すと、Storeは適用したActionだけで決まる。AppComponent::tickに経過時間を渡せば、Componentのテストでも時間を固定できる。

イベントが文言を持たないので、通知の文言を組み立てる処理はUsecaseからToastListComponentに移る。これにより、upload_issue.rsのFIXMEが指摘する負債が解消する。文言をToastListComponentに置くのは、表示する情報の保持とWidgetの生成までを各Componentが担う構成に合わせるためである。

失敗をUsecaseFailureにまとめると、ToastListComponentは失敗の種類だけを漏れなくmatchできる。AppComponentは上の層でイベントの種類ごとに渡す先を決める。失敗以外のイベントを足しても、どちらのmatchも網羅性をコンパイラが確かめる。種類は受け取り手ではなく起きたことで分けるので、Usecaseは受け取り手を知らないままである。

Consequences

  • ADR 9の次の決定を置き換える。
    • 一時通知をNoticeAction::PushとしてNoticeStoreに送ること。今後はUsecaseがUsecaseEventを返し、AppComponentがtoastを持つ。
    • 時間で変化するStoreの状態をStore::update(now)へ集約すること。
    • 同じNoticeIdの再追加とすでに消えたnoticeのDismissを、冪等なno-opの例とすること。NoticeIdはなくなる。
  • ADR 10の「Noticeと経過時間」のうち、Storeが表示経過時間を受け取る契約を、AppComponent::tickが受け取る契約で置き換える。editor中に経過時間を消費しないことは維持する。
  • ADR 15のUsecaseOutputにeventsを加える。runnerのcompletion処理に、イベントの受け渡しが加わる。
  • UsecaseOutputを組み立てる箇所にeventsが必要になる。From<Vec<Action>>はeventsを空にする。
  • 通知を返すUsecaseのテストは、Action::NoticeではなくUsecaseEventを検査する形に変わる。通知の文言はToastListComponentのsnapshotで、AppComponentとToastListComponentの結合はE2Eで確かめる。notice_store_tests.rsはToastListComponentのテストに置き換える。
  • 表示から外れた対象についてのイベントは、AppComponentが無視する。新規作成中に別のIssueを開いた場合の完了イベントがこれにあたる。
  • docs/architecture.mdのusecases、runner、Flux構成の説明（RequestSink、update、冪等no-opの例）を更新する。
  • 複数の通知が同時に出たときのtoastの集約・積み上げの規則は、ADR 9のFuture Workのまま残す。

Alternatives Considered

  • イベントをActionのvariantにしてDispatcherのqueueに載せる: runnerの型は変わらないが、ActionがStoreの状態遷移を表すという意味が崩れる。Actionは1件ずつ消費してupdateするため、同じcompletionの残りのActionを適用する前にイベントが届く。採用しない。
  • Dispatcherにイベントのqueueを持たせる: Usecaseの同期処理からもイベントを出せるが、今は同期処理から通知を出す箇所がない。Storeの情報保存とイベントの通知の責務がDispatcherに同居するため、採用しない。
  • Rc<dyn Subject>のような購読者の登録方式にする: 受け取り手がAppComponentだけの今は、登録と解除の管理が増えるだけである。受け取り手が増えたときに改めて検討する。
  • イベントをupdateの引数で渡す: updateはActionを1件消費するたびに呼ばれるため、どの呼び出しでイベントを渡すかの規則が別に要る。Storeの反映とComponentの生成・破棄が同じメソッドに混ざるため、採用しない。
  • イベントの処理にRequestSinkを渡し、イベントからUsecaseを起動できるようにする: 後続のUsecaseを表す経路がUsecaseOutput::requestsと2つになる。採用しない。
  • 汎用のNotice { message }イベントにして、文言はUsecaseが組み立てる: 移行は機械的になるが、Usecaseが表示の文言を組み立てる負債が残るため、採用しない。
  • toastにするかどうかでイベントの種類を分ける: Usecaseが受け取り手を知ることになるため、採用しない。
  • 文言をAppComponentが組み立てる: AppComponentがtoastの表示内容まで持つことになり、表示情報とWidgetの生成を各Componentが担う構成から外れるため、採用しない。
  • toastがInstantを持ち、自分で期限を判定する: テストで時間を固定できず、editor中に経過時間を止める契約も守れないため、採用しない。
  • NoticeStoreを残し、イベントの仕組みだけを足す: 時間で中身が変わるStoreが残り、通知が2つの経路に分かれるため、採用しない。
