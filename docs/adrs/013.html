13. テストの層構成と期待値の書き方

Status

Accepted

Context

現在のテストは、Storeやfocus stateの単体テスト、wiremockを使うRedmine clientのテスト、Componentやrunnerの結合テストで構成されている。結合テストはsrc/components/app.rsとsrc/runner/tests.rsに集中している。これらはAppComponent、Dispatcher、Store、popupを組み立て、キー入力からStore更新やeffect発行までを検証する。1件のテストに、選択肢の組み合わせとユーザー操作の流れが同時に含まれることも多い。そのため、組み合わせを増やすと結合テストの数が増え、構成するstructが増えると準備手順が長くなる。

Redmine clientのテストはwiremockの応答を前提にしている。Redmine APIの仕様を読み違えても、wiremockの応答は読み違えたとおりに書かれるため、テストは通る。実際に何度か、手動でRedmineにつないだときに初めてエラーが見つかった。

テストデータはdatas/のYAML fixtureから読み込んでいる。IssueAction::LoadはIssueStoreの中でparse_issue_yamlを呼ぶ。このActionは本番コードから発行されず、テストだけが使う。test_support::sync_fixture_entitiesとdispatch_fixture_entity_actionsも、fixtureをパースしてマスターデータのSync Actionを作る。このため、各テストがfixtureのどの値に依存しているかをコードから読み取れない。また、fixtureは件数が少なく、境界値や組み合わせを十分に含まない。

期待値をfixtureのパース結果や入力から計算するテストもある。このようなテストでは、入力の誤りが期待値にも同じ形で伝わるため、実装とテストが同時にずれても検出できない。

Decision

テストを3層に分ける

テストは次の3層を中心に構成する。

層対象接続先
単体テストStore、focus state、usecase、widget、component単体、value object、変換処理なし
Redmine clientテストDefaultRedmineClientの各メソッドRedmine container、エラー変換のみwiremock
E2Eユーザー操作の流れ全体testtyのPTY上のnativeバイナリとRedmine container

内部で閉じるstruct同士の結合テストは減らす。

単体テストかどうかは、組み合わせるstructの数ではなく、テスト対象がひとつかどうかで判断する。テスト対象がひとつで、Storeを入力のfixtureとしてのみ使う場合は単体テストとする。たとえば、Storeを組み立てて渡し、Componentの描画、process_eventの戻り値、発行したActionを検証するテストは単体テストである。

結合テストは基準に従って残すか移す

既存の結合テストを次の基準で仕分ける。1件のテストが複数の性質を含む場合は、分割してそれぞれの移し先へ移す。

  • 残す: 層の間の契約のうち、画面から観測できないものを検証するテスト。例として、ComponentがAppEffectを発行するかどうかと発行回数、take_effectによる取り出し、action処理とupdateを交互に行うlifecycleがある。
  • 単体テストへ移す: 組み合わせを検証するテスト。例として、popupの選択肢からNoneを除く判定はissue_popup_optionsの単体テストで検証する。
  • E2Eへ移す: ユーザー操作の流れを検証するテスト。例として、popupでの選択がIssueの属性に反映されることを検証する。

Redmine clientテストは実際のRedmineに接続する

DefaultRedmineClientの正常系は、xtaskがDocker Composeで起動したRedmine containerに接続して検証する。containerに接続するテストは専用のmoduleに置き、container-tests featureを有効にしたときだけcompileする。

401、5xx、壊れたJSONなど、実際のRedmineでは発生させにくい応答は、wiremockで再現する。wiremockを使うテストは、HTTP応答をRedmineClientErrorへ変換する処理の検証に限る。

E2EはtesttyとRedmine containerで行う

E2Eはtesttyを使い、nativeバイナリをPTY上で起動して操作する。接続先はRedmine clientテストと同じRedmine containerとする。Web adapterはE2Eの対象外とし、従来どおり手動で確認する。

シナリオ間の独立性は次の方法で保つ。

  • E2Eは直列に実行する。
  • シナリオを開始するたびにseedを投入し直す。
  • seedの投入時に、各テーブルのAUTO_INCREMENTもリセットする。fresh_test_data.sqlは、Issue、Journal、version、categoryなどのテーブルをDELETEした後にALTER TABLE ... AUTO_INCREMENT = 1を実行しており、これを前提とする。これにより、シナリオ中にAPIで作成したデータのIDも毎回同じ値になる。
  • seedには全シナリオで共通の土台だけを入れる。対象は、マスターデータ、複数project構成、categoryやversionの有無などである。
  • シナリオ固有のデータは、Givenの段階でRedmine APIを使って追加する。他のユーザーによる更新や衝突も、APIによる更新として記述する。

期待する結果は、画面の表示と、シナリオ終了後にRedmine APIで取得した状態の2つで検証する。Redmine APIで取得する状態の例は、journalの件数、属性値、updated_onである。E2Eではリクエスト回数を検証しない。回数や副作用の有無は、AppEffectの発行回数や、呼び出しを記録するmockのRedmineClientを使った結合テストで検証する。

シナリオはテスト関数ごとに固定し、Gherkinをコメントとして記述する。

  • テスト関数名とScenario名を1対1で対応させる。
  • // Given、// When、// Thenは、それぞれに対応するコードブロックの直前に置く。

ページパターンは導入しない。シナリオが増えた段階で導入を検討する。ただし、seedの投入やAPIによるデータ追加を行う補助関数は、E2E用のsupport moduleへ最初から切り出す。

テストデータはSyncでentityを直接渡す

IssueAction::Loadを削除する。test_support::sync_fixture_entitiesとdispatch_fixture_entity_actionsも削除する。テストでは、Syncなどの本番Actionでentityを直接Storeへ渡す。

テストが必要とするentityは、各テストかtest_supportの小さな組み立て関数で定義する。これにより、テストが依存する値がテストのコード上に現れる。

datas/はDemo clientとRedmine seederの入力としてだけ使う。

期待値は定数で書く

assertの期待値はリテラルまたはconstで書く。

  • 入力と期待値で同じconstを使ってよい。どちらも定数のため、片方だけがずれることはない。
  • 期待値を、入力のコレクションの長さや、パースしたentityのフィールドなど、定数でない値から取得してはならない。
  • 期待値がconst同士の計算で決まる場合でも、コード上はリテラルで書き、計算方法をコメントに残す。

Rationale

組み合わせの検証を単体テストへ移すと、組み合わせが増えても準備手順は増えない。操作の流れの検証をE2Eへ移すと、構成するstructが増えても、結合テスト用の組み立てコードを保守する必要がない。層の間の契約は画面から観測できないため、結合テストとして残す。

Redmine APIの仕様の読み違いは、実際のRedmineに接続しない限り検出できない。E2EとRedmine clientテストはどちらも実行頻度が低い。そのため、実行時間より検出力を優先する。seedの再投入は手元の計測で平均0.04秒であり、シナリオ数が3桁に届かない見込みのため、シナリオごとに再投入しても実行時間は問題にならない。

テスト専用のActionを本番のStoreに置くと、本番の状態遷移とは別の経路でStoreに状態が入る。Syncでentityを直接渡せば、テストも本番と同じ経路を通る。

期待値を定数にすると、入力や実装の誤りが期待値へ伝わらない。

Consequences

  • app.rsとrunner/tests.rsの結合テストを、本ADRの基準に従って仕分ける必要がある。1件のテストに複数の性質が含まれる場合は分割するため、移し替えの作業量は件数より多くなる。
  • IssueAction::Loadは58か所のテストで使われている。Loadは登録済みの場合に何もしないが、Syncは登録済みの状態によってはpanicする。そのため、機械的に置き換えると失敗するテストがある。
  • datas/をテストが使わなくなるため、seedの内容はE2Eの必要に合わせて変更できる。変更時は、Demo clientとtests/redmine_seeder_files_test.shへの影響を確認する。
  • libs/yaml.rsの利用者がDemo clientとseederだけになるため、公開範囲を見直す。
  • E2EとRedmine clientテストはDockerを必要とする。どちらも通常のcargo testではcompile・実行せず、xtaskから実行する。Redmine clientテストはcontainer-tests featureで切り替え、cargo xtask test-redmine-clientから実行する。
  • 実装時にdocs/architecture.mdへテストの層構成を追記する。

Alternatives Considered

  • E2Eの接続先をwiremockにする: 速度と安定性は高いが、Redmine APIの仕様の読み違いを検出できないため採用しない。
  • seedを1回だけ投入し、シナリオごとにAPIで専用のデータを作って分離する: seedの再投入が十分に速いため(記載時平均0.04秒/回)、分離の漏れが起きにくい再投入を採用する。
  • シナリオごとにcompose projectを分けて並列に実行する: シナリオ数の見込みに対してcontainer管理の複雑さが見合わないため採用しない。
  • 既存の結合テストをすべて残す: 組み合わせと構成structの増加に伴って保守コストが増え続けるため採用しない。
