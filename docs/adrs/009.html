9. UsecaseとStoreにおけるエラー分類とハンドリング方針

Accepted

Context

redmine-tui はRedmineサーバーとの通信を行い、IssueとJournalを取得・編集・保存するようになった。StoreはIssue、Remote Journal、Local Journal、およびそれぞれのupload状態を段階的な状態機械として保持している。

ネットワーク障害のように、アプリが正しく動作していても発生する失敗は、ユーザーに伝えて再試行できるようにすべきである。一方、Storeの状態機械に反するActionや、Usecaseの事前条件を満たさない呼び出しは、自プロセスの制御が破綻していることを示す。そのまま処理を続けると、不整合な状態が別の場所へ伝播する。

現行のJournalStoreでは、状態機械に反するActionをpanic!で拒否する実装パターンが確立している。SyncFetchedの所有者不一致、RemoveMissingRemoteJournalの状態不一致、EditRemoteNotesのupload中編集などがこれにあたる。一方、IssueStoreには成立しないActionを黙って捨てる箇所が残っており、それが意図した破棄なのか、握り潰されたバグなのかを読み分けにくい。

Journal CRUDの実装に伴い、JournalUploadFailure、NoticeStore、ToastWidget、panic時のterminal復帰、worker taskのpanic伝播はすでにmainへ導入されている。本ADRはこれらを共通基盤として扱い、Issue側を含むエラーハンドリングへ一貫して適用する。

また、IssueStatusやCategoryなどのマスターデータは起動時に一度だけ同期する。起動後に取得したIssueやJournalが、起動時のスナップショットに存在しないIDを参照することはあり得る。この参照失敗を、自プロセスの不変条件違反と同列に扱ってはならない。

Decision

エラーに見える分岐の4分類

失敗またはActionの不受理に見える分岐を、以下の4つに分類する。新しい分岐を追加する際は、どの分類に該当するかを明確にする。

分類発生源扱い
異常系自プロセスの制御破綻panic! / assert!
準異常系外部プロセスや外部データ起因の復帰可能な失敗messageをActionに載せ、状態復帰とユーザー通知を行う
stale completion重複を許した非同期要求の追い越しrequest IDで判定して破棄する
マージ戦略ローカル編集の保護意図的なno-op

Action自体が冪等性を契約として持つ場合は、この4分類の対象外となる正常なno-opを認める。たとえば同じNoticeIdの再追加や、すでに消えたnoticeのDismissは、重複通知および手動破棄と期限切れ処理の競合を安全に扱うための仕様である。このようなno-opは対象variantと理由をコード上で明記する。

異常系

自プロセスの制御が破綻している状態を異常系とし、panic!またはassert!で即座に停止する。復帰を試みない。

  • 現在のIssueまたはJournalの状態に対して成立し得ないAction。
  • Usecase呼び出し時点で、StoreのIssueまたはJournalが事前条件を満たしていないこと。
  • ActionのIDや所有関係が、検証済みであるべきStore上の関係と矛盾すること。
  • 存在を前提にした単体getterの対象がStoreに存在しないこと。

upload中のIssueまたはJournalに対する編集Actionは異常系とする。UI側で編集や重複保存をブロックし、Actionが発行され得ない状態を保証する。uploadと編集の同時進行に必要なgeneration管理は採用しない。

サーバーからRemote Journalが消えていた場合のRemoveMissingRemoteJournal、三者比較での競合検出、server == afterによるPUT省略は正常な処理であり、異常系には含めない。

準異常系

アプリの制御が正しくても発生する、外部プロセスまたは外部データ起因の復帰可能な失敗を準異常系とする。

  • Redmineとのnetwork / HTTP I/O失敗。
  • Redmineレスポンスの形式不正や、要求したIDとレスポンスの不一致。
  • 外部editorの起動、終了状態の確認、編集ファイルの読み書きの失敗。

RedmineClientErrorなどClient層のエラー型からユーザー向けmessageへの変換はUsecaseまたは外部副作用を扱うmain.rsで行う。StoreはClient層のエラー型へ依存せず、Actionで受け取ったmessageだけを保持する。

失敗後の再試行に必要な状態がある場合は、失敗Actionによって対象を再試行可能な状態へ戻し、messageを状態の一部として保持する。JournalUploadFailureのようなStore固有の失敗型はsrc/stores/に置き、src/vos/には置かない。

現時点ではIssueとJournalの保存失敗をmessage: Stringで表す。Local JournalのPUT失敗とPUT後GET失敗のように案内を変える必要がある場合は、違いをmessageへ含める。

一時通知はNoticeAction::PushとしてNoticeStoreへ送り、ToastWidgetで表示する。Storeが保持する失敗状態とnoticeは役割が異なるため、必要に応じて同じ失敗から複数のActionを生成する。

stale completion

同一対象への重複した非同期要求を意図的に許す場合に限り、完了Actionの破棄を認める。破棄はrequest IDの一致判定で行い、暗黙の状態判定では行わない。

現時点で該当するのはProjectIssuesStoreである。fetch_project_issues_pageは同じexact keyへ新しい要求を開始できるため、is_loading_requestがrequest IDの不一致を検出して古い完了を破棄する。

IssueActionとJournalActionは重複要求を許さず、generation管理を持たない。完了Actionが想定状態以外へ着弾した場合はstale completionとして捨てず、異常系として拒否する。

マージ戦略としてのno-op

サーバー由来のデータを取り込む際、ローカル編集を保護するため更新を適用しないことがある。JournalAction::SyncFetchedがEditedまたはUploadingのRemote Journalを取得値で上書きせず、取得結果から消えていても保持する処理がこれにあたる。該当箇所には意図をコメントで明記し、対象variantを列挙したテストで固定する。

Store getterの契約

Store getterが不在を許すかどうかは、entityの種類だけで一律に決めず、APIが表す状態とcardinalityで決める。

存在が呼び出し元の事前条件である単体取得: 直前の検査によって存在が保証されるgetterは参照を直接返し、不在を異常系としてpanic!する。get_remote_journal(issue_id, journal_id)がこれにあたる。

不在そのものが状態またはcardinalityを表す取得: get_issue、get_project_issues_page_state、get_local_journalはOptionを維持する。get_remote_journalsは未登録なら空sliceを返す。特定経路で存在を前提にする呼び出し側は、不変条件を説明するexpect(...)または明示的なpanic!を使う。

起動時に一度だけ同期するマスターデータ: IssueStatus、Priority、Category、TargetVersion、Tracker、Project、User、TimeEntityActivityの単体getterはOptionを返し、欠損を表示上のfallbackで処理する。現状この規則に反するStore::get_issue_statusはOption<&IssueStatus>へ変更する。

panicを利用するための共通基盤

現行のmainには以下が実装済みであり、本ADRの実装でも維持する。

  • process全体のpanic hookが既定hookの前にratatui::restore()を呼ぶ。
  • Actionを返す非同期処理はspawn_action_taskを使い、taskのpanicをAction::WorkerPanickedとしてmain loopへ送る。
  • taskのcancellationはworker panicとして扱わない。

Actionを返すworker taskを追加する際は、runtime.spawnを呼び出し側へ増やさず、同じhelperを使う。

Error Handling

準異常系のnoticeはtoastとして最前面に表示し、focusを取らない。AppComponent::renderは通常画面とpopupの後にToastWidgetを描画し、toastはキー入力やcursor位置を変更しない。

IssueおよびJournalのupload失敗と、TUI実行中の外部editor失敗はtoastで表示する。IssueState::FetchFailedとProjectIssuesPageState::Failedは再試行操作を持つ各Component内に表示する。初期マスターデータの取得失敗はTUI初期化前にstderrへ出力して起動を中止する。

NoticeStoreが発生時刻を保持し、main loopがtickごとにDispatcher::update_store(now)を呼んで期限切れを破棄する。現在時刻はStore内で取得せず、NoticeAction::Pushのcreated_atとStore::update(now)の引数で受け取る。

tokio timerとchannelでnoticeを破棄する方式は、worker taskとchannel往復を追加する割にmain loopのtick粒度で十分な精度が得られるため採用しない。

Rationale

4分類を明示することで、条件を満たさないActionを扱う箇所が、バグの検出、外部失敗からの復帰、古い完了の排除、ローカル編集の保護のどれなのかを読み分けられる。特にstale completionとマージ戦略は同じno-opに見えやすいため、独立して扱う。

getterの契約をAPIの意味とcardinalityで決めるのは、不在が示す意味が異なるためである。Remote Journal単体の不在は事前条件違反になり得るが、Issueの未取得やLocal Journalが0件であることは通常状態である。マスターデータの不在も、起動時スナップショットの陳腐化によって通常運用で発生し得る。

準異常系をmessageで保持するのは、現時点の分岐と表示に必要な情報がmessageに尽きるためである。再試行可否など構造化情報が必要になった時点で追加する。

既存のNoticeStoreとToastWidgetを再利用し、Journal CRUDですでに動作しているfocus非依存の表示、期限切れ、決定的なStoreテストをIssueやeditorの失敗にも適用する。

Consequences

  • IssueStoreで黙って破棄している不正な完了Actionと編集Actionを異常系として拒否する。
  • IssueAction::FailUploadへmessageを追加し、再試行可能な状態へ戻しながら失敗情報を保持する。あわせて、同じ失敗をnotice表示へ接続する。
  • TUI実行中の外部editor失敗をnoticeへ接続する。
  • Store::get_issue_statusの戻り値変更を、呼び出し元と関連snapshotへ反映する。
  • 異常系で停止した場合、未保存の編集内容は失われる。
  • 既存のnotice、toast、Store更新、panic hook、spawn helperは新設せず、共通基盤として維持・再利用する。

Alternatives Considered

すべてのエラーをResultで呼び出し元へ返す

Actionをdispatchした時点とconsumeされる時点が分離しているため、呼び出し元に返す先がない。main loopへ各Storeの状態機械の知識も漏れる。

異常系も含めてすべてtoast表示する

壊れた状態のまま処理を続けると、別の場所で不整合が顕在化して原因の特定が難しくなる。

debug_assert!を使う

release buildでだけ不整合が黙って進み、build種別によって状態機械の契約が変わる。

すべてのマスターデータをIssue fetchのたびに再同期する

通信量と応答性の代償が大きいため、参照失敗をUI上のfallbackで扱う。

ToastStoreを新設する

現行のNoticeStoreは表示方法に依存しない一時通知としてすでに使われている。同じ状態を分割せず、表示側だけをToastWidgetとする。

tokioのunhandled_panicを使う

--cfg tokio_unstableが必要で、main threadの終了とterminal復帰は別途必要になる。既存のJoinHandle監視とAction::WorkerPanickedを維持する。

Future Work

  • 編集内容のfileへのflushと起動時の復元。
  • IssueStoreのentry統合による、Issue本体と状態の不整合の型levelでの排除。
  • Optionを返すqueryとstrict getterを分離する必要性の再検討。
  • RedmineClientErrorの種別に基づく再試行可否とUI導線の出し分け。
  • 複数toastの集約・積み上げ規則。
  • fetch失敗messageの構造化と、log向け情報・UI向け文言の分離。
  • 同一IssueまたはJournalへの再取得・cancelを導入する場合のgeneration管理。
