# 5. Issue 子 Store と IssueAction の分離方針

## Status

Accepted

## Context

`src/app.rs` は `Action`、`Dispatcher`、`Store` を定義し、Issue、Journal、Redmine のマスターデータに関する状態と更新処理を一つのファイルで管理している。

Issue 保存フローの追加により、Issue 本体だけでなく、Issue ごとの同期状態、未保存差分、upload 競合情報を Store が保持するようになった。Issue の読み込み、同期、編集、upload、競合管理に関する action も増え、`src/app.rs` の責務とテストが重厚になっている。

ADR 2 では Issue 関連 action が増えた場合に Issue 専用の子 Store へ切り出す余地を残していた。現在は、Issue に関する状態と action 処理が独立したまとまりを形成しており、子 Store へ分離する時点に達している。

一方、Component と usecase は親 `Store` の getter を通して Issue を参照している。この参照方法や Component lifecycle を変更せず、Store 内部の責務だけを分離する必要がある。

## Decision

Store 関連コードを `src/stores/` へ移し、以下の構成にする。

```text
src/stores/
├── mod.rs
├── store.rs
├── issue_store.rs
└── issue_store_tests.rs
```

各ファイルの責務は以下とする。

- `store.rs` は親 `Action`、`Dispatcher`、`Store`、Journal とマスターデータの状態を定義する。
- `issue_store.rs` は `IssueStore`、`IssueState`、`IssueAction` と Issue Action の処理を定義する。
- `issue_store_tests.rs` は親 `Store` の公開インターフェースを通して Issue Action を検証する。
- `mod.rs` は利用側に必要な型を再エクスポートし、内部のファイル配置を隠蔽する。

`src/main.rs` の `mod app;` は `mod stores;` に変更する。既存の `crate::app` import は `crate::stores` へ移行する。

親 `Store` は `IssueStore` を一つのフィールドとして所有する。次の Issue 固有状態は `IssueStore` へ移す。

- Issue 本体
- Issue ごとの `IssueState`
- 未保存の `IssuePropertyDiff`
- upload 競合検出時のサーバー Issue と競合 diff

親 Action は Issue 固有 Action を一つの variant として保持する。

```rust
pub enum Action {
    Issue(IssueAction),
    // Journal、マスターデータ関連 Action
}
```

`IssueAction` は Issue という文脈が型名で明らかなため、variant 名から重複する `Issue` を除き、以下を定義する。

- `Load`
- `Sync`
- `StartUpload`
- `CancelUpload`
- `ClearUploadConflicts`
- `FailUpload`
- `UploadConflictsDetected`
- `UpdateDescription`
- `UpdateStatus`
- `UpdateAssignedTo`
- `UpdateTargetVersion`
- `UpdateCategory`
- `UpdateDoneRatio`
- `UpdateStartDate`
- `UpdateDueDate`

親 `Store::consume_action` は `Action::Issue(action)` を `IssueStore::consume_action(action)` へ委譲する。Journal とマスターデータの Action は従来どおり親 Store が処理する。

`From<IssueAction> for Action` を実装する。`Dispatcher::dispatch` は `impl Into<Action>` を受け取り、Component や usecase は通常、`IssueAction` を直接 dispatch する。

```rust
dispatcher.dispatch(IssueAction::UpdateStatus { id, status_id });
```

非同期処理など、戻り値として親 `Action` が必要な箇所では `.into()` で変換する。

既存 Component や usecase が子 Store を直接参照しないよう、次の公開 getter は親 Store に残し、内部で IssueStore へ委譲する。

- `get_issue`
- `get_issues`
- `get_issue_property_diffs`
- `get_issue_upload_conflict`

既存の `IssueState::Synced / Edited / Uploading`、状態遷移、許可されない操作の panic 条件とメッセージは変更しない。`Load` は引き続き YAML fixture を読む暫定 Action とし、`Sync` は Issue の置換、diff と競合情報の破棄、`Synced` への遷移を行う。

Issue Store のテストは `src/stores/issue_store_tests.rs` へ分離する。ただし `IssueStore` を直接テストせず、現在と同様に親 `Store::consume_action` と親 Store の公開 getter を通して外部から観測できる振る舞いを検証する。

現在 `src/app.rs` にある次のテスト群を `issue_store_tests.rs` へ移す。

- Issue の読み込みと参照 ID の保持
- Issue property 更新と diff 記録
- upload 開始、中断、失敗、成功時の状態遷移
- upload 競合情報の保持と破棄
- 不正な状態遷移および upload 中編集の panic
- Issue 同期時の置換と状態初期化

`SyncIssueStatuses`、`SyncUsers` などマスターデータ Action のテストは親 Store のテストとして残す。既存の Issue テストの内容や検証量は削減せず、配置と Action 名だけを新構成へ追従させる。

## Rationale

Issue 本体、同期状態、差分、競合情報は同じ Issue ID をキーとして連動し、Issue Action によって一貫して更新される。この状態と更新規則を `IssueStore` にまとめることで、Issue の状態遷移を親 Store の他の責務から独立して読める。

Issue 固有 Action を `Action::Issue(IssueAction)` として構造化すると、親 Store がアプリケーション全体の Action を受け取る入口であることを維持しながら、子 Store が処理できる Action の範囲を型で表現できる。親 Store に15個の Issue Action variant を残して個別メソッドへ委譲する案は、`store.rs` の match が重いままになるため採用しない。

`IssueAction` の variant から `Issue` という接頭辞を除き、`From<IssueAction> for Action` と `impl Into<Action>` を受け取る dispatch を組み合わせることで、構造化に伴う呼び出し側の冗長さを抑えられる。

親 Store の getter を維持することで、Component は Store 内部の分割を意識しない。子 Store を直接公開すると、Component が複数 Store を個別に参照し、将来の状態配置変更が表示層へ漏れるため採用しない。

テストを親 Store 経由のまま維持することで、子 Store の実装詳細ではなく、アプリケーションが利用する公開インターフェースと Action dispatch の結合を検証できる。Issue テストを実装ファイルから分離することで、実装とテスト双方の可読性を改善する。

## Consequences

`src/app.rs` は廃止され、Store 関連の利用箇所は `crate::stores` から型を import する。`src/stores/mod.rs` の再エクスポートにより、利用側は `store` や `issue_store` という内部モジュール名へ依存しない。

Issue Action の呼び出し元は新しい `IssueAction` variant 名へ更新する必要がある。worker や usecase が親 `Action` を返す箇所では、Issue Action から親 Action への変換が必要になる。

親 Store は Issue 固有状態を直接保持しなくなるが、既存 getter を維持するため、Component の Store 参照と描画結果は変化しない。UI 表示の意図的な変更はないため、snapshot の更新は想定しない。

Journal とマスターデータは引き続き親 Store が保持する。これらの子 Store 分離は本 ADR の対象外とする。

既存 ADR は変更しない。ADR 2 に記載された Issue 子 Store 分離の余地を、本 ADR によって具体化する。
