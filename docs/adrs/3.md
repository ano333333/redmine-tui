# 3. 非同期I/O worker と Dispatcher 所有方針

## Status

Accepted

## Context

`redmine-tui` は `ratatui` / `crossterm` を使う TUI であり、キー・マウス入力の解釈、Store 更新、Component 更新、描画を main thread の event loop で行っている。
現在の実装では `crossterm::event::read()` が入力待ちでブロックし、`AppContainer` が `AppComponent` と `Dispatcher` を接続している。

今後 Redmine サーバー接続により、以下のような外部I/Oや長時間処理が必要になる。

- Redmine サーバーとの network I/O
- 将来的な key config などの file I/O
- 将来的な mermaid code block の画像化処理

ADR 2 では、issue 保存中に `IssueState::Uploading` を Store で管理し、保存完了時に `SyncIssue` などの action で Store を更新する方針を決めた。
このADRでは、その保存処理や将来の外部I/Oを Rust の非同期処理としてどう扱うかを決める。

懸念点は以下である。

- キー入力処理を非同期化すると、現在の「生の入力 event を Component の親子関係に沿って下ろし、適切な Component が解釈する」構造を崩す可能性がある。
- worker thread から `Dispatcher` / Store を直接更新すると、main thread の描画・入力処理と排他制御が必要になり、Component や property 単位に lock の都合が漏れる可能性がある。
- `Arc<Mutex<Dispatcher>>` を採用すると実装は可能だが、Store 更新順序、lock lifetime、`.await` との相性を慎重に扱う必要がある。

## Decision

Tokio を使用して、外部I/O専用の worker を1つ導入する。
ただし、キー・マウス入力の解釈と描画は main thread に残す。
ここでいう worker は、main thread から見た非同期処理の入口を1つに集約するという意味である。
Tokio runtime の内部 thread 数や、mermaid 画像化のために起動する子 process は実装上の詳細として扱う。

main thread は以下を担当する。

- `crossterm` の terminal event を受け取る。
- 受け取った terminal event を既存の Component 親子関係に沿って `process_event` へ渡す。
- `Dispatcher` / Store を所有する。
- worker から返った action を受け取り、`Dispatcher` へ dispatch する。
- `Component::update` と render を実行する。

worker は以下を担当する。

- Redmine network I/O
- file I/O
- mermaid の画像化などの外部 process 実行
- 完了結果を action として main thread へ返すこと

worker は `Dispatcher` / Store / Component に直接触れない。
`Arc<Mutex<Dispatcher>>` は採用しない。
非同期処理の完了結果は channel 経由で main thread に返し、main thread が action として dispatch する。

初期実装では、`AppContainer` が Tokio runtime と worker action receiver を持つ。
`AppEffect` は非同期処理の開始要求を表す。
`AppContainer::handle_app_effect` は effect を受け取り、必要な action を main thread で先に dispatch したうえで、非同期 task を1つ queue する。
非同期 task は完了時に1つの `Action` を返す。

概念的なコードは以下である。

```rust
pub struct AppContainer<'a> {
    dispatcher: Dispatcher,
    app_component: AppComponent<'a>,
    runtime: tokio::runtime::Runtime,
    worker_action_rx: std::sync::mpsc::Receiver<Action>,
    worker_action_tx: std::sync::mpsc::Sender<Action>,
}

impl<'a> AppContainer<'a> {
    fn handle_app_effect(&mut self, effect: AppEffect) {
        match effect {
            AppEffect::SaveIssueRequested { id } => {
                self.dispatcher
                    .dispatch(Action::StartIssueUpload { id });

                let tx = self.worker_action_tx.clone();
                self.runtime.spawn(async move {
                    let action = save_issue(id).await;
                    let _ = tx.send(action);
                });
            }
            AppEffect::OpenEditor(request) => {
                // 既存の同期的な editor 起動処理を扱う。
            }
        }
    }

    pub fn update(&mut self) {
        while let Ok(action) = self.worker_action_rx.try_recv() {
            self.dispatcher.dispatch(action);
        }

        while self.dispatcher.consume_actinos_len() > 0 {
            self.dispatcher.consume_action();
            self.app_component
                .update(self.dispatcher.store(), self.area());
        }
    }
}

async fn save_issue(id: IssueId) -> Action {
    tokio::time::sleep(std::time::Duration::from_secs(3)).await;
    Action::FailIssueUpload { id }
}
```

このコードは方針を示すための例であり、実際の型名や `AppComponent::update` の引数は移行時に調整する。

キー入力処理は非同期 task にしない。
main loop は `crossterm::event::poll(Duration)` で短い間隔の待ち受けを行い、入力がある場合だけ `event::read()` で取得する。
これにより、入力がない場合でも worker action を定期的に取り込める。

```text
loop:
  app.update()
  draw
  if event::poll(timeout):
    event = event::read()
    app.handle_key_event(event)
```

入力読み取り task 化は初期実装では採用しない。
必要になった場合は、入力待ちの `crossterm::event::read()` だけを別 task に逃がし、生の terminal event を main thread に channel で戻す。
その場合でも、Component による event 解釈、Store 更新、描画は main thread に残す。

worker action と terminal event の厳密な物理時刻順序は保証しない。
アプリケーション上の順序は、main loop が channel と terminal event から受理し、`Dispatcher` に dispatch した順序とする。
ADR 2 の `IssueState::Uploading` 中の編集禁止により、保存中のローカル編集と保存完了 action の競合は UI 状態として抑止する。

mermaid の画像化処理は非同期 task として扱う。
`mermaid-cli` や `mermaid-rs-renderer` などの外部 command / renderer を使う場合、worker が process を起動し、終了 status と成果物 file の存在確認をもって完了と見なす。
成功時は成果物 path を含む action を返し、失敗時は error action を返す。
外部 process の起動と完了待ちは render path では行わない。

Dispatcher の所有方針は以下とする。

- 最終形では、`AppContainer` が `Dispatcher` を直接所有する。
- `Dispatcher` / Store は main thread のみが更新する。
- Component は原則として `Dispatcher` を保持しない。
- Component は同期的な `EventProcessResult` または `AppEffect` を返し、親 Component または `AppContainer` が action dispatch / effect 起動へ変換する。
- 初期移行では既存の `Rc<RefCell<Dispatcher>>` を main thread 内に閉じて維持してよい。
- `Rc<RefCell<Dispatcher>>` から `AppContainer` 所有の `Dispatcher` と `&mut Dispatcher` 受け渡しへ段階的に移行する。

非同期 task が返せる action は型で明示する。
たとえば issue 保存 task は `Future<Output = Action>`、またはより限定した `Future<Output = IssueUploadResultAction>` のように扱い、worker が返せる action の種類を絞る。
これにより、worker が任意の Store 更新を発生させるのではなく、許可された完了 action だけを main thread に返す境界を作る。

## Rationale

`ratatui` の immediate mode rendering では、render path を軽く保ち、I/O や長時間処理を render 中に行わないことが重要である。
外部I/Oを worker に逃がし、完了結果だけを action として main thread に戻す構成は、既存の `Action -> Store -> Component::update -> render` の流れに合う。

キー入力の解釈を main thread に残すことで、現在の Component 親子関係、focus 遷移、popup 処理を維持できる。
キー入力処理そのものを非同期 task 化すると、Component と Store の間に排他制御や順序制御が漏れやすい。
初期実装ではその複雑さを持ち込まない。

`Arc<Mutex<Dispatcher>>` を worker に渡すと、worker が Store を直接更新できるようになる。
これは実装可能ではあるが、Store 更新順序が複数 thread に分散し、`.await` をまたいだ lock 保持や UI 停止のリスクを生む。
main thread だけが `Dispatcher` / Store を所有すれば、Rust の lock ではなく application state と action 順序で同期を扱える。

worker action と terminal event の物理時刻順序を厳密に保証しないのは、TUI として必要な一貫性が main loop の受理順で十分だからである。
worker 完了時刻は Store 更新時刻ではない。
Store が変わるのは main thread が action を受理して dispatch した時点である。

`IssueState::Uploading` はこの設計と相性がよい。
保存処理中であることを Store が main thread 上で表現し、Component はそれを見て編集操作を受け付けない。
worker 側は保存処理を進めるだけで、UI の排他制御や Store 更新には関与しない。

mermaid 画像化を worker task として扱うことで、外部 process の待ち時間や失敗を UI から分離できる。
成果物 file の存在確認を完了条件に含めれば、process が成功 exit したが file が生成されていないケースも error action として扱える。

## Consequences

`Cargo.toml` に Tokio 依存を追加する必要がある。
必要な feature は、初期実装では `rt` / `rt-multi-thread`、`time`、`sync`、`process` を中心に選ぶ。
network adapter を追加する時点で HTTP client に必要な feature も検討する。

main loop は `event::read()` の永久ブロックから、`event::poll(Duration)` を使う短い待ち受けへ変更する。
これにより、入力がない状態でも worker action を取り込み、保存完了や失敗を画面に反映できる。

`AppContainer::handle_app_effect` は、同期 effect と非同期 effect の両方を扱う境界になる。
editor 起動のように terminal mode を切り替える同期処理は当面既存の形を維持し、Redmine I/O や mermaid 画像化は worker task として起動する。

`Dispatcher` の `Rc<RefCell<_>>` 共有は段階的に減らす。
最終的には `AppContainer` が `Dispatcher` を直接所有し、Component には必要な範囲で `&mut Dispatcher` を渡すか、Component の戻り値を親が action に変換する。

worker task は `Dispatcher` / Store を参照できないため、必要な入力値は task 起動時に owned data として渡す必要がある。
たとえば issue 保存では、issue id、畳み込み済み diff、または upload payload などを worker command に含める。

worker task の結果は channel に積まれるため、結果が Store に反映されるまで最大で main loop の poll interval 分だけ遅延する。
この遅延は許容する。

非同期処理のテストでは、数秒 sleep する task を network I/O の代替として使える。
これにより、`IssueState::Uploading` の表示、編集禁止、完了 action の dispatch、失敗 action の dispatch を Redmine 接続前に確認できる。

## Future Work

- `Rc<RefCell<Dispatcher>>` から `AppContainer` 所有の `Dispatcher` と `&mut Dispatcher` 受け渡しへ段階的に移行する。
- 入力読み取り task 化は必要になるまで採用しない。採用する場合も、生 event の待ち受けだけを分離し、Component による解釈は main thread に残す。
- 複数種類の worker command / worker result が増えた場合、`Action` を直接 channel で返す形から、より限定された `WorkerResult` を main thread で action に変換する形へ移行する。
- mermaid 画像化の具体的な backend は、`mermaid-cli`、Rust renderer、または他の外部 command のどれを採用するかを別途判断する。
