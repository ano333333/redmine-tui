ADR 14Architecture

15. Usecase起動要求の統一とrunnerのqueue

Status

Accepted

Context

ComponentからrunnerへUsecaseの起動を要求する方法が統一されていない。

  • AppComponentはpending_effect: Option<AppEffect>を1つだけ持つ。runnerは1周につき1回take_effectを呼び、handle_app_effectで処理する。
  • effectを設定する方法が2種類ある。install_effectは既存のeffectをassertで検査し、直接代入は検査しない。
  • AppEffectには、Redmine Usecaseの起動要求と、platformの副作用であるOpenEditorが混在している。
  • IssueSelectPopupComponentは独自のEffectとpending_effectを持つ。AppComponentはこれを取り出し、AppEffectへ詰め替える。
  • cancel_issue_uploadとcontinue_issue_uploadは、Componentから直接呼ばれている。ContinueIssueUploadでは、同期の前処理をComponentが行い、非同期処理をrunnerが起動している。Remote Journalの競合popupでCancelを選ぶと、ComponentがJournalAction::CancelRemoteUploadConflictを直接dispatchする。

pending_effectが1つしかないため、1回の処理で発行できる要求は1件に限られる。表示中Issueの親を取得するrequest_parent_issue_fetch_if_neededは、他のeffectが待っている間は要求を見送り、次のupdateで改めて判定している。この処理はupdateから要求を発行しており、ADR 6の「updateからeffectを生成しない」にも反している。

Usecaseの戻り値の型も統一されていない。

Usecase 戻り値
fetch_issue Option<FetchIssueFuture>
fetch_project_issues_page OutputがProjectIssuesAction1つのFuture
start_issue_upload Boxしていないimpl Future<Output = Vec<Action>>
start_remote_journal_upload、start_local_journal_upload、start_deleted_journal_upload、continue_remote_journal_upload 別名で中身が同じPin<Box<dyn Future<Output = Vec<Action>> + Send>>
upload_issue_action Dispatcherを受け取らないasync fn。runnerが直接spawnする
cancel_issue_upload、continue_issue_upload 同期関数。Componentが直接呼ぶ

また、あるUsecaseの完了後に別のUsecaseを起動する手段がない。そのためupload_issue_actionは、保存前GET、PUT、確認GETを1つのFutureで続けて実行し、結果を最後にまとめて返している。PUTの成功をStoreへ確定してから確認GETを始めることができず、確認GETだけを再試行する経路もない。ADR 14は各リクエストの完了Actionを適用してから後続のリクエストへ進むと定めているが、今の実行方式ではこれを実現できない。

後続のUsecaseをFutureの中で起動することはできない。理由は次の2つである。

  • FutureはSend + 'staticであり、Tokio adapterでは別threadで動く。Usecaseの起動関数はRc<RefCell<Dispatcher>>を受け取るため、Futureの中から起動できない。
  • Usecaseの起動関数は、起動時に消費済みのStoreを見て起動条件を判定する。Futureは、返したActionが消費される時点のStoreを参照できない。そのため、後続Usecaseの開始Actionを完了Actionと一緒に返すと、Storeの遷移規則に反してpanicすることがある。

Decision

Usecase起動要求をUsecaseRequestに統一する

Redmine Usecaseの起動要求を表すUsecaseRequest enumをsrc/usecases/に置く。Componentは、Usecaseを直接呼ばずにUsecaseRequestを発行する。runnerがこれを受け取って、Usecaseを起動する。1つのUsecaseRequestは1つのUsecaseに対応する。 

pub enum UsecaseRequest {
    FetchIssue { id: IssueId, with_parent: bool },
    FetchProjectIssuesPage { project_id: ProjectId, page: NonZeroUsize },
    StartIssueUpload { id: IssueId },
    CancelIssueUpload { id: IssueId },
    ContinueIssueUpload { id: IssueId, selected_local_diffs: Vec<IssuePropertyDiff> },
    PutIssueUpload { id: IssueId, diffs: Vec<IssuePropertyDiff> },
    ConfirmIssueUpload { id: IssueId },
    RetryIssueUploadConfirmation { id: IssueId },
    StartRemoteJournalUpload { issue_id: IssueId, journal_id: JournalId },
    CancelRemoteJournalUpload { issue_id: IssueId, journal_id: JournalId },
    ContinueRemoteJournalUpload { issue_id: IssueId, journal_id: JournalId, resolved_notes: String },
    StartLocalJournalUpload { issue_id: IssueId },
    StartDeletedJournalUpload { issue_id: IssueId, original_id: JournalId },
}

ContinueIssueUploadは、continue_issue_uploadの同期処理とupload_issue_actionの非同期処理を、1つのUsecaseにまとめる。CancelRemoteJournalUploadは、Componentが直接dispatchしていた競合の取り消しをUsecaseに移したものである。

Issue保存を段階ごとのUsecaseに分ける

upload_issue_actionは、保存前GET、PUT、確認GETをそれぞれ別のUsecaseに分ける。各段階の完了が次の段階を後続要求として返す。

  • 保存前GET: StartIssueUploadとContinueIssueUploadが起動する。競合があれば、今と同じく競合を返す。競合がなければ、取得したIssueを基準値にしてStoreのdiffを送信するdiffに置き換える完了Actionと、PutIssueUpload { id, diffs }の後続要求を返す。競合の続行では、送信するdiffがStoreのdiffと異なる。置き換えないと、サーバーの値を選んだ属性がローカルの値で表示される。送信するdiffは、Storeではなく要求に載せて運ぶ。
  • PUT: 成功したら、送信したdiffを基準値へ適用する完了Actionと、ConfirmIssueUpload { id }の後続要求を返す。
  • 確認GET: 成功したら、取得したIssueを取り込んでSyncedにする。

PUTの成功から確認GETの完了までは、IssueをUploadingのままにして編集を受け付けない。確認GETは短時間で終わることが多く、編集を許すと確認結果と新しい編集を比べる処理が必要になるためである。

確認GETに失敗しても、PUTの成功は取り消さない。PUTで確定した基準値のままSyncedにし、失敗の理由を残す。ヘッダには「？未確認」と表示する。利用者がrを押すとRetryIssueUploadConfirmation { id }を発行し、PUTを繰り返さずに確認GETだけをやり直す。編集を始めたとき、またはJournalの保存でIssueを取得し直したときは、失敗の理由を消す。編集した場合は次の保存で保存前GETを行い、取得し直した場合はその取得値が確認GETの代わりになるためである。

Componentは借用したRequestSinkに要求を書く

Componentは要求をフィールドに溜めない。runnerが持つRequestSinkを&mutで借用して受け取り、そこに要求を書く。RequestSinkはsrc/components/に置き、Usecaseの起動要求とeditorの起動要求を保持する。 

pub struct RequestSink {
    usecases: Vec<UsecaseRequest>,
    editor: Option<EditorRequest>,
}

AppEffectは廃止し、OpenEditorもRequestSinkへ移す。editorの起動要求は1件までとし、2件目はassertで検出する。

RequestSinkを受け取るのは、要求を発行してよい次の入口だけである。

  • AppComponent::new、AppComponent::process_event、AppComponent::handle_key_event
  • IssueSelectPopupComponent::new、IssueSelectPopupComponent::process_event

updateとrenderはRequestSinkを受け取らない。そのため、updateからは型の上で要求を発行できない。updateで競合popupを開く処理はStoreの状態の表示であり、要求ではないため、この制約の対象外である。

UsecaseRequestの値をフィールドに保存して後でRequestSinkへ書くことは、型では防げない。updateで作った要求を保存しておくことは禁止とし、レビューで確認する。

親Issueは1段だけ取得する

表示中Issueの親の題名を表示するため、親Issueを1段だけ取得する。

  • Issueを開いて詳細取得を要求するとき、ComponentはFetchIssue { id, with_parent: true }を発行する。
  • with_parent: trueの取得が完了し、親IDが分かれば、完了はFetchIssue { id: parent_id, with_parent: false }を後続要求として返す。親の取得完了は、さらに上の親を要求しない。
  • 取得済みのIssueを開くときは完了が発生しない。この場合、Componentは開く時点でStoreから親IDを読み、FetchIssue { id: parent_id, with_parent: false }も発行する。起動するかどうかはfetch_issueが判定する。

request_parent_issue_fetch_if_neededは廃止する。Issue保存時のGETで親IDが変わっても、新しい親は取得しない。この間の親の表示が古いままになることは許容する。

Usecaseの戻り値を統一する

runnerが起動するUsecaseの戻り値をOption<UsecaseTask>に統一する。引数は、Usecaseごとに必要な値が異なるため統一しない。 

pub struct UsecaseOutput {
    pub actions: Vec<Action>,
    pub requests: Vec<UsecaseRequest>,
}

pub type UsecaseTask = Pin<Box<dyn Future<Output = UsecaseOutput> + Send + 'static>>;
  • 起動関数は、同期のActionをdispatchしてからUsecaseTaskを返す。これは既存の基本形と同じである。
  • 非同期処理がない場合はNoneを返す。事前条件によって起動しない場合と、CancelIssueUploadのように同期処理だけのUsecaseが該当する。
  • UsecaseTaskは、完了Actionに加えて後続のUsecaseRequestを返せる。後続要求はデータとして返し、closureは返さない。

UsecaseRequestから起動関数への対応は、src/usecases/に置く1つの関数にまとめる。runnerは、この関数を呼んで得たUsecaseTaskをspawnするだけにする。 

pub fn start_usecase<C>(
    request: UsecaseRequest,
    dispatcher: Rc<RefCell<Dispatcher>>,
    client: Arc<C>,
) -> Option<UsecaseTask>
where
    C: RedmineClient + Send + Sync + 'static;

runnerがUsecase起動要求をqueueする

runnerはVecDeque<UsecaseRequest>を持つ。queueに要求を積むのは次の2か所である。

  • AppComponent::newまたは入力処理の後に、RequestSinkのUsecase起動要求を取り出して積む。
  • completionを受理したときに、UsecaseOutput::requestsを積む。actionsは従来どおりdispatchする。

runnerは次の手順でqueueを処理する。

drain_requests:
  while let Some(request) = queue.pop_front():
    if let Some(task) = start_usecase(request, ...):
      spawner.spawn(task)
    update()   // 起動時にdispatchしたActionを消費し、Componentを更新する

queueを処理する時点は次の2つである。

  • Component生成と入力に由来する要求: RequestSinkを受け取った処理の直後、updateの前に処理する。その後、editorの起動要求があればeditorを起動する。
  • completion由来の要求: completionのActionを消費するupdateの後に処理する。

1件起動するたびにupdateを行う。これにより、次の要求の起動時には、前の要求がdispatchしたActionが消費済みになっている。たとえば、Issueを開いたときのFetchIssueがStartFetchingをdispatchした後、同じIssueへのFetchIssueが続いても、2件目はFetchingを観測して起動しない。

editor起動中に受理したcompletionの後続要求は、queueに残す。editorから戻った後の通常loopで処理する。

platformのportは完了値の型に依存しない

BackgroundSpawnerとBackgroundCompletionを、完了値の型について汎用にする。こうすれば、platformはusecasesの型に依存しない。runnerがUsecaseOutputを型引数として指定する。

Rationale

Usecaseの起動をrunnerにまとめると、ComponentはStoreの状態を見てUsecaseを起動する責務を持たなくなる。Componentは要求を発行し、Usecaseが起動条件を判定する。この分担は、fetch_issueが起動可否を判定している現在の形と同じである。

1つの要求を1つのUsecaseに対応させると、1回の操作で何を起動するかをComponentの発行内容から読み取れる。取得済みのIssueを開く操作では、Issue自身と親の2件を発行することがComponentのコードに現れる。

要求をフィールドに溜めず借用したRequestSinkに書かせるのは、updateから要求を発行できないことを型で保証するためである。pending_effectのようなフィールドがあると、updateからも書き込めてしまい、assertでは実行時にしか検出できない。RequestSinkは一時的な借用なので、Componentのフィールドに保持することもできない。

後続要求をデータとして返すと、Usecaseの単体テストで後続要求を検証できる。closureを返す方法ではテストで中身を検査できない。また、Clientの型引数がclosureの型に現れる。

入力由来の要求をupdateの前に起動するのは、同期の前処理の結果を同じupdateへ反映するためである。たとえばContinueIssueUploadはClearUploadConflictsをdispatchする。これをupdateの後に起動すると、updateが競合情報を観測し、閉じたはずの競合popupを開き直す。現在のContinueIssueUploadはComponentが同期処理を直接呼んでいるため、この問題が起きていない。一方、ContinueRemoteJournalUploadは競合情報を同期的に消さないため、続行直後のupdateで競合popupが開き直る問題が起きている。

completion由来の要求をupdateの後に起動するのは、後続要求の起動条件が、completionを反映した後のStoreに依存するためである。

親の取得を1段に限るのは、画面に表示するのが親の題名だけだからである。

Consequences

  • ADR 3、ADR 6、ADR 7、ADR 10、ADR 14のうち、次の記述は本ADRで置き換える。
    • AppEffectが非同期処理の開始要求を表すという記述（ADR 3）。
    • 1回の入力で発行できる要求を、AppComponentの単一のpending_effectで検査するという記述（ADR 6、ADR 7）。重複の抑止は、queue処理中に1件ごとにupdateすることで担保する。
    • IssueSelectPopupComponent::take_effectと、popupの初期effectをpending_effectへ移して共通の処理点で開始するという記述（ADR 7）。
    • main loopのeffect処理の位置（ADR 7のmain loop、ADR 10の手順5）。
  • ADR 6の「updateからeffectを生成しない」という規則は維持し、本ADRで型によって保証する。
  • AppEffect、pending_effect、install_effect、take_effectは、AppComponentとIssueSelectPopupComponentの両方から削除する。take_effectを使うテストは、RequestSinkの中身を検査する形に変える。
  • 次のUsecaseをUsecaseTaskに移行する: fetch_issue、fetch_project_issues_page、start_issue_upload、start_remote_journal_upload、start_local_journal_upload、start_deleted_journal_upload、continue_remote_journal_upload。個別の型エイリアスは削除する。
  • upload_issue_actionを段階ごとのUsecaseに分割する。これが後続要求を使う最初のUsecaseになり、ADR 14の「各リクエストの完了Actionを適用してから後続のリクエストへ進む」を実現する。
  • cancel_issue_uploadとcontinue_issue_uploadは、Componentから呼ばれなくなる。Remote Journalの競合の取り消しも、ComponentからdispatchせずUsecaseで行う。
  • 入力由来の要求をupdateの前に起動することで、ContinueRemoteJournalUploadの競合popupが開き直る問題も、起動時に競合情報を同期的に消せば解消できるようになる。
  • runnerは、入力処理の直後にupdateしている今の順序を変え、RequestSinkの処理をupdateの前に入れる。
  • BackgroundSpawnerの型が変わるため、Tokio adapterとWeb adapterの両方を変更する。
  • docs/architecture.mdのusecases、runner、AppEffect、ComponentからUsecaseへの依存の説明を更新する。
  • 親の取得（with_parent: false）が終わる前にその親を開くと、さらに上の親は取得されない。取得中のFetchIssueは起動されず、Storeにも親IDがないためである。起動済みの取得に親の取得を後から依頼する手段は、別途設計する。
  • 起動時に呼ぶload_initial_entitiesは、runnerのloopが始まる前に実行するため対象外とする。
  • issue_popup_optionsのobserverは、popupの選択結果をComponent上で直接dispatchする処理であり、Usecaseの起動要求ではないため対象外とする。

Alternatives Considered

  • pending_effectをVecに変えて複数の要求を溜め、updateで書き込まないことをassertで検査する: updateからの書き込みを実行時にしか検出できないため採用しない。
  • UsecaseRequestをsrc/usecases/の外から作れないようにし、RequestSinkのvariantごとのメソッドでしか発行できないようにする: フィールドへの保存も防げるが、variantごとにメソッドが増え、Componentのテストで要求の中身を検査しにくくなるため採用しない。
  • Actionに要求を表すvariantを追加し、runnerがdispatch前に取り除く: platformの型は変わらないが、ActionがStoreの状態遷移を表すという意味が崩れるため採用しない。
  • runnerがActionを監視し、特定の完了Actionに反応して後続を起動する: どのUsecaseから生じた完了かを区別できず、制御の流れがUsecaseの外に隠れるため採用しない。
  • 後続処理をclosureで返す: テストで中身を検査できず、Clientの型引数がclosureの型に現れるため採用しない。
  • fetch_issueが常に親の取得を後続要求として返す: 親の取得完了がさらに上の親を要求し、根元のIssueまで取得してしまう。表示に必要なのは親の題名だけなので採用しない。
