# 1. リファクタリング初期方針

## Status

Accepted

## Context

現在のコードには、文字列を読むだけの関数・メソッドでも `&String` を受け取っている箇所がある。

例:

- `BodyWidgetState::update(width, body: &String)`
- `render_in_buffer(body: &String, width)`
- `create_title_widget(title: &String)`
- `create_header(creator: &String, ...)`

一方で、`Issue` や `Journal` などのアプリ状態・エンティティは `String` を保持している。
これは、YAMLや編集結果から読み込んだ文字列をアプリ内部で所有する必要があるため自然である。

`cargo clippy --all-targets --all-features` では、`&String` を受け取る箇所に `clippy::ptr_arg` の警告が出ている。
警告内容は概ね以下の意味である。

> `&String` の代わりに `&str` を使うべき。`String` への参照を要求すると不要に具体的になり、文字列スライスで足りる場面でも `String` しか受け取れなくなる。

Clippy の実際の警告例:

```text
warning: writing `&String` instead of `&str` involves a new object where a slice will do
help: change this to: `&str`
```

## Decision

文字列型の方針を以下にする。

1. アプリ状態・エンティティ・イベント payload など、文字列を所有して保持する型は `String` を使う。
2. 文字列を読むだけの関数・メソッド引数は `&str` を使う。
3. 文字列を受け取って内部で所有する constructor / builder は `impl Into<String>` を使ってよい。
4. `&String` は原則として使わない。
5. `Into<str>` は使わない。

## Rationale

`String` は所有する文字列であり、`&str` は借用した文字列スライスである。
この違いをAPI境界に反映すると、関数の責務が読みやすくなる。

`Issue.subject` や `Journal.notes` のようなフィールドはアプリ状態として保持されるため、`String` が適している。
`str` は unsized type なので、そのまま通常の struct field として保持できない。
また、struct に `&str` を持たせると lifetime が状態管理全体に伝播し、TUI の component / widget / store の境界が扱いづらくなる。

一方、描画・markdown変換・hash計算・ラベル生成のように文字列を読むだけの処理では、`&str` が適している。
`&str` は `String`、文字列リテラル、slice のどれからでも自然に渡せる。
`&String` にすると呼び出し側へ `String` の存在を要求してしまい、APIが不要に狭くなる。

`impl Into<String>` は、最終的に `String` として保存する関数に限って有用である。
例えば `IssueSelectPopupProject::new(id, name: impl Into<String>)` のような constructor では、呼び出し側が `&str` と `String` のどちらでも渡せるため、テストや変換コードが書きやすくなる。

ただし、読むだけの関数に `impl Into<String>` を使うと、不要な allocation や clone を発生させやすい。
また、その関数が文字列を所有するのか読むだけなのかがAPIから分かりにくくなる。
そのため、`impl Into<String>` は所有化する境界に限定する。

`Into<str>` は実用上ほとんど使わない。
`str` は unsized type であり、通常の値として受け取れないためである。
必要なら `Into<String>`、特殊な所有スライス最適化が必要になった場合のみ `Into<Box<str>>` を検討する。

## Consequences

今後のリファクタリングでは、まず `clippy::ptr_arg` の警告が出ている `&String` 引数を `&str` に置き換える。

代表例:

```rust
fn render_in_buffer(body: &String, width: u16) -> Buffer
```

は以下に変更する。

```rust
fn render_in_buffer(body: &str, width: u16) -> Buffer
```

`String` を保持する struct のフィールドは、明確な理由がない限り変更しない。
constructor が必要になった場合は、所有フィールドに対応する引数を `impl Into<String>` として受け取り、内部で `.into()` する。

この方針により、所有する場所と借用する場所が分かれ、APIが柔軟になり、Clippy の `ptr_arg` 警告も解消しやすくなる。

## Component lifecycle と Widget 生成

### Context

`src/components/issue/` 配下の component は、component が `create_widget` で `Widget` を実装した struct を返し、その `Widget::render` が描画を行う形で揃っている。

component の基本 lifecycle は以下とする。

1. Store の action 処理時は、dispatcher が action を1件処理し、そのたびに component の `update` を呼ぶ。
2. 同期的なキーイベント処理時は、`process_event -> update -> render` の順に進む。
3. 他 component のキーイベント処理に伴う同期的な focus 遷移は、`focus_event -> update -> render` の順に進む。

Store の更新は dispatcher を介して行う。
初期セットアップを除き、action の処理と `update` が交互に行われることは意図した設計である。

`create_widget` が `&Store` を受け取る component がある。
これは描画に必要な entity を Store から取得するためである。
これを `update` 側に寄せる案もあるが、その場合は以下の問題がある。

- component が entity 参照を保持すると、frame 間をまたがる lifetime の管理が重くなる。
- component が entity の一部を所有して保持すると、毎回の clone/copy と Store との二重管理が増える。
- Store 更新と component 内 view model の同期漏れを気にする必要が出る。

一方で、`create_widget(&Store)` には以下の注意点がある。

- component が Store の構造に結合する。
- `create_widget` 時点で必要な entity が欠損している場合の扱いを決める必要がある。
- テストで widget を作る際に Store fixture が必要になりやすい。
- 重い派生処理を `create_widget` に入れると render path が重くなる。

### Decision

`create_widget` の返り値は `Widget` を実装した concrete struct とし、`Option<Widget>` にはしない。

`create_widget(&Store)` は許容する。
ただし、`create_widget` で行う Store 利用は、描画に必要な entity の取得と軽い関連解決に留める。
幅依存の buffer、markdown render cache、scroll/focus 補正などの重い派生状態は `update` 側で扱う。

`src/components/issue/` 配下の component では、`create_widget` 時点で対象 issue が Store に存在することを設計上の不変条件とする。
この不変条件に依存する箇所では、無言の `unwrap()` ではなく、不変条件を説明する `expect(...)` を使う。

将来的には、`IssueDetailComponent` が対象 issue の欠損を検知した場合、子 component をインスタンス化しない方針へ移行する。
この移行後も、子 component の `create_widget` は「対象 issue が存在する」前提でよい。

### Consequences

現時点では `create_widget(&Store)` を無理に排除しない。
これにより、component に entity 参照や entity のコピーを保持する必要がなくなり、Store を single source of truth として扱いやすくなる。

一方で、`create_widget` 内の Store lookup は設計不変条件に依存するため、panic する場合は何が破れたか分かる message を残す。
例えば以下のように書く。

```rust
let (issue, _) = store
    .get_issue(self.id)
    .expect("PropertyComponent requires its issue to exist in Store");
```

今後 `IssueDetailComponent` の欠損時処理を整理する際は、子 component 側で `Option<Widget>` を返すのではなく、親 component が子 component の生成・描画対象を制御する。
