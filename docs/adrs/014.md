# 14. IssueとJournalの取得単位、編集差分、保存状態

## Status

Accepted

## Context

現在のIssueAggregateは一覧用Issueと詳細属性、子IssueのID一覧を持つ。親IssueのIDは保持していない。Journal本体と編集状態はJournalStoreにあり、IssueStoreとは別に更新される。

RedmineのIssue詳細GETでは、Issue本体とJournal、子Issueの情報を一度に取得できる。しかし初回取得ではJournalとIssueを別々のActionで登録している。ActionごとにComponentを更新するため、同じ応答の一部だけを反映した状態が生じる。Issue保存前GETではJournalを捨て、Journal保存時のGETではIssue本体を捨てている。

Issueのローカル編集は、本体の変更とIssuePropertyDiffの追加で表している。同じ編集内容を本体と差分の両方に反映する必要があり、サーバーから取得した値と編集中の値の区別も曖昧になる。

LocalJournalの投稿はPUTと確認GETを続けて実行する。PUTが成功してもGETに失敗するとLocalOnlyへ戻るため、確認GETだけを再試行したい場合にも投稿を繰り返してしまう。

## Decision

### 1リクエストの結果を1つのActionで反映する

「1 APIリクエスト = 1トランザクション」を、アプリ内での反映単位として採用する。Issue詳細GETの結果は、IssueStoreが検証してから1つのActionで反映する。Issue本体、Journal、子一覧の適用途中にComponentを更新しない。ActionごとにComponentを更新する既存のlifecycleは維持する。

GET、PUT、確認GETはそれぞれ独立したリクエストとして扱う。確認GETの失敗でPUT成功を取り消さない。この方針は、サーバーのGETがDBの同一時点の値を返すことや、事前GETとPUTの間に他者の更新が入らないことを保証するものではない。

| API                                              | 用途               | 保存対象                                |
| ------------------------------------------------ | ------------------ | --------------------------------------- |
| `GET /issues/:id.json?include=children,journals` | 詳細取得・競合確認 | IssueAggregateと関連する取得情報        |
| `PUT /issues/:id.json`                           | Issue属性の保存    | 送信したIssue属性                       |
| `PUT /issues/:id.json`の`notes`                  | Journalの新規投稿  | LocalJournalまたはDeletedJournalのnotes |
| `PUT /journals/:id.json`                         | 既存Journalの保存  | 対象Journalのnotes                      |

Issue属性、既存Journal、LocalJournal、DeletedJournalは個別に保存する。APIがIssue属性とnotesの同時送信に対応していても、今回の保存操作は統合しない。

### IssueAggregateがJournal本体を所有する

IssueAggregateに親を示す`parent_id: Option<IssueId>`とJournal一覧を持たせる。IssueAggregateと、その中の一覧用Issueの名前は維持する。ProjectIssuesStoreの一覧モデルも変更しない。

Journal本体の所有先をIssueAggregateに一本化し、JournalStoreは撤去する。JournalActionの処理、Issue属性とJournal間のupload排他、Journalのgetterは、IssueStoreがIssueの取得状態とあわせて扱う。IssueStoreへ移す状態型はRemoteJournalStateであり、Journal本体を内包するRemoteJournalEntryは使わない。

`include=journals`では、JournalのID、投稿者、notes、作成日時、更新日時、更新者、非公開フラグ、変更詳細を取得できる。Journal内のissue_idは外側のIssueから補える。現在のJournalを構築する情報は、このGETで得られる。

取得対象は利用者に見える履歴である。権限によって非公開notesや一部の変更詳細が除外され、notesも可視の変更詳細もないJournalも返らない。取得結果から消えたことと、DBから削除されたことは区別する。

### 子Issueの情報は表示用の取得データとして扱う

`include=children`の各要素にはID、トラッカー、題名と、その下のchildrenが再帰的に含まれる。子Issueの説明文、ステータス、Journalなどの詳細は含まれない。子Issue自身の親IDは詳細GETの`parent.id`で取得し、親変更の送信には`parent_issue_id`を使う。

子一覧はStoreに取得済みの関連情報として保持する。子Issueの詳細が取得済みなら、表示にはStoreから得た編集反映後の値を使う。未取得なら子一覧の取得情報を使う。取得済みIssueだけからの逆引きでは、未取得の子が欠落するため、取得した子一覧を保持する。

子の題名などを表示用に保持する場合も、子Issueの編集対象として二重に管理しない。親変更の編集UIは別の機能として扱う。

### 既存IssueEntry enumを維持し、本体をローカル編集で変更しない

[ADR 11](011.md)のIssueEntry enumを維持する。取得済みの各variantが保持するIssueAggregateはサーバーから取得した基準値とし、ローカル編集では変更しない。Issue属性の編集はIssuePropertyDiff、既存Journalの編集はJournalNotesDiffとして保持する。画面へ返す値は、基準値に差分を適用して作る。

差分を元に戻して実効的な変更がなくなれば、該当対象をSyncedへ戻す。再取得時は新しいサーバー値と差分を比較してから基準値を更新する。競合判定に必要なbeforeを、比較前に新しい値へ置き換えない。

IssueStateのSynced、Edited、UploadingはIssue属性の保存状態だけを表す。Journalの編集や投稿下書きは含めない。IssueStateがSyncedで、あるJournalのRemoteJournalStateがEditedである状態を許可する。

取得済みのIssueEntryには、次の付加情報を持たせる。

| 付加情報                          | 保持する内容                                          |
| --------------------------------- | ----------------------------------------------------- |
| JournalIdごとのRemoteJournalState | 全JournalのSynced、編集差分、保存状態、競合・失敗情報 |
| LocalJournalEntry                 | 0件または1件の新規投稿下書きと保存状態                |
| DeletedJournalの一覧              | 複数の消失Journalの元ID、編集後notes、保存状態        |

RemoteJournalStateはSyncedも含めて全件を明示する。状態MapにないことをSyncedと解釈しない。Issue属性の状態が変わるときも、Journalの差分と下書きを引き継ぐ。付加情報の共通部分をstructにまとめても、IssueEntryのenumによる状態の区別は維持する。

Journal操作はIssue取得済みの場合だけ許可する。Issue本体がない状態でJournalだけを登録する経路は廃止し、初回GETでまとめて登録する。

### Issue保存前GETでJournalの競合も検出する

Issue保存Usecaseでは、次の順序で取得と競合解決を進める。

1. Issue本体、Journal、子一覧をGETする。
2. 取得結果から消えた編集中JournalをDeletedJournalへ退避する。残存Journalのnotesも差分と比較し、競合を各Journalの状態へ保持する。
3. Issue属性に競合があれば、利用者が項目ごとの値を選択した後、再び1から確認する。
4. Issue属性に競合がなければ、GET結果でIssueAggregateを更新する。未保存の差分、LocalJournal、DeletedJournalは保持する。

Journalの競合確認では、diff.before、diff.after、取得したnotesを比較する。編集後と同じ値がサーバーに反映済みなら差分を解消する。Journalの競合解決は、そのJournalを個別に保存する操作で扱う。

現行RemoteJournalStateはUploadingだけに競合情報を持つ。Issue保存前GETでは、未送信のJournalでも競合を検出するため、送信中でなくても競合を保持できるよう状態定義を調整する。

手順4はサーバーから取得した基準値の更新である。その後、Issue差分を適用した更新要求をPUTし、成功した送信分を確定する。確認GETでは更新日時や自動生成されたJournalを取り込む。確認GETに失敗した場合の再試行はGETだけを行う。

同じIssueについて同時にuploadできる操作は1件とする。Issue属性とJournal間の排他検査はIssueStore内で行う。各リクエストの完了Actionを適用してから後続のリクエストへ進み、Componentに通信手順を持たせない。

### 消失した編集中JournalをDeletedJournalへ退避する

DeletedJournalはIssueEntryの付加情報として保持する。元JournalIdと編集後notesを残し、通常のRemoteJournalStateから退避対象を外す。IssueAggregateの取得済みJournal一覧には含めない。

退避は元JournalIdで識別する。競合解決によってGETを繰り返しても、同じJournalを二重に退避しない。DeletedJournalの退避や保存によって、既存LocalJournalを置き換えない。

DeletedJournalは対象を選択してctrl+sを押すと、新規Journalとして投稿する。LocalJournalと同じく、`PUT /issues/:id.json`のnotesを使う。元の投稿者、日時、変更履歴を新規投稿として送信しない。Issue保存中の自動再投稿や、破棄・再投稿の選択確認は行わない。

IssueのGETで元JournalIdが再出現したら、GET時のサーバーnotesをbefore、DeletedJournalの保存notesをafterとするJournalNotesDiffを作る。通常のRemote Journalの編集へ戻すと同時にDeletedJournalを除去する。両値が同じなら差分を残さずSyncedにする。

### 投稿PUTの成功時に下書きを削除する

LocalJournalとDeletedJournalは、投稿PUTの成功Actionで対象を削除する。後続GETに失敗しても復元しない。確認GETに失敗したことを通知し、再取得を可能にする。PUT成功からGET成功まで、新しいJournalが一覧にまだ現れない場合がある。

PUTが失敗した場合は、投稿内容を保持して失敗を通知する。通信が切れて成功応答を受け取れない場合も同様に扱う。サーバーでは保存済みだった場合、利用者の手動再送で二重投稿になり得るが、これを許容する。重複防止の専用状態や照合処理は設けない。

### API固有の値表現はRedmineClientで変換する

Entity、Store、UsecaseはOptionなどのRustの表現を使う。Redmine APIが要求するnull、空文字、項目省略への変換はRedmineClientのHTTP実装が担当する。例えば担当者解除はRust側でNoneとして表し、ClientがAPIの解除表現に変換する。

部分更新で送信対象を選ぶ場合は差分などで対象を示し、Noneと「今回は送信しない」を区別する。編集差分と更新要求は、送信可能な属性に合わせて整理する。

## Error Handling

[ADR 9](009.md)のエラー分類と、[ADR 12](012.md)の存在を前提にするgetterの契約を維持する。不正な状態遷移、要求IDとの不一致、Journalの所有関係・ID重複は適用前に検査する。一部のデータだけを書き換えてから不正なActionを拒否しない。

外部通信の失敗は状態へ反映し、利用者に通知する。GET失敗で編集差分や退避データを破棄しない。成功したPUTと、後続GETの失敗は別の結果として保持する。

## Rationale

Issue詳細GETの応答とStoreの適用単位を揃えることで、IssueとJournalの部分的な反映をなくす。Entityには取得値、IssueEntryには編集差分と通信状態を置き、画面表示と競合判定の基準を明確にする。

既存IssueEntry enumを維持するため、状態と付加情報の組み合わせを型で制限する設計を継続できる。Issue属性とJournalはAPIごとに保存し、それぞれの成功・失敗を独立して扱う。

DeletedJournalを別に保持すれば、LocalJournalを最大1件とする契約を維持したまま複数の編集内容を退避できる。手動保存にすることで、Issue保存Usecaseに複数投稿の順序や途中再開を組み込む必要もなくなる。

## Consequences

JournalStoreを撤去し、そのAction処理とgetterをIssueStoreへ移す。IssueAggregateがJournalを所有するため、HTTP実装、Demo client、fixture変換、テストデータの組み立ても更新する。fixture形式を変える場合はseeder、SQL、整合性テストへの影響を確認する。

現在のget_issueはIssueAggregateへの参照を返す。差分を適用した表示値を返すため、getterと呼び出し側を変更する必要がある。所有値を返すか、参照を組み合わせた表示用の型を返すかは実装時に決める。保存済み本体の存在を要求する契約は維持する。

実装時にはdocs/architecture.mdを更新する。既存ADRは書き換えず、本ADRを所有関係と同期処理の更新として参照する。

検証では、1回のAction適用で取得結果が揃うこと、未保存差分が維持されること、Issue属性の状態遷移でJournalの作業が失われないことを確認する。消失と再出現、再GETでの二重退避防止、複数DeletedJournalとLocalJournalの共存も対象とする。

投稿については、PUT成功時の下書き削除、確認GET失敗後のGETのみの再試行、PUT失敗時の内容保持を検証する。Redmine clientテストで親IDとJournalの取得・更新契約を確認し、UI変更ではsnapshotとctrl+sによる保存操作を確認する。

Journalの空notes更新では、取得一覧からの消失とDB上の削除を同一視しない。対象Redmineの応答を契約テストで確認する。共通層の変更はnativeのテストとWebのcompileでも検証する。

## Alternatives Considered

Issue本体を編集しながら差分も保持する方式は、同じ編集を二重に適用する必要があるため変更する。IssueStateを差分から毎回計算する方式も採らず、既存enumを維持する。

消失Journalを複数のLocalJournalへ変換する案に代えて、元IDを保持するDeletedJournalを採用する。元IDが再出現した場合に、サーバー値から退避値への編集として戻せる。

RemoteJournalStateを編集中のJournalだけに持たせる案は採用しない。全件のSyncedを明示し、本体と状態の対応を検査できるようにする。

## Future Work

親変更の編集UIと、Project Entityが現在の一覧用Issue相当を所有するかは別途検討する。DeletedJournalの表示、選択、編集、ローカルでの破棄操作の詳細は実装時に具体化する。
