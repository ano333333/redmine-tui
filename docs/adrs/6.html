ADR 6

Issue詳細の非同期取得状態と表示Component

Accepted

Context

Issue選択ポップアップは、Issue詳細をまだ取得していないIssueも一覧候補として表示する。一覧用の ProjectsIssue はID、Project ID、subject、description、statusだけを持ち、詳細画面が必要とする完全な Issue ではない。そのため選択直後に IssueDetailComponent を生成すると、IssueStore に対象Issueが存在せず、描画時の不変条件に違反する。

既存の AppComponent は IssueDetailComponent を直接所有する。詳細ComponentはIssueがStoreに読み込み済みであることを前提とし、未取得、取得中、取得失敗の表示を担当しない。一方、詳細のHTTP取得は非同期であり、その間も安全に描画とキー入力を継続する必要がある。

現在の IssueState は Synced、Edited、Uploading で構成され、いずれもIssue本体の存在を前提とする。今回は完全な状態モデル再設計を行わず、未取得Issueの初回fetchを表す暫定状態を追加する。

Issue選択、y によるポップアップ再表示、同じIssueの再選択が短時間に行われても、重複した完了結果がローカル編集を上書きしないよう、fetch中の再取得抑止と完了Actionの状態検証を行う。プロジェクト別Issue一覧の取得、ページ状態、一覧用entityはADR 7で扱う。

Decision

IssueStateの暫定拡張

IssueState に Fetching と FetchFailed を追加する。

pub enum IssueState {
    Fetching,
    FetchFailed { message: String },
    Synced,
    Edited,
    Uploading,
}
Fetching と FetchFailed ではIssue本体を持たない。
Synced、Edited、Uploading ではIssue本体を必ず持つ。
IssuePropertyDiff とupload競合情報は、Issue本体を持つ状態だけで利用する。

親StoreはIssue本体の有無とは独立して Option<&IssueState> を返すgetterを公開する。未登録Issueは None、登録済みの各stateは Some(&IssueState) とする。既存の get_issue は本体を持つ場合だけ値を返し、Fetching と FetchFailed では None を返す。

fetch用IssueAction

StartFetching { id }
FetchSucceeded { id, issue }
FetchFailed { id, message }
未登録または FetchFailed のときだけ StartFetching を受理して Fetching へ遷移する。
StartFetching は同じIDの古いIssue本体、diff、upload競合情報を保持しない。
現在が Fetching で、Actionの要求IDと issue.id が一致するときだけ FetchSucceeded を受理し、Issueを登録して Synced へ遷移する。
現在が Fetching のときだけ FetchFailed を受理し、messageを持つ失敗状態へ遷移する。
Fetching 中の再開始と、その他の状態または未登録へ遅れて届いた成功・失敗Actionは無視する。

ADR 2で定めた編集・保存の遷移を含め、今回のfetch状態を追加した IssueState 全体の状態遷移は以下とする。遷移ラベルはStoreにdispatchされるActionを表す。

Fetching と FetchFailed はIssue本体を持たない。
Synced、Edited、Uploading はIssue本体を持つ。

Fetching への重複した StartFetching と、Fetching 以外へ届いたfetch完了Actionは状態を変えないため、図には遷移として記載しない。後述する受理条件に反する Sync も、内部ライフサイクル違反としてpanicするため記載しない。

完了にはGenerationを付与せず、同じIssueに同時に複数fetchを開始しないことと完了時の状態検証を暫定的な競合防止規則とする。明示的な再読み込みやcancelで複数世代を許可する場合はGenerationを導入する。

既存fixture用 Load は、Issue本体とstateの両方が未登録の場合だけfixtureを登録して Synced にし、いずれかが既に存在すれば何も変更しない。これにより、Fetching または FetchFailed のIDへ Load が届いても、Issue本体だけを追加して不変条件を壊さない。

upload成功等の Sync は、Issue IDが完全に未登録の場合と、Edited、Uploading から受理する。Synced、Fetching、FetchFailed への Sync は内部ライフサイクル違反としてpanicする。編集とuploadの既存遷移は維持し、FetchSucceeded は初回登録専用として Sync と混同しない。

Issue詳細取得usecase

Issue IDを受けて RedmineClient::get_issue を呼び、fetch完了Actionを返すusecaseを追加する。worker action senderはusecaseへ渡さない。

未登録または FetchFailed なら StartFetching を同期dispatchし、HTTP取得のFutureを返す。
Fetching、Synced、Edited、Uploading なら新しいHTTP取得を開始しない。

StartFetching はその場でconsumeせず、main loopの通常updateでconsumeする。Futureは Future<Output = IssueAction> + Send + 'static とし、成功は要求IDとIssue本体を含む FetchSucceeded、失敗は表示用messageを含む FetchFailed を返す。usecaseはClient結果の issue.id が要求IDと一致することも検証し、不一致を FetchFailed に変換する。spawnとworker action channelへの送信はmainが担当し、Clientは Arc<C>、C: Send + Sync とする。

重複抑止の範囲: 通常のユーザー入力イベント間について保証する。1回の入力イベントまたは初期化処理が生成できるIssue詳細fetch effectは最大1個で、AppComponentの単一 pending_effect が検査する。入力イベント後のupdateが StartFetching をconsumeしてから次の入力を受けるため、その次は Fetching を観測する。同じupdateを挟まずusecaseを直接2回呼ぶことは上位層の内部ライフサイクル違反とする。

IssueComponent

AppComponent と IssueDetailComponent の間に IssueComponent を追加する。少なくとも対象 IssueId と Option<IssueDetailComponent> を保持し、Storeの状態に応じて表示を切り替える。

Fetching: 詳細を生成せず、「表示中です」とだけ表示するWidgetを使う。
FetchFailed: 詳細を生成せず、エラーと「r で再試行」を表示する。
Synced、Edited、Uploading: IssueDetailComponent を使う。
未登録: 詳細を生成せず、初回fetch effectを要求する。

詳細ComponentはIssueが読み込み済みで、かつ未保持の場合だけ生成する。IssueComponent は生成時に受け取った1つの対象Issueだけを破棄されるまで表示し、対象IDを変更するメソッドは設けない。別Issueの遅延fetchはStoreへ登録するだけで現在の表示対象を変えない。

Component lifecycleとeffect生成点を次のように固定する。

IssueComponent::new は対象IDとStoreを受け取り、未登録または FetchFailed なら FetchRequested { id } を戻り値として一度だけ返す。
Issue選択が確定するたび、AppComponentは同じIssue IDでも新しい IssueComponent を生成して置換する。
ポップアップ表示中と、選択せずに閉じた場合は、背後の IssueComponent を保持する。
update は読み込み済みになったときの詳細Component生成と表示切替だけを行い、effectを生成しない。Fetching と FetchFailed では詳細Componentを保持しない。
render はI/Oやeffect生成を行わない。

これにより、worker Actionをconsumeしたupdateでは詳細Componentの生成だけが行われ、キー入力後または初期化時にしか取り出されないAppEffectを取り逃がさない。

process_event は、IssueDetailComponent が存在する場合、同じeventを最初に IssueDetailComponent::process_event へ渡す。Detailが結果を返した場合はその結果をそのまま上位へ委譲し、IssueComponent 自身は同じeventを解釈しない。Detailがeventを未処理（None）とした場合、またはDetailが存在しない場合だけ、外側Componentが自身のキー入力として y と r を判定する。将来キーが競合した場合もDetailを優先する。

y はstateにかかわらずIssue選択ポップアップを開く要求を返す。r は FetchFailed の場合だけ FetchRequested { id } のようなComponent結果をAppComponentへ返す。現時点のDetailは y と r を処理しないため、これらは未処理eventとして外側の IssueComponent が担当する。WidgetはStoreを直接参照せず、Componentから表示状態とmessageを受け取る。

AppComponentは FetchRequested をIssue詳細取得 AppEffect へ変換し、単一 pending_effect へ登録する。mainがeffectを処理するとusecaseが StartFetching をdispatchし、次の通常updateからmessageを消して「表示中です」へ切り替える。

Issue選択後の遷移

Issue選択後、AppComponentはポップアップを閉じる前にADR 7の InvalidateGeneration をdispatchする。その後、ポップアップを除去し、選択されたIssue IDを対象とする新しい IssueComponent を生成して設置する。

読み込み済みならfetchせず詳細表示へ切り替える。
未登録または FetchFailed なら詳細取得effectを上位層へ渡す。
Fetching なら追加fetchを開始せず、「表示中です」を継続する。

Issue選択確定を返す1回のキーイベントは、プロジェクト移動、ページ移動、再試行を同時には返さない。したがって選択確定時にポップアップが保持するページ取得effectは必ず空であることを内部不変条件として検査する。

AppComponentは InvalidateGeneration のdispatch、popupの除去、IssueComponent::new(store, id)、AppComponentへの設置の順に処理し、new が返した FetchRequested を詳細fetch effectへ変換して pending_effect へ登録する。前の入力イベントで作られたeffectはmainが取り出し済みであり、選択確定時に既存 pending_effect があれば内部ライフサイクル違反として検出する。

重複抑止: 新しいComponentを生成してもStoreのstateは共有される。「Issueを選択する → yを押す → 同じIssueを選択する」操作では2回目に Fetching が観測され、HTTP取得を追加しない。FetchFailed なら new が再試行effectを返す。

Error Handling

Clientエラーはusecaseが FetchFailed { id, message } へ変換し、Storeは対象Issueが現在 Fetching の場合だけ失敗を反映する。IssueComponent はmessageと再試行案内を表示し、r で同じIssueの取得を再開する。

再試行開始時は FetchFailed から Fetching へ遷移し、以前のmessageを表示しない。失敗は他のIssue本体、編集diff、upload状態、プロジェクト別Issue一覧へ影響させない。

Rationale

component詳細の不変条件を維持する

外側に状態解決Componentを置き、IssueDetailComponentの「Issueは必ずStoreに存在する」という前提を保つ。

store一方向データフローで非同期状態を扱う

FetchingとFetchFailedをStoreに置き、Componentの生存期間を越えるworker Actionと失敗通知を既存フローで処理する。

safety初回fetchをSyncから分離する

Fetchingからだけ成功を受理し、遅延fetchが既存Issueや編集内容を上書きすることを防ぐ。

scope完全な2軸化は先送りする

upload、diff、競合解決を同時に変更せず、今回必要な暫定variantに範囲を限定する。

Consequences

IssueState が String を含むvariantを持つため、既存の Copy 前提を見直し、必要箇所では参照またはcloneを使う。getterと不変条件testはstateだけ存在してIssue本体がない状態も扱う。

Store test: 開始可能状態、重複抑止、要求IDとIssue IDが一致する成功だけの登録、不一致成功Actionの無視、失敗message、遅延完了の無視、編集・upload済みIssueの保護、不変条件、Fetching と FetchFailed へのfixture Load がIssue本体を追加しないこと、Synced、Fetching、FetchFailed への Sync がpanicすること。
Usecase test: 同期的な StartFetching dispatch、重複抑止、ID一致検証、成功・失敗Action変換、sender非依存。
Component test: 状態ごとの表示、詳細Component生成、effect生成点、Detailが処理したeventを外側で再解釈しないこと、Detailが未処理または不在の場合の y、失敗時の r、別Issue完了時の表示対象維持。
AppComponent test: popup表示中とcancel時のComponent保持、同一Issue IDを含む選択確定時の再生成、InvalidateGeneration から pending_effect 登録までの順序と不変条件。
Widget snapshot: 「表示中です」とfetch失敗・再試行案内。

Alternatives Considered

fetch状態をIssueComponentだけで保持する

表示との対応は直接的だが、worker ActionはComponentの生存期間を越えて到着し、StoreにIssueがないまま失敗だけを通知する別経路も必要になるため採用しない。

既存のSync Actionをfetch成功にも使う

Action数は増えないが、Sync は既存Issueの置換やupload完了にも使われ、重複fetchの遅延結果が編集済みIssueを置換し得るため採用しない。

IssueStateを直ちに完全な2軸へ分離する

同期・編集状態とfetch/upload進行状態を独立させればGenerationを含む厳密な管理が可能だが、既存diff、upload、競合解決の遷移全体へ影響するため、今回は暫定variant追加に留める。

Future Work

Synced / Edited をIssue本体とdiffから導出し、fetch/upload進行状態とGenerationを別軸で管理する。
明示的な再取得、cancel、複数世代fetchを導入する場合のstale completion排除。
fetchとuploadが同時に要求された場合の状態遷移整理。
fetch失敗messageの構造化と、ログ向け情報・UI向け文言の分離。
同一Issue再選択時のcursor、scroll、focusの復元をAppComponent以上のlayerで扱う。

現時点では通常のApp lifecycleで同じIssueに複数のfetchを同時に開始せず、Fetching からの完了だけを受理することで競合を防止する。
