# 17. 添付画像のダウンロードと表示用データの保持

## Status

Accepted

## Context

[ADR 16](016.md)で、Issueの添付ファイルのメタデータを`IssueAggregate`に持たせた。添付ファイルの中身を取得して保持する場所は、画像表示を実装するときに決めるとした。次は、本文とJournalのnotesに埋め込まれた画像を、`ratatui-image`でterminal内に表示する。

画像の表示には、次の制約がある。

- terminalがKitty graphics protocolに対応するかを、確実に知る方法がない。`ratatui-image`の`Picker::from_query_stdio`は、環境変数とterminalへの問い合わせで推測する。しかし、環境変数は起動元のterminalから引き継がれ、実際のterminalと食い違うことがある（WezTermから起動したKittyでは、WezTermと判定されてKittyを使わない）。また、問い合わせに応答しないterminalでは、応答を待つスレッドが後から入力したキーを読み取ってしまう。
- 表示はKitty graphics protocolだけを対象にする。Sixelは行単位で切り取れないため、スクロール中に上下が欠けた画像を正しく描けない。Halfblocksは解像度が低く、背景色で描くためfocus表示とも両立しない。Webデモは対象外とする。
- 利用者が画像表示を無効にできる必要がある。表示できるterminalでも、通信量や描画の重さを避けたい場合がある。
- 画像を表示するには、ダウンロード、decode、縮小、Kitty protocolへのencodeが必要である。どれもUIスレッドで行うと操作が止まる。[docs/architecture.md](../architecture.md)は、Componentの`update`から要求を発行することを禁止しているため、`update`で画像が必要だと分かってもUsecaseを起動できない。

Redmine APIでは、画像の取得に次の経路がある。

| API                                      | 内容                                                                                                    |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `GET /attachments/download/:id`          | 原画像。サイズに上限はない                                                                              |
| `GET /attachments/thumbnail/:id(/:size)` | サムネイル。`size`は50px単位に切り上げられ、最大800pxになる。サーバーでImageMagickが使えない場合は`404` |

Issue詳細の`attachments`には、サムネイルを作れる添付ファイルにだけ`thumbnail_url`が入る。

Issueを取得するGETは、初回取得のほかに、Issue属性の保存前GETと確認GET、Journal保存後のGET、添付ファイル追加の確認GETがある。どのGETも、取得結果で`IssueAggregate`を置き換える。他の利用者が追加した添付ファイルは、どのGETで初めて現れるか分からない。

## Decision

### 設定ファイルを起動時に読み込む

native版は、起動時に`$XDG_CONFIG_HOME/redmine-tui/config.toml`を読み込む。`XDG_CONFIG_HOME`が未設定なら`~/.config`を使う。この規則はLinuxとmacOSで共通とする。

```toml
[image]
enable = true
```

ファイルがない場合や`[image]`がない場合は、画像表示を無効として扱う。ファイルはあるのに、TOMLとして読めない場合や値の型が違う場合は、Redmine接続設定の誤りと同じく、起動を中止してエラーを表示する。読み込み処理は`src/platform/`に置き、Webデモでは使わない。

### 画像表示の可否を設定Storeに置く

設定値をまとめる`SettingsStore`を`Store`に加える。画像表示の可否は、次の2値で持つ。

```rust
pub enum ImageDisplay {
    Disabled,
    Enabled { encoder: TerminalImageEncoder },
}
```

画像表示の可否は、設定ファイルの値だけで決める。terminalへは問い合わせず、環境変数も見ない。`enable = true`なら、Kitty graphics protocolに対応したterminalで動いているものとして`Enabled`にする。非対応のterminalで有効にした場合は、表示が崩れる。描画は失敗として検出できないため、利用者の設定に任せる。

画像のセル数を求めるには、フォントのピクセルサイズが必要である。起動処理は、`ratatui::init()`の後、runnerを始める前に、terminalのピクセル数とセル数（ioctlの`TIOCGWINSZ`）からフォントのピクセルサイズを求める。ピクセル数を得られないterminalでは`Disabled`にする。結果は初期Actionで`SettingsStore`に反映する。Webデモは常に`Disabled`とする。

`Picker`は、求めたフォントのピクセルサイズで作り、protocolをKittyに固定する。問い合わせをしないため、Kittyの圧縮（`o=z`）は使わず、画像を圧縮せずに送る。`Picker`は画像の前処理に必要なので、`Picker`を包んだ`TerminalImageEncoder`を`Enabled`の中にだけ持たせる。`Disabled`のときは、画像に関するUsecaseは起動時に何もせず終わる。

個々の画像の取得、decode、encodeに失敗したときは、その画像だけを代わりの文字で表示する。

`ratatui-image`は、依存する`rustix`がwasm32に対応しないため、Webデモではbuildできない。そこで、`ratatui-image`と`image`はnative版だけの依存とし、`src/stores/terminal_image.rs`の型で包む。native版の`TerminalImageEncoder`は`Picker`を、前処理の結果の`PreparedImage`はdecode済みの画像とKitty protocolを持つ。Webデモでは、どちらも値を作れない空のenumにする。cfgによる分岐はこのファイルに閉じ、Store、Usecase、Componentには書かない。

### 画像を取得元ごとのキーで持つ

表示する画像の状態を`ImageStore`で持つ。`ImageStore`は、画像の取得元を表す`ImageKey`ごとに状態を持ち、添付ファイルに固有の情報は持たない。同じ添付ファイルでも、サムネイルと原画像は別の画像として扱う。

```rust
pub enum ImageKey {
    AttachmentThumbnail { id: AttachmentId, size: u32 },
    AttachmentOriginal { id: AttachmentId },
}

pub enum ImageState {
    Loading,
    Preparing { path: PathBuf },
    Ready(PreparedImage),
    Failed { reason: String },
}
```

| 状態        | 処理                                                                               | 成功時                                                  | 失敗時         |
| ----------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------- | -------------- |
| `Loading`   | 画像を取得し、一時ディレクトリへ書き込む                                           | `Preparing`へ進み、ファイルのパスを載せた後続要求を返す | `Failed`にする |
| `Preparing` | 一時ファイルを読んでdecodeし、必要なら縮小して、表示用のKitty protocolへencodeする | `Ready`へ進み、前処理の結果を保持する                   | `Failed`にする |
| `Ready`     | なし                                                                               | -                                                       | -              |
| `Failed`    | なし                                                                               | -                                                       | -              |

状態がない画像と`Failed`の画像だけが、読み込みを始められる。`Ready`の画像は起動中ずっと残す。

添付ファイルの表示にどの`ImageKey`を使うかは、`IssueStore`が`AttachmentId`ごとに持つ。添付ファイルの追加状態と同じく、Issueのentryとは別のMapとし、Issueを取得し直しても引き継ぐ。対応と画像の状態を同時に変える更新は、2つのStoreをまたぐ`AttachmentImageAction`1件で行う。

| Action               | 更新                                                                         |
| -------------------- | ---------------------------------------------------------------------------- |
| `Start`              | 対応を登録し、その画像の読み込みを始める                                     |
| `FallBackToOriginal` | サムネイルを`Failed`にし、原画像の読み込みを始めて、対応を原画像へ切り替える |

各段階は別のUsecaseとし、`UsecaseRequest`のvariantを1つずつ割り当てる。前の段階の完了は、状態を進めるActionと、次の段階の`UsecaseRequest`を返す。[ADR 14](014.md)の「1リクエストの結果を1つのActionで反映し、完了Actionを適用してから後続へ進む」と、[ADR 15](015.md)の後続要求に従う。

| 要求                                                       | 処理                                                                            |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------- |
| `DownloadAttachmentImage { attachment_id, thumbnailable }` | 読み込みを始め、`thumbnailable`ならサムネイルを、そうでなければ原画像を取得する |
| `DownloadAttachmentOriginal { attachment_id }`             | サムネイルを取得できなかった添付ファイルの原画像を取得する                      |
| `PrepareImage { key, path }`                               | 一時ファイルの画像を前処理する。取得元を問わない                                |

`Ready`の`PreparedImage`には、表示に必要な前処理を済ませた値を持たせる。

- decode済みの画像
- その画像を元の解像度で表示する大きさでencodeしたKitty protocol

セル単位の大きさは、Kitty protocolから求める。

表示する幅がこの大きさより狭いときは、表示側で縮小してencodeし直し、元の画像と幅ごとに結果を保持する。性能に問題があれば、別の段階のUsecaseに切り出す。

### Issue詳細GETの完了でダウンロードを要求する

`IssueAggregate`を置き換えるGETの完了は、どれも画像の添付ファイルのダウンロードを後続要求として返す。画像かどうかは、`content_type`が`image/`で始まるかで判定する。ただし`image/svg+xml`は、`image` crateでdecodeできないため除く。対象は初回取得、Issue属性の保存前GETと確認GET、Journal保存後のGET、添付ファイル追加の確認GETである。保存前GETで競合を検出した場合、Journalの退避、確認GETに失敗して保存前GETの値で完了する場合も、`IssueAggregate`を置き換えるため対象に含める。後続要求の組み立ては、これらのUsecaseで共通の処理にする。

完了のFutureはStoreを参照できないため、後続要求は対象を絞らずに返す。ダウンロードのUsecaseは、起動時に`SettingsStore`と`ImageStore`を見て、次の場合だけ始める。

- `ImageDisplay`が`Enabled`である。
- その添付ファイルに対応する画像がないか、対応する画像が`Failed`である。

本文やnotesから参照されているかは判定しない。参照の解釈は表示側の責務であり、記法の違いもある。Issueに添付された画像はすべて取得する。

### サムネイルを優先し、取れなければ原画像を取得する

まず`GET /attachments/thumbnail/:id/:size`でサムネイルを取得する。`size`はUsecaseの定数とし、初期値はRedmineの上限の800pxとする。サムネイルのGETが失敗したら、`GET /attachments/download/:id`で原画像を取得する。`404`に限らず、どの失敗でも原画像の取得へ進む。サムネイルがない理由が、サーバーにImageMagickがないためか、生成に失敗したためかを、clientからは区別できないためである。`thumbnail_url`がない添付ファイルは、サムネイルを試さずに原画像の取得から始める。

原画像は大きさに上限がない。そこで、原画像の取得にはバイト数の上限を設け、上限を超えたら`Failed`にする。上限はUsecaseの定数とし、サムネイルは4 MiB、原画像と前処理で読むファイルは20 MiBとする。`Preparing`では、画像の長辺が800pxを超えていたら、800pxまで縮小してからencodeする。サムネイルの`size`もこの値に合わせる。これにより、`Ready`に置く画像の大きさは、どちらの経路でも同じ範囲に収まる。

URLは、`thumbnail_url`や`content_url`の値ではなく、HTTP実装が接続先と添付ファイルIDから組み立てる。これらのURLはRedmineのホスト名の設定に基づいており、proxyやcontainer越しの接続では、clientから届かないことがある。`Attachment`には、`thumbnail_url`があったかどうかを`thumbnailable: bool`として持たせる。

`RedmineClient`に、サムネイルのバイト列を取得するメソッドと、原画像のバイト列を取得するメソッドを加える。どちらも、応答が上限のバイト数を超える場合は、全体を読まずにエラーにする。

### 一時ファイルはLocalFileClientが管理する

`LocalFileClient`に、一時ディレクトリへバイト列を書き込み、書き込んだパスを返すメソッドを加える。native版の起動処理は、`std::env::temp_dir()`の下へ`redmine-tui-<プロセスID>-<UUID>`のディレクトリを権限`0700`で作り、終了時に削除する。他のユーザーが同じ名前を先に作っていても使わないよう、推測できない名前で新しく作る。ディレクトリは画像表示の可否にかかわらず作る。macOSの`$TMPDIR`も`temp_dir()`で解決する。

ファイル名は`ImageKey`から作り（`attachment-<ID>-thumbnail-<size>`、`attachment-<ID>-original`）、Redmine上のファイル名は使わない。ファイル名にパス区切りや`..`が含まれても、一時ディレクトリの外に書き込まないようにするためである。clientも、ディレクトリを含む名前を拒否する。

### 各段階でリトライしない

どの段階で失敗しても、その段階を再試行しない。サムネイルのGETの失敗だけは、原画像の取得という別の段階へ進む。それ以外の失敗では、状態を`Failed`にして失敗理由を残す。一時ファイルへの書き込みに失敗した場合は、原画像を取っても同じく失敗するため、サムネイルの段階でも`Failed`にする。表示に使う画像が`Failed`の添付ファイルは、次にIssue詳細GETが完了したときに、サムネイルの取得からやり直す。画像の取得や前処理の失敗は通知せず、表示側で代わりの表示にする。

## Rationale

画像表示の可否と`Picker`をStoreに置くと、Usecaseは起動時にStoreを見るだけで判定できる。起動処理から各Usecaseへ引数で配る必要がない。可否の判定は起動時の1か所で行うため、Usecaseと表示側で食い違わない。

可否を設定ファイルの値だけで決めるのは、terminalの判別に確実な方法がなく、推測のための例外処理が増えるためである。どのterminalで使うかは利用者が知っているため、設定で選んでもらう。

前処理の結果をStoreに置くのは、decodeとencodeをUIスレッドの外で済ませるためである。ADR 16はStoreを画面の状態だけに保つため、添付ファイルの中身を置かないとした。この判断は送信用のファイルを対象にしたもので、表示用の画像は画面に必要な状態そのものである。そのため、Issueの状態とは分けて`ImageStore`に置く。

`ImageStore`を取得元ごとのキーで持つのは、今後、本文のmermaidのコードブロックを画像にして表示するときにも、同じStoreと前処理を使うためである。添付ファイルとサムネイル・原画像の区別を`ImageStore`の状態に持たせると、添付ファイル以外の画像を足せない。取得元に固有の情報はキーと、対応を持つ側に置く。

`ratatui-image`の型を包むのは、Webデモでbuildできない依存とcfgの分岐を1つのファイルに閉じるためである。Storeは包んだ型を通して`ratatui-image`と`image`に依存する。Kitty protocolを外から組み立てる公開APIがないため、Storeを標準の型だけにするには、Kittyへの送信を自前で実装するか、encodeを表示側で行う必要がある。

ダウンロードと前処理を分けると、どちらで失敗したかがStoreの状態から分かる。前処理をやり直すときに、再びダウンロードせずに済む。一時ファイルを経由するのは、この2つの段階の間でバイト列をStoreやActionに載せないためである。

サムネイルを優先するのは、decodeとencodeの時間、メモリ、通信量を一定の範囲に収めるためである。原画像は数MBの写真を含み、前処理の時間が読めない。一方、サーバーにImageMagickがない環境では、サムネイルを一切取得できない。原画像へのフォールバックがあれば、そうした環境でも画像を表示できる。原画像の経路では、バイト数の上限で通信量を抑え、`Preparing`での縮小で画像の大きさをサムネイルと同じ範囲に収める。

サムネイルと原画像を別の画像として扱い、別のUsecaseで取得するのは、どちらのGETで失敗したかをStoreに残すためである。1つのUsecaseの中で続けて試すと、ADR 14の1リクエスト1状態に反する。

GETの完了ごとに対象を絞らずに要求すると、他の利用者が追加した添付ファイルも、どのGETで現れても取得できる。重複の判定はダウンロードの開始時に行うため、取得済みの画像を再び取得しない。

## Consequences

- `Cargo.toml`に`ratatui-image`、`image`、`toml`を追加する。いずれもnative版だけの依存とする。`ratatui-image`は`default-features = false`とし、`crossterm`と`image-defaults`だけを有効にする。`libchafa`には依存しない。LinuxとmacOSでは、`ratatui-image`がrustix経由でterminalを操作するため、FFIは不要である。
- `Store`に`SettingsStore`と`ImageStore`を加え、`Action`に`Settings`、`Image`、`AttachmentImage`のvariantを加える。`IssueStore`は、添付ファイルと`ImageKey`の対応を持つ。
- Storeは`terminal_image.rs`の包んだ型を通して、`ratatui-image`と`image`の型に依存する。
- `UsecaseRequest`に`DownloadAttachmentImage`、`DownloadAttachmentOriginal`、`PrepareImage`を加える。
- `RedmineClient`にサムネイルと原画像の取得メソッドを加えるため、HTTP実装、Demo client、テスト用のClientを更新する。両方の応答と、サムネイルを作れないときの応答を、Redmine clientテストで確認する。テスト用のRedmine containerでImageMagickが使えるかも確認する。
- ImageMagickのないサーバーでは`thumbnail_url`が返らないため、サムネイルのGETは行わない。`thumbnail_url`があるのにサムネイルの生成や通信に失敗した場合だけ、画像1件につきGETが1回増える。
- `LocalFileClient`に一時ファイルの書き込みを加えるため、native実装とdemo実装を更新する。demo実装は、画像表示が常に無効なので呼ばれない。
- `Attachment`に`thumbnailable`を加えるため、HTTP実装、Demo client、fixture変換、テストデータの組み立てを更新する。fixtureを変える場合は、seeder、SQL、整合性テストへの影響も確認する。
- Issue詳細GETを行うUsecaseはすべて、完了時にダウンロードの後続要求を返す。
- 起動処理は、Redmineの初期読み込みと`ratatui::init()`を済ませてから、terminalのピクセル数でフォントのピクセルサイズを求め、設定Storeを初期化する。
- Kitty graphics protocolに対応しないterminalで画像表示を有効にすると、表示が崩れる。READMEで、対応したterminalでだけ有効にするよう案内する。
- 画像を圧縮せずに送るため、送るデータは圧縮した場合より大きくなる。送るのは画像ごとに1回だけである。
- `ImageStore`の画像は、起動中は削除しない。多数の画像を持つIssueを多く開くと、メモリ使用量が増える。
- SVGの添付ファイルは画像として表示しない。
- 一時ディレクトリは、画像表示が無効でも起動のたびに作って削除する。
- `Failed`の理由には、Redmineが返したエラーページの本文がそのまま入ることがある。表示するときは短くする必要がある。
- 外部エディタから戻った後に、Kitty側に送信済みの画像が残っているかは確認していない。
- `docs/architecture.md`に、`SettingsStore`、`ImageStore`、一時ファイル、`terminal_image.rs`の扱いを追記する。
- スクロール中の画像の描画は、この決定の対象外とする。

## Alternatives Considered

- 画像表示の可否を、起動処理から`UsecaseClients`や各Componentへ引数で渡す: 表示側とUsecaseの両方へ配る経路が必要になるため採用しない。
- `Picker::from_query_stdio`でterminalへ問い合わせ、Kittyと判定したときだけ有効にする: 引き継いだ環境変数でKittyを誤って除外し、応答しないterminalではキー入力を奪われるため採用しない。
- `ImageDisplay`に`Picker`を直接持たせ、使う場所ごとにcfgで分岐する: Store、Usecase、Componentの各所にcfgが散らばるため採用しない。
- `ImageStore`を`AttachmentId`ごとに持ち、サムネイル取得中・原画像取得中を状態で区別する: 添付ファイル以外の取得元（mermaidのコードブロックなど）の画像を同じStoreで扱えないため採用しない。
- Storeを標準の型だけに依存させ、Kittyへの送信とplaceholderの描画を自前で実装する: Storeは`ratatui-image`から切り離せるが、Kitty protocolの実装とテストが必要になるため、今は採用しない。
- Storeを標準の型だけに依存させ、Kittyへのencodeを表示側で行う: UIスレッドでzlibとbase64の変換を行うことになり、`Picker`を表示側へ渡す経路も別に必要になるため採用しない。
- 前処理をComponentの`update`で行う: decodeとencodeでUIスレッドが止まるため採用しない。
- ダウンロードと前処理を1つのUsecaseで続けて行う: どこまで成功したかをStoreに残せず、ADR 14とADR 15の方針に反するため採用しない。
- 一時ファイルを使わず、ダウンロードしたバイト列をActionで運ぶ: 前処理をやり直すたびに再取得が必要になり、大きなバイト列がActionとStoreを経由するため採用しない。
- 本文やnotesから参照されている画像だけを取得する: Usecaseが表示側の記法を解釈することになるため採用しない。
- 原画像だけを取得する: 前処理の時間と通信量が、すべての画像で原画像の大きさに左右されるため採用しない。
- サムネイルだけを取得する: ImageMagickのないサーバーでは画像を一切表示できないため採用しない。
- サムネイルの`404`のときだけ原画像へ進む: 通信の失敗とサムネイルの生成失敗とで扱いが分かれ、生成失敗が`404`以外で返る場合に表示できないため採用しない。
- `thumbnail_url`の値をそのまま使う: proxyやcontainer越しの接続で、clientから届かないURLになることがあるため採用しない。
- Sixelにも対応する: スクロール中に上下が欠けた画像を描けないため採用しない。

## Future Work

- 表示する幅に合わせた縮小とencodeを、性能を測ったうえで別の段階のUsecaseに切り出すか決める。
- terminalへKittyの圧縮（`o=z`）に対応するかを問い合わせ、対応していれば圧縮して送るように切り替える。問い合わせは画像表示を有効にしたときだけ行い、応答しないterminalでキー入力を奪わない方法を取る。
- iTerm2のInline Images Protocolでも描けるようにする。WezTermやiTerm2で画像を表示できる。設定ファイルでprotocolを選べるようにし、スクロール中に上下が欠ける画像は、行ごとに分けた画像（`ratatui-image`の`SlicedProtocol::Sliced`）で描く。
- `ImageStore`から使わなくなった画像を削除する。
- 取得した画像をキャッシュする。今は一時ディレクトリに置いて終了時に削除するため、起動のたびに取得し直す。起動をまたいで再利用するキャッシュを設け、その動作をE2Eで確かめる。今のE2Eは、仮想端末がピクセル単位の大きさを返さず画像表示が無効になるため、画像の取得と一時ファイルを確かめていない。
- 外部エディタから戻った後のKitty画像の再送。
- 設定ファイルに画像表示以外の項目を加える。
- 本文のmermaidのコードブロックを画像にして、`ImageStore`で扱う。
- Storeを標準の型だけに依存させるかを、表示側の実装を踏まえて見直す。
