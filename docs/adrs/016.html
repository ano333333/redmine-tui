16. Issue添付ファイルの取得と追加

Status

Accepted

Context

Redmineでは、Issueにファイルを添付でき、本文やJournalのnotesに添付した画像を埋め込める。現在のTUIは添付ファイルを扱っていない。

  • Issue詳細GETはinclude=children,journalsだけを指定し、添付ファイルを取得していない。
  • IssueAggregateとentities/には、添付ファイルを表す型がない。
  • JournalDetailはAttrだけを持つ。propertyがattrでないJournal detailは、Clientが変換時に読み飛ばしている。添付ファイルの追加・削除の履歴は表示されない。
  • RedmineClientには、ファイルを送るメソッドがない。HTTP実装には、JSONのGETとPUTしかない。

Redmine APIでは、添付ファイルは次のように扱う。

API 用途 成功時の応答
GET /issues/:id.json?include=attachments 添付ファイル一覧の取得 IssueのattachmentsにID、ファイル名、サイズ、Content-Type、説明、content_url、作成者、作成日時が入る
POST /uploads.json ファイル本体の送信 201と{"upload": {"id", "token"}}
PUT /issues/:id.jsonのuploads tokenをIssueに紐付ける 204。本文はない

ファイルを添付するには、まずPOST /uploads.jsonで本体を送ってtokenを受け取る。次にPUT /issues/:id.jsonのuploadsにtokenを指定して、Issueに紐付ける。tokenは1回しか使えない。紐付けなかったuploadは、Redmineが後で削除する。

PUTの応答には本文がない。添付ファイルのcontent_urlや作成日時、追加で作られたJournalを知るには、Issueを取得し直す必要がある。追加で作られたJournalのdetailは、propertyがattachment、nameが添付ファイルID、new_valueがファイル名になる。

ADR 14は、1 APIリクエストの結果を1つのActionで反映し、各リクエストの完了Actionを適用してから後続のリクエストへ進むと定めた。ADR 15は、その手段としてUsecaseOutputの後続要求とrunnerのqueueを導入した。添付ファイルの追加は3つのリクエストを順に行うため、この仕組みを使う。

Decision

添付ファイルをIssueAggregateが所有する

添付ファイルを表すAttachment entityをsrc/entities/に置き、IssueAggregateに取得順のattachments: Vec<Attachment>を持たせる。集約ルートとStore境界は、Journalと同じくIssueAggregateとIssueStoreとする。添付ファイル用のStoreは作らない。

Attachmentは、IDのAttachmentId、ファイル名、サイズ、Content-Type、説明、content_url、作成者、作成日時を持つ。値の表現は既存のJournalやIssueAggregateに合わせ、詳細は実装時に決める。

添付ファイルは取得値だけを持ち、ローカル編集の差分は持たない。追加はサーバーへの送信が成功し、確認GETで取得し直したときにIssueAggregateへ現れる。

Issue詳細GETは常に添付ファイルを含める

get_issueは常にinclude=children,journals,attachmentsで取得する。初回取得、Issue保存前GET、確認GET、Journal保存後のGETのすべてが対象になる。

IssueStoreは、取得結果でIssueAggregateを置き換える。添付ファイルを含めないGETがあると、その取得で添付ファイル一覧が空になる。

Journal detailの添付ファイル履歴を変換する

JournalDetailに添付ファイルのvariantを追加する。Redmineは、追加を変更後だけに、削除を変更前だけにファイル名を持つdetailで表す。Clientは、propertyがattachmentのdetailを、添付ファイルIDと、追加か削除かとファイル名の組へ変換する。変更前と変更後の両方にファイル名があるか、どちらにもないdetailはエラーにする。cfとrelationは、今回も読み飛ばす。

添付ファイル追加を1リクエスト1状態で進める

添付ファイルの追加状態は、IssueStoreがIssueごとに、IssueEntryとは別のMapで持つ。Issue属性の状態が変わっても、追加状態はそのまま引き継がれる。取得済みのIssueは未取得の状態へ戻らないため、追加を始めるときにIssueが取得済みかを検査すれば、取得済みのIssueにだけ追加状態があることを保てる。

1つのIssueで同時に追加できる添付ファイルは1件とする。追加は次の3段階で進め、1つのリクエストに1つの状態を対応させる。

状態 リクエスト 成功時
Uploading POST /uploads.json Attachingへ進み、tokenを載せた後続要求でPUTを起動する
Attaching PUT /issues/:id.jsonのuploads Confirmingへ進み、後続要求で確認GETを起動する
Confirming GET /issues/:id.json 取得したIssueを取り込み、追加状態を削除する

各段階は別のUsecaseとし、UsecaseRequestのvariantを1つずつ割り当てる。前の段階の完了は、状態を進めるActionと、次の段階のUsecaseRequestを返す。tokenはStoreに置かず、ADR 15のPutIssueUploadと同じく要求に載せて運ぶ。

紐付けのPUTは、Issue属性の保存やJournalの投稿と同じPUT /issues/:id.jsonである。それでも、このPUTではuploadsだけを送り、Issue属性の差分やnotesを同じリクエストに含めない。ADR 14がnotesをIssue属性の保存と分けたのと同じく、Issue属性、Journal、添付ファイルは個別に保存する。

添付ファイルの追加は、3段階のすべてでIssueのupload排他の対象になる。Issue属性やJournalのupload中は追加を始めず、追加中はそれらのuploadを始めない。排他の検査はIssueStore内で行う。

各状態でリトライしない

どの段階で失敗しても、その段階を再試行しない。失敗したら追加状態を削除し、失敗を通知する。

失敗した段階 サーバーの状態 利用者の操作
Uploading 何も残らないか、未紐付けのuploadが残る ファイルの追加をやり直す
Attaching 未紐付けのuploadが残る ファイルの追加をやり直す
Confirming 添付ファイルはIssueに紐付いている 追加はやり直さない

Confirmingの失敗では、添付ファイルはすでにIssueに紐付いている。通知では、追加が成功して確認だけに失敗したことを伝え、二重に追加しないよう促す。添付ファイルは、Issue属性やJournalの保存などで次にIssueを取得し直したときに表示される。PUTの成功応答を受け取れずにAttachingで失敗した場合も、サーバーでは紐付いていることがある。利用者がやり直すと二重に添付されるが、これを許容する。

Storeには添付ファイルのメタデータだけを置く

Storeには添付ファイルの中身を置かず、メタデータだけを置く。取得した添付ファイルはAttachmentとしてメタデータだけを持ち、中身はダウンロードしない。添付ファイルの中身を取得して保持する場所は、画像表示やダウンロードを実装するときに決める。

追加するファイルも同じく扱う。Uploadingの状態には、表示に使うファイル名などだけを持たせる。ファイルの中身は、POST /uploads.jsonを行うUsecaseの非同期処理の中で読み込む。

ローカルファイルの読み込みはplatformごとに異なる。usecasesはplatformに依存できないため、RedmineClientと同じくsrc/clients/にLocalFileClient traitを置き、実装は起動処理が組み立てる。Usecaseは、RedmineとローカルファイルのclientをUsecaseClientsにまとめて受け取る。Webデモの実装は、どのパスにも埋め込みのサンプル画像を返す。

ファイルを選ぶUIは、ファイル名とファイルパスを入力するpopupとする。ファイルエクスプローラなどのGUIとの結合は今後の課題とする。

API固有の表現はRedmineClientで変換する

RedmineClientに、ファイル本体を送ってtokenを返すメソッドと、tokenをIssueに紐付けるメソッドを追加する。application/octet-streamでの送信やuploadsのJSON表現は、HTTP実装が担当する。UsecaseとStoreはtokenの中身を解釈せず、tokenを専用の型で包んで扱う。

Rationale

添付ファイルをIssueAggregateに持たせると、Issue詳細GETの1回の応答を1つのActionで反映するADR 14の方針を保てる。別のStoreに分けると、同じ応答の一部だけを反映した状態が生じる。

GETで常に添付ファイルを含めるのは、IssueStoreが取得結果でIssueAggregateを置き換えるためである。GETごとに含めるかを選ばせると、含めないGETの後に添付ファイルが消えて見える。

1リクエスト1状態にすると、どのリクエストまで成功したかがStoreの状態から分かる。Confirmingでの失敗をUploadingやAttachingでの失敗と区別でき、確認だけに失敗したときにPUTを繰り返さずに済む。

リトライをしないのは、失敗がまれで、やり直しの手間も小さいためである。UploadingとAttachingの失敗は、ファイルの追加をやり直せば回復できる。未紐付けのuploadはRedmineが削除する。Confirmingの失敗は、次にIssueを取得し直したときに回復する。段階ごとの再試行経路を設けると、状態とUsecaseが段階の数だけ増える。

同時に追加できる添付ファイルを1件に限り、Issueのupload排他に含めるのは、確認GETによるIssueAggregateの置き換えと、他のuploadの確認GETが重ならないようにするためである。

Storeにメタデータだけを置くのは、Storeを画面の状態だけに保ち、大きなファイルを状態遷移のたびに保持しないためである。

Consequences

  • IssueAggregateにattachmentsを追加するため、HTTP実装、Demo client、fixture変換、テストデータの組み立てを更新する。fixtureに添付ファイルを加える場合は、seeder、SQL、整合性テストへの影響も確認する。
  • get_issueのURLを変えるため、Redmine clientテストでattachmentsの取得を確認する。
  • JournalDetailのFIXMEのうち、添付ファイルの分を解消する。Journalの表示では、添付ファイルの履歴の表示を追加する。
  • IssueStoreに添付ファイルの追加状態のMapを加える。Issue属性とJournalのupload排他の検査に、添付ファイルの追加を加える。
  • start_usecaseとrunnerは、Redmineのclientに代えてUsecaseClientsを受け取る。
  • 取得済みのIssueを利用者が取り直す操作はないため、Confirmingで失敗すると、次の取得まで追加した添付ファイルが表示されない。
  • UsecaseRequestに3段階分のvariantを追加する。
  • RedmineClientにメソッドが増えるため、HTTP実装、Demo client、テスト用のClientを更新する。HTTP実装には、バイト列をPOSTしてJSONを受け取る処理を追加する。
  • POST /uploads.jsonの応答、PUTの204、紐付け後のJournal detailの形は、Redmine clientテストで確認する。
  • docs/architecture.mdに、LocalFileClientとUsecaseClients、upload排他の範囲の変更を追記する。

Alternatives Considered

  • 添付ファイル用のStoreを分ける: Issue詳細GETの応答を2つのStoreへ分けて反映することになり、ADR 14の反映単位に反するため採用しない。
  • 追加状態をIssueEntryのSynced・Edited・Uploadingに付加情報として持たせる: どのvariantも追加状態を持つことを型で表せるが、variantを作り直すすべての箇所で値を受け渡す必要があるため採用しない。
  • ファイルの読み込みをRedmineClientのuploadに含める: clientは増えないが、Redmineとの通信とローカルファイルの読み込みが1つのtraitに混ざるため採用しない。
  • 添付ファイルが必要な画面を開いたときだけinclude=attachmentsを付ける: 含めないGETで添付ファイル一覧が消えるため採用しない。
  • 3つのリクエストを1つのFutureで続けて実行する: どこまで成功したかをStoreに残せず、ADR 14とADR 15の方針に反するため採用しない。
  • 段階ごとに再試行を設ける: 失敗がまれで、やり直しで回復できるため採用しない。必要になったら、ConfirmingのGETだけを再試行する経路から追加する。
  • 添付ファイルの追加をIssue属性の保存フローに組み込み、保存PUTにuploadsを含める: Journalが1件にまとまり、ctrl+sで全てを保存できる。しかし、Issue属性の競合確認と添付ファイルの追加が1回の操作に結び付き、一方が失敗するともう一方も保存されない。属性を編集していないIssueでも、添付するだけでEditedになる。保存までファイルのパスをStoreに持ち続ける必要もあるため採用しない。
  • ファイルの中身をStoreに置く: Storeが大きなデータを持ち、状態遷移のたびに保持し続けるため採用しない。

Future Work

  • 添付ファイルの削除（DELETE /attachments/:id.json）とダウンロード（content_url）、ファイル名と説明の変更（PATCH /attachments/:id.json）。
  • 本文とJournalのnotesに埋め込まれた画像の表示と、未対応terminalやWebでの代替表示。
  • ファイルエクスプローラなどのGUIとの結合。Webでのファイル選択。
  • 取得済みのIssueを利用者が取り直す操作。
