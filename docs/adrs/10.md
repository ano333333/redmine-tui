# 10. GitHub Pages向けWASMデモとplatform境界

## Status

Proposed

## Context

`redmine-tui`を操作可能なサンプルとしてGitHub Pagesへ公開する。Web版は実Redmineへ接続せず、repositoryのfixtureを組み込んだデモとし、描画にはRatzillaの`DomBackend`を使用する。

GitHub Pagesは静的ファイルだけを配信するため、server process、PTY、filesystem、環境変数、子processを利用できない。現在のnative実装には次のplatform依存がある。

- Ratatui/crosstermによる描画と入力
- Tokio multi-thread runtimeと`Send + 'static`なworker task
- HTTPを行う`DefaultRedmineClient`
- `std::fs`で`datas/`を読むfixture loader
- 一時ファイルと外部processを使うeditor
- local fileへのlog出力とprocess環境変数

Store、Component、Widget、entity、value object、Redmine usecaseの状態遷移はnative/Webで共有する。platform差をComponentやStoreへ散在させず、アプリケーションの入口と外部副作用のadapterへ閉じ込める。

既存ADRとの関係は次のとおりである。

- ADR 1のComponent lifecycleとADR 6・7の非同期取得状態を維持する。
- ADR 3の「Dispatcher / Store / Componentはmain threadだけが更新する」という所有方針を維持する。
- ADR 3のTokio workerおよび同期editorに限定した実行方式を、本ADRのruntime/editor境界で置き換える。
- ADR 9のupload中編集を異常系とする判断を維持する。
- ADR 9のNoticeが壁時計の発生時刻を保持する契約だけを、本ADRの表示経過時間による契約で置き換える。履歴を保存するため既存ADR自体は更新しない。

## Decision

### 全体構成

共通アプリケーション層とplatform固有adapterを分離する。

```text
 InputEvent ──> Component ──effect──> App runner ──> platform ports
                    │                    │             ├─ Redmine
                    v                    │             ├─ Editor
                  Action                 │             ├─ Runtime
                    │                    │             └─ Logging
                    v                    │
              Dispatcher/Store <── completion

 native: crossterm / Tokio / HTTP / external editor / file log
 Web:    DomBackend / spawn_local / memory mock / textarea / console
```

共通層はcrossterm、Ratzilla、DOM、Tokio runtime、filesystem、process、HTTP実装へ直接依存しない。初期実装では単一Cargo packageと単一binaryを維持する。`lib.rs`は追加せず、`main.rs`から`cfg(target_arch)`でnative/Webのentry moduleへ分岐する。ComponentやStoreの大規模な再編は行わない。

### build targetと配信

nativeをdefault、Webを明示的なfeatureとtargetで選択する。

```toml
[features]
default = ["native"]
native = ["dep:crossterm", "ratatui/crossterm"]
web-demo = ["dep:ratzilla", "dep:wasm-bindgen", "dep:wasm-bindgen-futures"]
```

実際の依存解決に応じてtarget-specific dependenciesも使い、native専用依存をWASMへ入れない。nativeと`web-demo`の同時指定、または非WASM targetでの`web-demo`は`compile_error!`で拒否する。

Web成果物はTrunkでbinary crateをWASMとしてbuildし、repository名を含むGitHub Pagesのbase pathを設定する。GitHub Actionsが静的な`dist/`をPagesへdeployする。公開成果物へRedmine URLやAPI keyを埋め込まない。

### 描画backendとrunner

nativeはRatatui/crossterm backend、WebはRatzilla `DomBackend`を使う。WidgetはRatatuiの`Frame`、`Buffer`、`Rect`だけを利用し、backend型を知らない状態を維持する。

native/Webは一つの共通async runner loopを共有し、platform差はrunnerが呼ぶplatform interfaceへ閉じ込める。runner loopは1周ごとに次のapplication lifecycleを守る。

1. completion、tick、resize、入力を受理する。
2. completion Actionをdispatchする。
3. Actionを1件consumeするごとに、描画可能ならComponentをupdateする。
4. 入力を現在のinteraction modeに応じた宛先へ渡す。
5. effectを取り出してplatform portを起動する。
6. 描画可能ならrenderする。

物理的なcallback時刻ではなくrunnerの受理順をアプリケーション上の順序とする。Dispatcher、Store、ComponentはWebでもbrowser main threadだけが更新し、DOM callbackやtaskから直接変更しない。

platform interfaceは、timeout付きの入力待ち、描画、描画領域、単調時計、editor前後のterminal/DOM操作を提供する。nativeは入力待ちで`crossterm::event::poll`を同期に呼び、runner全体をTokio adapterの`block_on`で駆動する。これにより現在のpoll loopと同じ順序とtick間隔を維持する。Webはrunnerを`spawn_local`で起動する。Ratzillaのkey callbackはeventをqueueへ積むだけにし、入力待ちはqueueとtimerのうち早い方を待つ。描画はRatzillaのrender loop（`draw_web`）に委ねず、runnerが`Terminal::draw`を呼ぶ。runnerはawait点でだけbrowserへ制御を返し、browser event loopをblockしない。

editorのFutureはwakerを登録しない場合があるため、runnerはeditor中もtickごとにpollして完了を確認する。`std::time::Instant`は`wasm32-unknown-unknown`で使用できないため、経過時間はplatformの単調時計で計測する。

### InputEvent

Componentが直接受け取る`crossterm::event::Event`をアプリ固有の`InputEvent`へ置き換える。native adapterはcrossterm eventを、Web adapterはRatzilla eventを変換する。

```rust
pub enum InputEvent {
    Key(KeyEvent),
}

pub struct KeyEvent {
    pub code: KeyCode,
    pub modifiers: KeyModifiers,
}
```

初期型は現在Componentが解釈するkey入力を損失なく表す最小構成とする。Ratzillaの`keydown`をpressへ変換し、必要になればpress/repeat/releaseのkindを追加する。resize、tick、worker/editor completionはComponent入力ではないためrunner eventとする。mouseはComponentが必要とした時点で追加する。

変換不能なplatform固有keyは無視する。文字、矢印、Enter、Escape、Tab、Backspace、現在使用する修飾keyを変換testで固定する。

### interaction modeと入力元

editorの開閉と入力のpull/配送先をplatform interaction hostが一元管理する。

```rust
enum InteractionMode {
    Application,
    Editing(EditorSession),
}
```

- `Application`: terminalまたはRatzilla入力をComponentへ渡す。
- `Editing`: 入力をexternal editorまたはtextareaへ渡し、Componentへ渡さない。

編集中は保存、Issue切り替え、再取得、popup操作、別editor開始などのComponent入力を配送しない。二重editor開始はlifecycle違反として拒否する。

tick、worker completion、resizeの記録は編集中も受理する。ActionはStoreへ適用するが、Component更新と通常画面の描画はeditor終了まで遅延する。終了時に最新のStoreと描画領域から一度updateして再描画する。

### editorの共通契約

platform固有editorを、同一UI threadから開始して非同期に完了する非`Send`のportとして抽象化する。

```rust
pub struct EditorRequest { pub initial_text: String }

pub enum EditorOutcome {
    Submitted { edited_text: String },
    Cancelled,
}

pub trait TextEditor {
    fn edit(&mut self, request: EditorRequest)
        -> impl Future<Output = Result<EditorOutcome, EditorError>> + '_;
}
```

空文字列のSubmitは有効な編集でありCancelの代用にしない。外部失敗は`Err`とする。EditorはIssue/Journal IDを知らず、共通側がpending contextを保持する。完了時はすべての結果でcontextをtakeし、Submitだけが対応する編集Actionをdispatchする。Cancelはno-op、失敗はADR 9に従ってnoticeを追加する。

editor開始前にStoreを検査し、次の状態でだけ開始する。

- Issue description: `Synced`または`Edited`
- Remote Journal: `Synced`または`Edited`
- Local Journal: `LocalOnly`

現在、Issue descriptionとRemote Journalはupload中のeditor開始を完全には抑止していないため、WASM対応の準備として制御を追加する。Storeのpanicは防御的検査として維持する。Local Journal新規作成では`CreateLocal`をconsumeしてからeditorを開く。

### native editor

nativeは一時ファイルと`$VISUAL`、`$EDITOR`、`nvim`による現在の仕様を維持するが、子processの終了は非同期に待つ。`std::process::Command::status`によるmain thread停止は維持しない。

raw mode解除、alternate screen離脱、再入場、raw mode再有効化、clearはnative platform interfaceが管理する。editor中はcrossterm入力と描画を止め、editor completionとworker completionを待つ。全終了経路でterminalと一時ファイルをcleanupするguardを使う。正常終了は`Submitted`、起動失敗または非zero終了は`Err`とする。

### Web textareaとRatzilla focus

Webは`textarea`を含むmodalをRatzilla gridの外側へ追加する。初期値を設定してtextareaへDOM focusを移し、Submit/Cancel callbackでFutureを完了させる。IME composition中のEnter/Escapeを誤認せず、完了後はDOM node、listener、Rust closureを解放する。

Ratzilla cursor、Componentの論理focus、browserのDOM focusは別に扱う。`DomBackend::on_key_event`はgridへ`tabindex="0"`とkey listenerを設定する。textareaがfocusを持つ間はRatzilla入力をComponentへ配送せず、editorが消費するeventの伝播も停止する。

終了時はmodalを破棄し、現在のgrid要素をDOMから取得し直して`focus()`する。その後、論理focusを変更せず最新サイズでupdate/renderする。`DomBackend`はresize後のdrawでgridを再構築し得るため、開始時のElement参照を再利用しない。

reload、tab close、navigationでは、未確定textareaを含むmemory上の編集をすべて破棄する。`beforeunload`警告、永続化、復元は行わない。editor session IDは初期実装へ入れず、遅延callbackが実際に問題になれば追加する。

### 非同期task実行境界

共通runnerは次を区別する。

- background task: Redmine I/Oまたはmock server処理。完了Actionをrunnerへ返す。
- local UI task: editorやDOM interaction。同一UI threadで完了し、`Send`を要求しない。

nativeはTokio、Webは`wasm_bindgen_futures::spawn_local`を使う。runtime handle、sender、executor固有型をComponent、Store、Clientへ渡さない。

Redmine usecaseのFutureは現在の`Send + 'static`を維持し、Clientも`Send + Sync`を要求する。Webの`spawn_local`は`Send`なFutureも起動でき、`DemoRedmineClient`はDOMへ触れないインメモリserver mockなので、この境界を弱める理由はない。Web clientの共有状態には`Arc`と短時間だけ保持する同期primitiveを使い、lockを`.await`越しに保持しない。現在の`RedmineClient`には返却Futureの`Send`を明示しない`async fn`形式のmethodもあるため、全methodを`fn -> impl Future<Output = ...> + Send`形式へ揃え、Clientの契約として明示する。

taskのspawn自体はusecaseではなく`main.rs`の`spawn_action_task`がTokio `Runtime::spawn`で行う。この起動部分をruntime portへ置き換え、nativeはTokio、Webは`spawn_local`へ同じ`Send + 'static`なbackground Futureを渡す。completionをrunnerへ返すchannelまたはlocal queueはplatform adapterが選ぶ。

`load_initial_entities`がusecase内で使用する`tokio::join!`はTokio固有なので、executorに依存しない`futures::join!`へ置き換える。これはtaskをspawnせず、同一task内で複数のClient Futureを並行pollする。

usecaseは開始Actionを同期dispatchした後、Dispatcher/StoreをFutureへ捕捉せず、owned inputとClientだけを渡す原則を維持する。Futureの完了だけをrunnerがmain threadでdispatchする。共通契約は「taskがStoreを直接変更しない」「runner受理順でAction化する」「UI taskをlocal実行できること」とし、同じexecutor型やthread数は要求しない。

### editor中のbackground completion

editor中もbackground完了ActionをStoreへ適用する。開始条件とComponent入力停止により、編集中の対象へ新しいuploadを開始する経路はない。同一対象のeditor結果とupload completionは競合しない。

安全に完了し得るのは別Issueのfetch、Issue選択用page fetch、別対象ですでに開始済みのuploadなどである。対象がupload中ならeditorを開始しない。

### Noticeと経過時間

Noticeの表示時間はeditor中に消費しない。現在の`created_at + 5秒 > now`では、editor中に発生したnoticeが一度も描画されず消える可能性がある。

Storeの時間更新を現在時刻ではなく表示経過時間で受け取る契約へ変更する。Noticeは残り表示時間を保持し、通常画面の表示中だけ減算する。editor中にActionを適用しても表示経過時間には`Duration::ZERO`を渡す。実時間の計測にはplatformの単調時計を使う。

これはADR 9の「Noticeが発生時刻を保持し、`Store::update(now)`へ現在時刻を渡す」という決定だけを置き換える。エラー分類、notice表示、決定的なStore testという目的は維持する。

### DemoRedmineClientとfixture

Webは実HTTPを行わない`DemoRedmineClient`を使い、master、Issue、Journal、project別Issue一覧を`include_str!`でWASMへ組み込む。

filesystem読込とYAML文字列のparseを分離する。native fixture loaderはfile内容を、Web clientはembedded文字列を同じparserへ渡し、fixtureを複製しない。

`DemoRedmineClient`はmemory内にserver側状態を持つ。

- get系methodはmemory snapshotを返す。
- Issue/Journal updateはmemory上のserver stateへ反映する。
- 更新後の再取得では反映済み値を返す。
- network、認証、CORS、API keyを使わない。
- reloadで初期fixtureへ戻る。

既存Redmine usecaseを通し、fetch/upload/conflict処理を操作可能にする。実通信を模した意図的な遅延は追加せず、memory上の処理を直ちに完了させる。fixture変更時は`datas/`、`docker/redmine/seed_test_data.rb`、`tests/redmine_seeder_files_test.sh`の整合性を確認する。

### loggingとpanic

nativeはfile tracingを維持する。Webはfilesystemへ書かず、`tracing` eventをlevelに応じてbrowser consoleへ出す。Web panicもmessageとstackをconsoleへ残す。nativeのpanic時terminal復帰は維持する。

Webのlog初期化失敗だけでデモを起動不能にしない。listener登録や`DomBackend`生成など必須処理の失敗は画面またはconsoleへ報告して停止する。

### 実装順

1. `InputEvent`と変換testを追加し、Componentからcrossterm型を除く。
2. editor/interaction host、開始可能状態、入力切替、cleanup、Notice経過時間をnativeへ適用する。
3. background/local taskのruntime境界を抽象化し、Tokioを適合させる。初期取得の`tokio::join!`を`futures::join!`へ置き換える。
4. Cargo feature、Web entry point、Trunk、`DomBackend`を設定する。
5. embedded fixture parserと`DemoRedmineClient`を実装する。
6. textarea、focus復帰、console loggingを実装する。
7. native test、WASM build、fixture整合性testを実行し、Pagesへdeployする。

各段階でnative版をbuild/test可能に保つ。UI変更時だけsnapshotを確認し、意図した差分に限って更新する。

## Rationale

RatzillaはRatatui bufferをbrowserへ直接描画できるため、Widgetを再利用しながらcrossterm非対応を回避できる。platform差を入力、runner、Client、editor、runtime、loggingへ限定すると、Storeの状態機械とComponent lifecycleを共有できる。

textareaをFutureとして待てばbrowser event loopを止めず、native editorも同じ開始・完了契約にできる。物理的な待機方法ではなくinteraction modeとAction適用順を共通化する。

embedded fixtureとmemory server mockによりcredential、CORS、Pages上のserverが不要になる。同じusecaseを通すため、静的画面ではなく編集・保存を含む操作サンプルになる。

## Consequences

- Componentはcrosstermではなく`InputEvent`へ依存する。
- `main.rs`のloopを共通runnerへ移し、platform処理をnative/Webのplatform interfaceとportへ分離する。
- `RedmineClient`とusecaseの`Send + Sync`契約は維持し、Webのbackground Futureも同じ契約で起動する。
- editor中もStoreはcompletionを受理するが、Component更新と描画は終了まで遅延する。
- Noticeは通常画面の表示経過時間で期限切れになる。
- native editorは子processを非同期に待つ。
- Web編集は永続化されずpage離脱ですべて失われる。
- Web bundle内のfixtureは公開情報として扱う。
- native/Web双方のbuild検証がCIに必要になる。
- 実装完了時に`docs/architecture.md`を更新する。

## Alternatives Considered

### xterm.jsとANSI出力

ANSI、入力、resize、日本語幅、IME、mouseのbridgeが必要になる。操作サンプルにはRatzillaの方が単純なため採用しない。

### native/Webでrunner loopを分離する

nativeのpoll loopとWebのcallback/render loopを別々に実装すると、lifecycleの順序を二重に実装することになり、両者の差異をtestで検出しにくい。共通async loopにしても、nativeは同期pollのまま同じ順序とtick間隔を維持でき、Webはawait点でbrowserへ制御を返せる。そのため一つのloopを共有する。

### `lib.rs`を導入する

Trunkはbinary crateをbuildできるため、cdylibと`#[wasm_bindgen(start)]`は必要ない。lib化すると、dev-dependencyに依存するtest支援codeをbinary testから参照できなくなり、公開項目がdead_code検出の対象外になる。そのため採用しない。

### platform event型を共通型として使用する

一方の型へ他方を擬装するかComponentへ条件コンパイルが広がるため、独自`InputEvent`を使う。

### browserから実Redmineへ接続する

CORS、mixed content、credential露出、接続先依存が生じるため採用しない。

### fixtureをfetchする

追加の非同期初期化と配信path管理が必要になる。初期デモでは`include_str!`を使う。

### Web editorをRatatui componentにする

IME、選択、clipboard、accessibilityを再実装するため、標準textareaを使う。

### textarea完了を同期blockする

browser event loopが止まりSubmit/Cancelを処理できないため、Futureで待つ。

### editor中のcompletionを保留する

同一対象の競合は開始条件で排除でき、他対象まで保留する理由がないため採用しない。

### Webのすべてのtaskへ`Send`を要求する

Redmine background Futureは`Send`を維持するが、editorなどDOMを保持するlocal UI Futureは`Send`ではない。両者を一つのspawn契約へ統合しない。

### page離脱時に永続化する

fixture-onlyデモでは不要なため、初期状態へ戻す。
