4. Redmine テストデータ初期化と YAML seed 方針

Status

Accepted

Context

redmine-tui は現在、datas/ の YAML fixture を読み込むローカルプロトタイプとして実装されている。 一方、コンテナ上の Redmine に投入するテストデータは docker/redmine/seed_test_data.rb に固定値として書かれており、datas/ の内容とは対応していない。

この状態では、TUI が表示・編集対象としている fixture と、ローカル Redmine で確認できる issue、journal、project、user などがずれる。 今後 Redmine 接続を進めるには、datas/ を Redmine 側でも使えるようにし、少なくとも現在 datas/ に用意している範囲のデータを Redmine DB へ投入できる必要がある。

また、ローカル検証では「まっさらの Redmine DB に fixture を投入する」操作を繰り返す。 Redmine の schema は Redmine 本体の Rails migration により作成されるため、リポジトリ側で Redmine 全 schema を再定義する SQL を持つと Redmine version への追従コストが高い。 必要なのは schema 定義ではなく、テストデータ投入前に対象データを空にする SQL である。

Decision

Redmine テストデータ投入は以下の2つに分ける。

  1. まっさらのテストデータ状態を用意する SQL ファイルを追加する。
  2. datas/ の YAML から Redmine DB へ seed する Rust スクリプトを追加する。

SQL ファイルは Redmine schema を作成しない。 Redmine コンテナ起動後、Redmine 本体の Rails migration が schema を作った DB に対して、seed 対象テーブルのデータを削除し、auto increment を戻すために使う。

YAML seed は Rust の xtask crate として実装し、実行形式は以下にする。

cargo xtask seed-redmine

cargo xtask は .cargo/config.toml の Cargo alias で実現する。 xtask は workspace member として追加し、seed-redmine サブコマンドを持つ。

xtask は TUI 本体 crate の entities、libs、vos を公開させて再利用しない。 理由は以下である。

  • datas/ の YAML 読み込みは Redmine 接続までの暫定機能であり、将来アプリ本体からは削除される見込みである。
  • seed では SQL insert/update を構成できればよく、TUI の domain entity struct を構成する必要はない。
  • Redmine DB への投入都合と TUI 表示用 entity の境界を混ぜない方が、将来の削除や置き換えが容易である。

そのため、YAML parsing helper と seed 用のデータ構造は xtask 内に閉じる。 一時的に src/libs/yaml.rs と似た処理が重複することは許容する。

Redmine DB 上の issues.id は datas/issues/*.yml の id と一致させる。 既存 DB に同じ ID の issue が存在する場合は、その issue を seed 対象として更新する。 親子関係は child_ids から逆算し、子 issue 側の parent_id を設定する。 一方で、Redmine の既定 admin / anonymous user を壊さないため、datas/users.yml の user ID は 1000 番台から始める。 Issue、journal からの user 参照はこの 1000 番台の ID を使う。

現在 datas/ にある以下の YAML を seed 対象とする。

  • projects.yml
  • users.yml
  • trackers.yml
  • issue_statuses.yml
  • priorities.yml
  • target_versions.yml
  • categories.yml
  • time_entity_activities.yml
  • issues/*.yml
  • journals/*.yml

Redmine 側で必須だが datas/ に存在しない値は、seed 側で決定的に補完する。 たとえば user の login と mail、project identifier、version status、journalized type などである。

Rationale

datas/ を source of truth にすると、TUI の fixture と Redmine 上の確認データが一致する。 これにより、Redmine 接続後の表示差分や保存処理を検証しやすくなる。

Ruby の Rails runner で seed し続ける案もあるが、現在のプロジェクトは Rust 製 TUI であり、開発者が cargo で操作できる形の方が既存の開発体験に合う。 cargo xtask はアプリ本体とは別の開発補助コマンドを置くための一般的な構成であり、DB seed、fixture 検証、将来の Redmine reset などを増やしやすい。

TUI 本体 crate を library 化して entity を公開する案は採用しない。 seed の目的は Redmine DB に現在の YAML の値を入れることであり、TUI 内部 entity を構成することではない。 また、YAML fixture 読み込み自体が暫定であるため、そのためにアプリ公開 API を増やすと後で削除しづらくなる。

Redmine 全 schema を SQL ファイルとして管理しないのは、Redmine version 依存を避けるためである。 Redmine の schema は Redmine 自身が管理すべきであり、このリポジトリではテストデータの初期化と投入だけを扱う。

Consequences

xtask crate には YAML parser crate が追加される。 DB への投入は、生成した SQL を Docker Compose の MySQL service 内の mysql command に渡して実行する。 TUI 本体の dependency には seed 専用 dependency を追加しない。

docker/redmine/seed_test_data.rb は今後の主経路ではなくなる。 既存スクリプトやドキュメントは、cargo xtask seed-redmine を使う手順へ更新する。

seed は Redmine DB schema の存在を前提にする。 そのため、Redmine コンテナ起動直後で Rails migration が完了していない状態では失敗する可能性がある。 必要に応じてコマンド実行前に Redmine の起動完了を待つ運用とする。

YAML から Redmine DB へ直接 insert/update するため、Redmine model validation や callback は通らない。 これはローカル fixture 投入用途では許容する。 ただし Redmine の必須カラム、参照整合性、journal 表示に必要な最小カラムは seed 側で明示的に埋める。

datas/ に存在しない Redmine 機能、たとえば custom field、attachment、workflow permission、watcher は初期実装の対象外とする。
