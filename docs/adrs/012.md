# 12. Storeのstrict getterと任意取得の分離

## Status

Accepted

## Context

[ADR 9](009.md)は、存在を前提にする単体getterの不在を自プロセスの契約違反としてpanicで拒否する。一方、get_issueは未取得・取得中・取得失敗を扱うためOptionを維持していた。[ADR 11](011.md)ではIssueStoreを単一MapとIssueEntryに統合し、このgetter契約を維持した。

IssueEntryのFetching / FetchFailedは本体を持たず、Synced / Edited / Uploadingは必ず本体を持つ。しかし公開IssueStateは5状態すべてを含み、get_issueの返り値にも実際には返らないFetching / FetchFailedを型として許している。また、詳細Componentなど本体の存在が前提の箇所にもOptionの処理が繰り返される。

本体の存在を要求する取得と、不在を正常な結果として扱う問い合わせを分離する。JournalStoreにも同じgetter方針を適用する。本ADRはADR 9およびADR 11のIssue getter契約を更新し、エラー分類と内部entry表現は維持する。

## Decision

### Optionを返すgetterはtry\_接頭辞を付ける

Optionを返す取得メソッドはtry*get_xxxとする。存在を前提とするget_xxxは値または参照を直接返し、前提違反はpanicする。try*は通信の試行ではなく、取得対象がない場合をOptionで表すことを意味する。

今回の変更対象はIssueStore、JournalStore、およびそれらを公開する親Storeのgetterと呼び出し側とする。他のStoreやマスターデータのgetterへの命名適用は別途行い、不在時の意味を変えない。boolを返すhas_xxx、sliceやiteratorを返すcollection getterはこの改名の対象外とする。

### Issueの取得済み状態と読み込み状態を分ける

公開型とgetterの契約を以下とする。引数型のimpl Into<IssueId>など既存の利便性は維持してよい。

```rust
enum IssueState {
    Synced,
    Edited,
    Uploading,
}

enum IssueFetchState {
    Fetching,
    FetchFailed { message: String },
}

fn get_issue(&self, id: IssueId) -> (&IssueAggregate, IssueState);
fn try_get_issue_state(&self, id: IssueId) -> Option<IssueState>;
fn try_get_issue_fetch_state(&self, id: IssueId) -> Option<IssueFetchState>;
```

get_issueは取得済み本体を要求する。未登録・Fetching・FetchFailedではpanicし、成功時には本体と取得済み状態を返す。公開IssueStateからFetching / FetchFailedを削除することで、返らない状態を型でも排除する。

状態getterはどちらもOptionを返し、問い合わせ先に該当状態がないことを正常に扱う。旧get_issue_stateは削除する。

| 内部状態    | try_get_issue_state | try_get_issue_fetch_state | get_issue       |
| ----------- | ------------------- | ------------------------- | --------------- |
| 未登録      | None                | None                      | panic           |
| Fetching    | None                | Some(Fetching)            | panic           |
| FetchFailed | None                | Some(FetchFailed)         | panic           |
| Synced      | Some(Synced)        | None                      | 本体とSynced    |
| Edited      | Some(Edited)        | None                      | 本体とEdited    |
| Uploading   | Some(Uploading)     | None                      | 本体とUploading |

try_get_issue_state(id).is_some()を取得済み本体の存在確認として使用する。try_get_issue_fetch_stateのNoneだけで未登録と判定してはならない。両方がNoneの場合が未登録である。

IssueEntryは非公開のままとし、getter用の状態はentryから導出する。公開用の状態キャッシュや別Mapは追加しない。FetchFailedのmessageは従来と同様に必要時にcloneする。

### 呼び出し側を用途に応じて移行する

- 外側のIssueComponentは取得済み状態を確認してdetailを生成・更新する。それ以外では読み込み状態を調べ、取得中・失敗・未登録を扱う。再試行キーの判定はtry_get_issue_fetch_stateへ移す。
- fetch_issueは未登録またはFetchFailedの場合だけ取得を開始する。try_get_issue_stateがNoneで、かつtry_get_issue_fetch_stateがNoneまたはFetchFailedであることを確認する。取得済みIssueやFetchingへの重複取得を許可しない。
- IssueDetailComponentなど本体の存在を不変条件とする経路はget_issueを直接使う。不在を一律に事前検査して処理をスキップする形にはしない。
- 子Issue一覧やIssue選択popupのfallbackなど、不在が正常な経路ではtry_get_issue_stateで取得済みか確認してからget_issueを使う。今回try_get_issueは追加しない。
- 親StoreおよびJournal upload usecaseのIssue upload排他判定はtry_get_issue_stateを使う。従来はIssue本体の存在を要求していないため、strict getterに置き換えて事前条件を強めない。
- 詳細ヘッダーなどのIssueStateのmatchから、到達不能だったFetching / FetchFailedの分岐を削除する。

Issueの付随情報getterも以下へ改名する。返り値と不在時の挙動は維持する。

- get_issue_upload_conflict → try_get_issue_upload_conflict
- get_issue_upload_failure → try_get_issue_upload_failure

get_issuesは取得済み本体のiterator、get_issue_property_diffsは該当差分がなければ空sliceを返す契約を維持する。

### JournalStoreにもstrict getterと任意取得を適用する

| メソッド                                   | 方針                                                         |
| ------------------------------------------ | ------------------------------------------------------------ |
| get_remote_journal                         | 参照を直接返し、不在はpanicする既存契約を維持                |
| get_local_journal                          | 参照を直接返し、不在はpanicするstrict getterにする           |
| try_get_local_journal                      | 現行get_local_journalのOption返却を引き継ぐ                  |
| try_get_remote_journal_upload_conflict     | 現行get_remote_journal_upload_conflictを改名し、Optionを維持 |
| get_remote_journals                        | 未登録なら空sliceを返す既存契約を維持                        |
| has_remote_journal / has_uploading_journal | boolを返す既存契約を維持                                     |

Local Journalは0件または1件である。任意の一覧表示はtry_get_local_journalを使い、存在が事前条件であるupload開始などはget_local_journalを使う。

RemoteJournalEntry / LocalJournalEntryは全状態で本体を持ち、取得中・取得失敗を表すvariantを持たない。Journalの状態型の分割やentryの返却形式変更は行わない。親Storeの公開getterも同じ名前と契約に揃える。

### 内部の遷移検査はIssueEntryで行う

現行のderived_state / entry_stateは取得前と取得済みの全状態を公開IssueStateへ変換し、Actionの事前条件検査にも使っている。公開型の分割に合わせ、内部の遷移検査はIssueEntryを直接matchする形へ移す。

特にtry_get_issue_stateのNoneを未登録と同一視してはならない。Syncは未登録・Edited・Uploadingのみを許可し、StartFetchingは未登録・FetchFailedのみ、取得完了ActionはFetchingのみを許可する既存契約を維持する。

getterによる本体の存在保証は、編集やuploadなどの操作を許可する保証ではない。Action受理時の状態検査、ID整合性、Journalとのupload排他、非同期完了の検査は維持する。

## Error Handling

ADR 9のエラー分類を維持する。strict getterを本体のない状態で呼ぶことは自プロセスの契約違反としてpanicする。panicには対象IDと、操作や現在状態が分かる診断を含める。呼び出し位置の診断には必要に応じてtrack_callerを用いる。

未登録、取得中、取得失敗を問い合わせること自体は正常であり、try_get_xxxで扱う。通信失敗は従来どおり失敗Action・状態復帰・ユーザー通知で扱い、getter変更によってpanicへ変更しない。

## Rationale

取得済み本体を使う処理からOptionの処理と不可能な状態分岐を取り除ける。不在を許す問い合わせはtry\_で明示され、存在前提の処理で不整合を黙ってスキップしにくくなる。

取得前と取得済みの状態を分けるため、読み込み制御では2種類の問い合わせが必要になる。一方、状態を横断する主な呼び出し側はIssueComponentとfetch_issueに限られ、その他の状態参照は取得済み状態だけで足りる。

## Consequences

- ADR 9およびADR 11の既存文書は書き換えず、本ADRをgetter契約の更新として参照する。実装時にdocs/architecture.mdのgetter契約とコード例を更新する。
- strict getterの前提は呼び出し側が守る。状態確認後にStoreの更新を挟まず取得し、確認と取得の間で状態が変わる使い方を避ける。
- 任意取得では確認と取得の二重検索が発生し得る。現時点では契約の明確さを優先する。

## Alternatives Considered

- IssueStateの5variantを維持し、get_issue専用の部分型を追加する: 取得済み状態の定義が重複するため採用しない。
- get_issueからIssueEntryの参照を返す: 取得中も返せるが、本体の存在保証にならず、内部のdiff・失敗・競合の表現へ呼び出し側が依存するため採用しない。
- get_issueのOptionを維持する: 存在前提の処理にもOption処理が残り、今回の目的を満たさない。
- すべての単体getterを非Option化する: Local Journalの0件や競合の不在など、正常な任意取得があるため採用しない。
