ADR 9 Architecture

11. IssueStoreのentry統合とStoreの状態検査の整理

Accepted

Context

IssueStoreはIssue本体、取得・保存状態、編集差分、upload競合、upload失敗を5つのHashMapに分けて保持する。各Actionが複数のMapを更新し、本体と状態の欠損や不要な付随情報の残存を実行時に防いでいる。

JournalStoreはすでにRemoteJournalEntry / LocalJournalEntryとデータを持つ状態enumを使う。一方、Action処理に存在確認・状態確認の重複がある。

ADR 9の不正Actionをpanicで拒否する方針を維持しながら、型によって内部不整合を表現できなくし、重複した検査を減らす。ADR 10は並行作業中であり、本ADRではその内容を仮定しない。

Decision

IssueStoreを単一のMapへ統合する

最終的な内部表現は以下を基本とする。型とフィールドはIssueStore内部に閉じ、公開getterから読み取り結果を返す。

struct IssueStore {
    entries: HashMap<IssueId, IssueEntry>,
}

enum IssueEntry {
    Fetching,
    FetchFailed { message: String },
    Synced {
        issue: IssueAggregate,
    },
    Edited {
        issue: IssueAggregate,
        diffs: Vec<IssuePropertyDiff>,
        failure: Option<String>,
    },
    Uploading {
        issue: IssueAggregate,
        diffs: Vec<IssuePropertyDiff>,
        conflict: Option<IssueUploadConflict>,
    },
}

struct IssueUploadConflict {
    server_issue: IssueAggregate,
    conflicts: Vec<IssuePropertyDiff>,
}

未登録はMapの不在で表す。Fetching / FetchFailedは本体を持たず、Synced / Edited / Uploadingは必ず本体を持つ。Syncedは差分・失敗・競合を持たず、失敗はEdited、競合はUploadingだけが保持する。状態を別フィールドにも保存する二重管理は行わない。空diffを禁止する型や、競合待ちの新variantは今回導入しない。

getterの意味は維持する。get_issueは本体がなければNone、diffは対象状態でなければ空slice、競合・upload失敗はなければNoneを返す。get_issuesは取得済み本体だけを列挙するiteratorへ変更する。公開IssueStateは内部状態から導出する表示・判定用の値として残し、get_issueとget_issue_stateは状態を値で返す。FetchFailedのmessageは必要時にcloneする。参照APIを保つための状態キャッシュは追加しない。

privateメソッドで重複を減らす

Issueの各Update Actionは本体変更とdiff追加を一緒に扱うprivate編集処理を利用する。存在と編集可能性を確認した後に同じIDを引き直してexpectする形を避ける。Synced / Edited variantを直接matchしてよい。

JournalStoreも既存enumを維持し、存在取得、upload排他、状態別処理の重複をprivateメソッドや借用範囲の整理で減らす。異常時の対象IDと操作が分かる診断を保つ。panicの行数を減らすために全Actionの状態検査を巨大な汎用フレームワークへ集めない。

状態別structの所有権を消費する遷移メソッドは必須としない。Map統合後、再利用や複雑さに具体的な問題が残った場合に再検討する。Synced / Edited / Uploading variantに本体を持たせ、取得済み状態と本体の存在を型で結び付ける。

Action契約と既存の振る舞い

  • dispatchとconsumeの分離、ActionごとのComponent updateを維持する。
  • 遷移元違反、未登録対象への不正Action、ID不一致、Journal所有関係・重複、upload排他違反の検査は残す。
  • 検査を削除できるのは新しい型で不正状態を構築できなくなった場合。Result、無言のno-op、debug_assertへの置換で削減しない。
  • IssueのSyncは未登録・Edited・Uploadingで受理する。Fetching・FetchFailed・Syncedでは拒否する。
  • IssueのLoadは未登録のみ登録し、登録済みなら変更しない。
  • Issueの再編集は現在のupload失敗情報を保持する。Journalの再編集は失敗情報を破棄する。両者の既存挙動を今回統一しない。
  • diffの順序、before/after、競合キャンセル・失敗・再試行のデータ保持規則を維持する。
  • Journalのdirty保護、取得順、Local upload完了時のmergeとLocal削除の不可分性を維持する。

テストを振る舞いに集中させる

合法な状態に不正なActionを適用するpanicテストは残す。テストが内部entryを直接構築していても、それだけでは削除理由にならない。

旧Mapを直接壊して「本体だけ存在する」等を作るテストは、新しい型で構築不能になった変更と同時に削除する。型が保証することを実行時に再検証するための裏口やunsafeを作らない。値をstruct / enumに入れ、そのまま取り出すだけのテストも削除する。

正常遷移で本体・差分・失敗・競合がどう変わるかは引き続き検証する。型が付随情報の存在範囲を保証しても、正しい遷移先やデータを選んだことは型だけでは保証できない。

Error Handling

ADR 9を継続する。非同期完了の現在状態は受理時に検査する。Map統合は非同期の時間的整合性を保証しない。型で消えた内部不整合の検査だけを削除し、不正Actionに対する診断を維持する。

Rationale

単一Mapとデータを持つenumにより、複数Mapの更新漏れと不正な状態の組み合わせを防げる。保存状態をIssueEntryのvariantに直接表すため状態判定は一段で済む。本体を参照するgetterと遷移では3つの取得済みvariantを扱う。

状態別structだけを追加してもAction受理時のmatchは残る。Map内の値に所有権を消費するメソッドを適用するには取り出し・復元が必要になるため、まず通常のprivateメソッドで十分か確認する。

Consequences

  • getterの状態は参照から値へ変わるため、呼び出し側とテストの比較・cloneを調整する。
  • Map統合を一度に行うタスクは100行未満に収まらない可能性がある。ビルド・テストが通る単位を優先する。
  • 実装時にdocs/architecture.mdを更新する。既存ADRは書き換えない。
  • 不可能な内部状態のテスト削除と、不正Actionのテスト保持を区別する。

Alternatives Considered

  • 全フィールドをOptionにしたentry: Mapは統合できるが、状態との矛盾が残るため最終形にはしない。
  • 平坦なenumと状態別struct: 遷移処理が複雑になった場合に再検討する。現時点では導入コストに見合う効果が確認できない。
  • 全panicの除去: Action到着時の状態は実行時に決まるため、今回の型変更だけでは保証できない。

Future Work

  • 検証済みJournal取得結果型。SyncFetchedとCompleteLocalUploadWithFetchedの入力検証経路の差も別途検討する。
  • 競合待ちの状態細分化と、その型を要求する操作API。
  • IssueとJournalをまたぐupload操作の単一所有。active_uploadと各entryの状態を二重管理するだけの変更は避ける。
  • Map統合後の実装を踏まえた状態別遷移メソッドの必要性の再評価。
