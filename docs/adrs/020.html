20. 表示文言の多言語化

Status

Accepted

Context

画面の文言は、Componentとwidgetのコードに日本語で直接書かれている。ボタン、popupのタイトル、toastの文言（src/components/toast_list.rs）がこれにあたる。表示言語を切り替える手段はない（ANO-15）。

現状の仕組みには、次の前提がある。

  • Usecaseは表示の文言を持たない。失敗はUsecaseEventで意味だけを返し、文言はToastListComponentが組み立てる（ADR 18）。そのため、翻訳する文言はComponentとwidgetに集まっている。
  • native版は起動時に$XDG_CONFIG_HOME/redmine-tui/config.toml（なければ~/.config/redmine-tui/config.toml）をapp_configで読む。今は[image] enableだけを持ち、読めないファイルは起動エラーにする。Web版は設定ファイルを読まない。
  • 表示する日付は、どこも%Y/%m/%dで組み立てている。
  • 単体テストのsnapshotとE2Eは、日本語の文言を前提にしている。
  • 日本語の文字は全角で、英語より表示幅が広い。

Decision

対応言語は英語と日本語にする

対応する言語は英語（en）と日本語（ja）の2つとする。言語は起動時に1つ決め、起動中は切り替えない。

Fluentのメッセージカタログを使う

文言はFluentの.ftlに書き、fluent-bundleで引く。

  • カタログはlocales/en/main.ftlとlocales/ja/main.ftlに置き、include_str!でバイナリへ埋め込む。native版とWeb版で同じカタログを使う。
  • bundleはset_use_isolating(false)で作る。Fluentは埋め込んだ値の前後に双方向分離文字（U+2068、U+2069）を入れるのが既定で、terminalでは表示幅が崩れる。
  • メッセージIDは画面の部品と用途で名付ける（例: toast-issue-upload-failed）。英語の文をそのままIDにしない。
  • Redmineから取得した値（tracker名、status名、Issueの題名など）と、Clientのエラーなどの外部由来の説明（reason）は翻訳しない。ログと、起動前に標準エラー出力へ出すメッセージも翻訳しない。

文言の取得に失敗したらunwrapする

文言を引く処理の失敗は、表示時にunwrap（expect）する。メッセージが見つからない（get_messageやmsg.value()がNone）場合と、format_patternが埋め込みの誤りを報告した場合がこれにあたる。

  • これらの失敗は、カタログとコードの組み合わせで決まり、実行時の入力では変わらない。英語のカタログについては、文言を表示するwidgetとComponentのsnapshotテストで、失敗しないことを確かめる。
  • 日本語のカタログは表示のテストを持たない。代わりに、cargo xtask check-localesでjaとenのカタログを比べる。メッセージIDと属性の名前、各メッセージが参照する変数が一致しなければ失敗する。PRのCIでこれを実行する。
  • 起動時のカタログの読み込み（FluentResource::try_new、add_resource）の失敗もexpectする。カタログは埋め込みで、check-localesも同じカタログを構文解析する。

言語は設定ファイルで選ぶ

native版はconfig.tomlの[ui] languageで言語を選ぶ。

[ui]
language = "ja"
  • 値は"en"か"ja"とする。項目がなければ英語にする。
  • それ以外の値は、今の設定ファイルの読み込み失敗と同じく起動エラーにする。
  • 環境変数LANGは見ない。
  • Web版は英語に固定する。

選んだ言語はプロセス全体で1つ持つ

起動処理が言語を決め、runnerを起動する前にプロセス全体で1つの値として設定する。文言を引く関数は引数に言語もbundleも取らず、設定された言語のbundleを使う。設定されていなければ英語を使う。

// src/i18n.rs
pub(crate) fn set_language(language: Language);
pub(crate) fn message(id: &str, args: Option<&FluentArgs>) -> String;

// 呼び出し側は`message`を包むマクロを使う
tr!("toast-issue-upload-failed", id = issue_id, reason = reason)
  • bundleはfluent_bundle::concurrent::FluentBundleで作り、OnceLockに置く。
  • set_languageは1度だけ呼ぶ。テストは呼ばず、英語で動く。
  • src/i18n.rsはどの層からも使ってよい。ただし、Usecaseは文言を持たないため使わない。

日付と数値の表示形式は変えない

日付は言語によらず今の%Y/%m/%dで表示する。数値も今の表示のままにする。

テストは英語だけで行う

単体テストとE2Eは英語で行う。日本語の表示は、上に書いたcheck-localesだけで扱う。

  • 今の日本語のsnapshotは、英語の文言で取り直す。
  • E2Eは設定ファイルにlanguageを書かず、英語の文言を前提にする。

Rationale

対応言語を2つに絞り、起動中に切り替えないのは、利用者が使い分けるのは英語と日本語で、起動後に言語を変える用途がないためである。起動中に変わらないので、bundleを作り直す処理もComponentへ変更を伝える処理も要らない。

Fluentを選んだのは、英語の複数形（1 attachmentと2 attachmentsなど）を、コードで分岐せずカタログで書き分けられるためである。rust-i18nは文字列の置換だけを持ち、複数形はコードで書き分ける必要がある。

文言の取得の失敗をunwrapするのは、失敗がカタログの書き誤りでだけ起き、テストで見つけられるからである。Resultを呼び出し元へ返すと、表示の処理のすべてにエラーの経路ができるが、その経路で利用者に見せられる情報はない。

日本語のカタログを表示のテストで確かめないのは、snapshotとE2Eを2言語分持つ手間に見合わないためである。ただし、jaだけにメッセージがない、またはenにない変数を参照していると、日本語で起動したときだけpanicする。check-localesは、この失敗を表示のテストなしで見つけるために置く。単体テストにせずxtaskにするのは、アプリのコードを通さずカタログのファイルだけを調べる検査だからである。

言語をプロセス全体で1つ持つのは、文言を引く箇所がComponentとwidgetの全体に散っているためである。bundleを引数で渡すと、文言を持つWidgetと、それを作る経路のすべてに引数かフィールドが増える。ratatuiのWidget::render(self, area, buf)は引数を足せないので、Widgetはbundleをフィールドに持つ必要がある。Storeに置いてもWidgetのフィールドは要り、Storeを受け取らないhandle_usecase_eventsからtoastを作る経路には別に渡す必要がある。テストは英語だけで行うので、並列に動くテストの間で言語が食い違うこともない。

LANGを見ないのは、terminalのロケールと表示したい言語が一致するとは限らず、設定ファイルで明示するほうが挙動を予測しやすいためである。未設定を英語にするのは、テストと同じ言語で動くようにするためである。

日付を言語によらず%Y/%m/%dにするのは、数字だけの形式は英語でも日本語でも読め、表示幅も変わらないためである。

Consequences

  • Componentとwidgetに直接書いた文言は、tr!の呼び出しに置き換わる。ToastListComponentの失敗の種類ごとの文言も、.ftlのメッセージになる。
  • 文言を追加するときは、enとjaの両方のカタログに書く。片方だけに書くと、CIのcheck-localesが失敗する。
  • 日本語の文言の表示崩れ（全角による幅の超過、切り詰め）は、自動テストでは見つからない。日本語で起動して手で確かめる。
  • 既定の言語が英語になるため、設定ファイルを書いていない利用者の表示は、今の日本語から英語に変わる。
  • snapshotとE2Eの期待値は、日本語から英語に置き換わる。
  • AppConfigに言語の項目が加わる。
  • docs/architecture.mdのディレクトリ構成にsrc/i18n.rsとlocales/を加え、依存の図にi18nを置く。

Alternatives Considered

  • rust-i18nを使う: マクロ1つとYAMLで導入できるが、複数形をカタログで書き分けられない。採用しない。
  • bundleを引数で渡す: テストごとに言語を変えられるが、テストは英語だけで行うため、その利点を使わない。文言を持つWidgetと、それを作る経路のすべてに引数かフィールドが増えるため、採用しない。
  • bundleをSettingsStoreに置く: updateとrenderはStoreを受け取るが、Widgetとhandle_usecase_eventsはStoreを受け取らない。Widgetにbundleのフィールドを足し、handle_usecase_eventsにStoreを渡す必要があるため、採用しない。
  • 文言の取得の失敗をResultで返し、メッセージIDを代わりに表示する: panicはしないが、誤りに気づくのが表示を見たときになる。テストで見つけられる失敗に実行時の経路を足すことになるため、採用しない。
  • 日本語のsnapshotも取る: 日本語の表示崩れも自動で見つけられるが、snapshotが2倍になり、文言を変えるたびに両方を見直す必要がある。採用しない。
  • LANGから言語を決める: 設定なしで日本語になるが、terminalのロケールと表示したい言語が一致するとは限らない。採用しない。
  • 日付を言語ごとの形式で表示する: 英語でNov 27, 2026のような形式にすると、表示幅が言語で変わり、列の幅を言語ごとに決める必要がある。採用しない。
