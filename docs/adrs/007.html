7. Issue選択ポップアップのプロジェクト別Issue取得とページ管理

Accepted

Context

Issue選択ポップアップでは、詳細未取得のIssueもプロジェクトごとに一覧取得して表示する。一覧用のProjectsIssueはIssue ID、Project ID、subject、description、statusだけを持ち、既存のIssueStoreとは別に保存する。

Issue列は一度に1ページだけを表示する。連続スクロールと先読みは、表示中にサーバー側でIssueが追加された場合にoffsetの重複・欠落を起こしやすいため採用しない。選択中プロジェクトのpage 1から開始し、境界入力で前後ページを明示的に取得する。

同じexact keyを再取得する通信は重なり得る。例えばA→B→Aと素早くプロジェクトを切り替えると、最初のAと2回目のAの完了順は保証されない。一方、AとBは独立して完了・キャッシュできる必要がある。popup全体のgenerationでは粒度が粗く、Actionのconsume前に新世代を共有するライフサイクルも複雑になる。

Decision

一覧用entityとClient

ProjectsIssueをsrc/entities/に置き、同じIssueがIssueStoreに存在しても別に保存する。

ProjectsIssue {
    issue_id: IssueId,
    project_id: ProjectId,
    subject: String,
    description: String,
    status_id: IssueStatusId,
}

RedmineClientへ指定プロジェクト・ページのIssue一覧取得を追加する。GET /issues.jsonへproject_id、status_id=*、sort=id:desc、limit=50、1始まりのpageを渡す。戻り値はIssue一覧、total_count、offset、limitを含む。

Clientはstatus objectをIssueStatusIdへ変換し、API response DTOをdomain entityへ漏らさない。

limitが50、offsetが(page - 1) * 50、各IssueのProject IDが要求値と一致することを検証し、不一致はRedmineClientError::Clientとする。期待offsetはchecked arithmeticで計算し、overflowするpageも同じClient errorとする。空の範囲外ページを許容するためoffset <= total_countは検証しない。並び順、Issue IDの一意性、issues.len() <= limitもRedmineを信頼して検証しない。

exact keyとページ状態

StoreはProject IDとpageの組をexact keyとして扱う。generationはkeyに含めない。

HashMap<(ProjectId, NonZeroUsize), ProjectIssuesPageState>

enum ProjectIssuesPageState {
    Loading { request_id: ProjectIssuesRequestId },
    Loaded {
        issues: Vec<ProjectsIssue>,
        total_count: usize,
        offset: usize,
        limit: usize,
    },
    Failed { message: String },
}

ProjectIssuesRequestIdは一般的なdomain Value Objectではなく、ProjectIssuesStoreのAction protocolで開始Actionと完了Actionを対応付ける相関IDである。そのためsrc/vos/には置かず、stores/project_issues_store moduleでAction・page stateとともに定義し、stores module経由でページfetch Usecaseへcrate内公開する。アプリ外へ公開するAPIにはしない。

値はUUID v4で、等値比較だけに使う。大小や発行順に意味はなく、UUID v4の衝突確率は実用上無視できる。中央採番器は設けず、ページfetch Usecaseは呼び出しごとに新しいIDを同期的に生成する。

StartLoading { request_id, project_id, page }
LoadSucceeded { request_id, project_id, page, result }
LoadFailed { request_id, project_id, page, message }

StartLoadingはexact keyが未登録、Loading、Loaded、Failedのいずれでも、Loading { request_id }へ置き換える。これが明示的なrefetchであり、ClearPageは設けない。完了Actionは同じexact keyがLoadingで、そのrequest_idが一致する場合だけ受理する。他のexact keyには影響しない。

[unloaded|Loading|Loaded|Failed]
  -- StartLoading(new request) --> Loading(new request)
Loading(request) -- matching success --> Loaded
Loading(request) -- matching failure --> Failed

A/page1 request X、B/page1 request Y、A/page1 request Zの順に開始した場合、A/page1はZだけを受理し、B/page1はYを独立して受理できる。XのHTTP自体はcancelしない。

Storeはexact-key getterとLoaded metadataを公開する。表示page、前後ページ、navigation可否、現在focusは保持・計算しない。取得開始可否をentryの有無で判定するqueryも設けない。

Usecaseと非同期処理

  1. UUID v4のProjectIssuesRequestIdを生成する。
  2. StartLoading { request_id, project_id, page }を同期dispatchする。
  3. 同じIDを捕捉し、成功または失敗Actionを返すFutureを構成する。

UsecaseはFuture<Output = ProjectIssuesAction> + Send + 'staticを返す。worker sender、Tokio runtime、spawnはmainが管理する。ClientはArc<C>で渡し、C: Send + Syncを要求する。開始Actionはその場でconsumeしない。

ComponentとAppEffectはproject_idとpageだけを持つ。Appがeffectを処理してUsecaseを呼ぶ時点でIDを発行する。AppComponentはrequest ID、generation、Clear/Invalidateの順序を管理しない。

Componentの表示pageと取得要求

Componentはpopup生成時のProject一覧snapshotと、HashMap<ProjectId, NonZeroUsize>によるプロジェクトごとの表示pageだけを保持する。全ProjectのStore状態を複製せず、表示対象のexact keyをStoreから読み、その都度viewを構成する。初期Projectは、フォーカス中IssueがIssueStoreにあり、そのProjectがsnapshotにもあればそのProject、それ以外はProject ID昇順の先頭とする。ProjectsIssue cacheは探索しない。Projectが0件なら初期effectを持たない。

初期page 1、Project切替、前後page移動、失敗時のrは、すべて対象Project ID/pageの新しいeffectを要求する。A→B→AではAを再取得し、各Usecase呼び出しが異なるrequest IDを発行する。Store cacheの存在を理由にProject切替時のfetchを省略しない。既にLoadingでも明示要求は新しいIDで置き換えられる。1入力イベントからeffectは最大1個とする。

popupを閉じて開き直すと新しいComponentと表示page Mapを作り、すべてpage 1から始める。IssueSelectPopupComponent::take_effectは保持したeffectを一度だけ返す。

popup終了時はstackから除去するだけで、generation更新、全page破棄、exact-key clearは行わない。他Project・他pageのcacheは保持する。

ページ移動と表示

  • 先頭Issueでさらにk: page > 1ならchecked subtractionで前pageを取得する。
  • 最終Issueでさらにj: 一覧が空でなく、offset.saturating_add(issues.len()) < total_countならchecked additionで次pageを取得する。
  • 前または次のpageがなければキーを消費するだけでeffectを生成しない。
  • 移動先pageを保存しIssue cursorを0へ戻す。Project切替時も0へ戻す。
  • page 2以降が空でもkで戻れる。空pageでjは開始しない。

FocusStateはStore metadataやnavigation policyを持たず、通常移動、境界k/j、Project切替、rを通知する。

Loadingは「読込中です」だけを表示し、以前の内容とpreviewを隠す。Failedはmessageとr案内、Loaded 0件は「Issueはありません」を表示する。Issue列から始めた取得中・失敗中もIssue focusを維持し、hでProject列へ戻れる。

Project列にfocusがあるとき、現在pageがLoading、Failed、未取得、またはpage 1のLoaded 0件なら、lでIssue列へ移動しない。rは現在pageがFailedならProject列・Issue列のどちらからでも受け付ける。Project列はVerticalScrollWidgetを使い、Issue列は現在pageの最大50件だけを表示する。WidgetはStoreを参照しない。

既存Issueの表示値

同じIssue IDがIssueStoreにあれば、一覧とpreviewのsubject/descriptionはその値を優先する。なければProjectsIssueを使う。statusは上書きしない。

main loop

  1. worker channelからActionをDispatcherへ移す。
  2. queued Actionを1件ずつconsumeし、直後にupdateする。
  3. take_effectし、あればUsecaseを開始する。
  4. draw、event poll/read、key処理を行う。
  5. key処理後もActionをdrain/updateし、ActionがなくてもComponent updateを1回行う。

UsecaseがdispatchしたStartLoadingは次の通常drainでconsumeされる。request IDは開始ActionとFutureに閉じ込められるため、dispatchとconsumeの間にStoreから読み直さない。

AppComponent::new直後にはComponent初期化用のAppComponent::updateを一度呼ぶが、queued Actionはconsumeしない。popupの初期effectは生成時にpending_effectへ移し、初期effect専用handlerを設けず、最初のmain loopの共通effect処理点で開始する。この処理点はdrawと最初のevent poll/readより前にあるため、初回入力より先に初期fetchを開始できる。

Error Handling

Clientエラーは同じrequest IDを持つLoadFailedへ変換する。Storeは現在のexact keyが同じrequest IDのLoadingである場合だけFailedへ遷移する。古い完了と他exact keyには影響させない。再試行は新しいIDのLoadingへ直接置き換え、不完全な結果は公開しない。

Rationale

fetch単位のrequest IDにより競合範囲をexact keyへ限定できる。popup全体を無効化せず、Aの先行要求だけを拒否しながらBを独立して完了できる。Usecase内で開始ActionとFutureを同時に構成し、Appは相関IDを管理しない。UUID v4は中央採番状態やoverflowを持たず、等値比較だけで利用する。Componentの表示意図とStoreのcacheも分離される。

Consequences

  • Store test: 全状態からの置換、同一exact keyのlatest-started-wins、異なるexact keyの独立完了、metadataと空page、generation/Invalidate/Clear/can-fetch queryの不在。
  • Usecase/Client test: 呼び出しごとに異なるID、開始・完了Actionの同一ID、成功・失敗変換、sender非依存、DTO変換と検証・非検証境界。乱数値や大小には依存しない。
  • Component test: 初期Project規則、初期page 1、popup再生成reset、表示page、A→B→Aの各effect、take_effect one-shot、pageなし境界のキー消費、focus抑止、両column retry、Loading/Failed/空page、既存Issue優先、scroll。
  • App/main test: effectはProject ID/pageだけを持ち、Clear/Invalidateをdispatchせず、初期updateがActionをconsumeせず、初期effectが共通処理点で初回入力前に開始され、開始Actionを通常drainでconsumeする。

Alternatives Considered

popup全体のGeneration

異なるexact keyの独立通信まで破棄し、dispatch/consume間の世代共有管理も必要になるため採用しない。

ClearPageして未登録キーだけ取得

Loading置換の競合識別には結局IDが必要であり、request ID付きStartLoadingで直接置換する方が単純である。

ComponentがIDを発行

非同期相関の詳細をUIへ漏らすため採用しない。

連番ID

中央状態、overflow、順序の誤用を避けるためUUID v4を採用する。
