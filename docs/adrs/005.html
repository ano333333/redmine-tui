ADR 5

Issue 子 Store と IssueAction の分離方針

Accepted

Context

src/app.rs は Action、Dispatcher、Store を定義し、Issue、Journal、Redmine のマスターデータに関する状態と更新処理を一つのファイルで管理している。

Issue 保存フローの追加により、Issue 本体だけでなく、Issue ごとの同期状態、未保存差分、upload 競合情報を Store が保持するようになった。Issue の読み込み、同期、編集、upload、競合管理に関する action も増え、src/app.rs の責務とテストが重厚になっている。

ADR 2 では Issue 関連 action が増えた場合に Issue 専用の子 Store へ切り出す余地を残していた。現在は、Issue に関する状態と action 処理が独立したまとまりを形成しており、子 Store へ分離する時点に達している。

一方、Component と usecase は親 Store の getter を通して Issue を参照している。この参照方法や Component lifecycle を変更せず、Store 内部の責務だけを分離する必要がある。

Decision

Store 関連コードを src/stores/ へ移し、以下の構成にする。

src/stores/
├── mod.rs
├── store.rs
├── issue_store.rs
└── issue_store_tests.rs
ファイル責務

store.rs は親 Action、Dispatcher、Store、Journal とマスターデータの状態を定義する。

issue_store.rs は IssueStore、IssueState、IssueAction と Issue Action の処理を定義する。

issue_store_tests.rs は親 Store の公開インターフェースを通して Issue Action を検証し、mod.rs は必要な型を再エクスポートする。

所有と境界

src/main.rs の mod app; は mod stores; に変更し、既存の crate::app import は crate::stores へ移行する。

親 Store は IssueStore を一つのフィールドとして所有する。Issue 本体、Issue ごとの IssueState、未保存の IssuePropertyDiff、upload 競合時のサーバー Issue と競合 diff を移す。

Action の構造

pub enum Action {
    Issue(IssueAction),
    // Journal、マスターデータ関連 Action
}

IssueAction は Issue という文脈が型名で明らかなため、variant 名から重複する Issue を除き、次を定義する。

Load、Sync、StartUpload、CancelUpload、ClearUploadConflicts、FailUpload、UploadConflictsDetected、UpdateDescription、UpdateStatus、UpdateAssignedTo、UpdateTargetVersion、UpdateCategory、UpdateDoneRatio、UpdateStartDate、UpdateDueDate

親 Store::consume_action は Action::Issue(action) を IssueStore::consume_action(action) へ委譲する。Journal とマスターデータの Action は従来どおり親 Store が処理する。
From<IssueAction> for Action を実装し、Dispatcher::dispatch は impl Into<Action> を受け取る。Component や usecase は通常 IssueAction を直接 dispatch し、親 Action が必要な非同期処理では .into() で変換する。
既存の get_issue、get_issues、get_issue_property_diffs、get_issue_upload_conflict getter は親 Store に残し、内部で IssueStore へ委譲する。
既存の IssueState::Synced / Edited / Uploading、状態遷移、panic 条件とメッセージは変更しない。Load は YAML fixture を読む暫定 Action、Sync は Issue の置換と diff・競合情報の破棄、Synced への遷移を行う。

テストの配置

Issue Store のテストは src/stores/issue_store_tests.rs へ分離する。ただし IssueStore を直接テストせず、現在と同様に親 Store の公開 getter と Store::consume_action を通して振る舞いを検証する。

維持する検証: 読み込みと参照 ID、property 更新と diff、upload の開始・中断・失敗・成功、競合情報、不正な状態遷移、Issue 同期時の置換と状態初期化。SyncIssueStatuses、SyncUsers などは親 Store のテストに残す。

Rationale

stateIssue の状態と規則をまとめる

Issue 本体、同期状態、差分、競合情報は同じ Issue ID をキーとして連動し、Issue Action によって一貫して更新される。IssueStore にまとめることで、状態遷移を親 Store の他の責務から独立して読める。

action型で処理範囲を表現する

Action::Issue(IssueAction) により、親 Store がアプリケーション全体の入口であることを維持しながら、子 Store が処理できる Action の範囲を型で表現できる。親 Store に15個の Issue Action variant を残す案は採用しない。

api呼び出し側の冗長さを抑える

IssueAction の variant から接頭辞を除き、From<IssueAction> と impl Into<Action> の dispatch を組み合わせることで、構造化に伴う呼び出し側の冗長さを抑える。

boundaryComponent lifecycle を守る

親 Store の getter を維持することで Component は Store 内部の分割を意識しない。子 Store を直接公開せず、状態配置の変更を表示層へ漏らさない。

test公開インターフェースを検証する

親 Store 経由のテストで、実装詳細ではなくアプリケーションが利用する公開インターフェースと Action dispatch の結合を検証する。実装とテストを分離し、双方の可読性も改善する。

Consequences

src/app.rs は廃止され、Store 関連の利用箇所は crate::stores から型を import する。再エクスポートにより内部モジュール名への依存は隠蔽される。
Issue Action の呼び出し元は新しい IssueAction variant 名へ更新する必要がある。worker や usecase が親 Action を返す箇所では変換が必要になる。
親 Store は Issue 固有状態を直接保持しなくなるが、既存 getter を維持するため Component の Store 参照と描画結果は変化しない。意図的な UI 表示変更はなく、snapshot 更新は想定しない。
Journal とマスターデータは引き続き親 Store が保持する。これらの子 Store 分離は本 ADR の対象外とする。
既存 ADR は変更しない。ADR 2 に記載された Issue 子 Store 分離の余地を、本 ADR によって具体化する。

Open Questions

なし。
