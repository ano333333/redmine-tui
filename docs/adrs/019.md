# 19. Issueの新規作成と下書きの保持

## Status

Accepted

## Context

Issueの新規作成（ANO-183）を実装する。作成を始める導線は次の2つとする。

- 導線1: Issue選択popupでフォーカスしているプロジェクトに、親を持たないIssueを作る。
- 導線2: Issue詳細の子一覧から、表示中のIssueを親とする子Issueを作る。親のプロジェクトに作る。

関連するRedmine APIは次のとおりである。

- `POST /issues.json`で作成する。`project_id`と`subject`が必須で、子Issueは`parent_issue_id`に親IDを入れる。`tracker_id`・`status_id`・`priority_id`を省略すると既定値になる。添付ファイルは`uploads: [{token, filename, content_type}]`で作成と同時に付けられる。
  - 成功は201 Createdで、bodyに`{"issue": {...}}`が入る。`children`と`journals`は含まない。
  - 検証エラーは422で`{"errors": [...]}`が返る。権限（`add_issues`）がなければ403が返る。
  - 親と別プロジェクトに子を作れるかは、管理設定「プロジェクト間の親子関係」で決まる。
  - 新規作成時に選べる初期ステータスは、ワークフローの「新規チケット」遷移で絞られる（未確認）。
- `POST /uploads.json`で送ったファイルのtokenは、作成の`uploads`に入れられる。既存の`upload_file`で取得できる。
- 作成後の取得は`GET /issues/{id}.json?include=children,journals,attachments`で、既存の`get_issue`を使う。

現状の仕組みには、次の前提と制約がある。

- Issueの編集中の値はStoreの`IssueStore`が`diffs`として持ち、編集popupのobserverが`IssueAction`をdispatchする（`src/usecases/issue_popup_options.rs`）。選択肢の組み立ても、Storeにある取得済みIssueの値を前提にしている。
- `DefaultRedmineClient`のHTTPヘルパーは、`put_empty`とバイナリ用の`post_bytes_json`だけである。
- `AppComponent`は表示中のIssueを`issue_component: Option<IssueComponent>`で持つ。
- Usecaseから`AppComponent`へ一度だけ起きたことを伝える経路として、`UsecaseEvent`がある（[ADR 18](018.md)）。
- `fetch_issue`は未取得か取得失敗のIssueしか取得を始めない。`IssueStore`の子一覧は、詳細取得の完了と保存後の取得でしか置き換わらない。

## Decision

### 下書きは新規作成用Componentが持つ

新規作成用の`NewIssueComponent`を`src/components/new_issue/`に置く。下書き`NewIssueDraft`はこのComponentが持ち、Storeには置かない。`NewIssueDraft`は作成の要求でUsecaseへ渡すため、型は`src/usecases/`に置く（`usecases`は`components`に依存しない）。

```rust
pub struct NewIssueDraft {
    pub project_id: ProjectId,              // 導線で決まり、下書きでは変えない
    pub parent_issue_id: Option<IssueId>,   // 導線2だけSome。下書きでは変えない
    pub subject: String,
    pub description: String,
    pub tracker_id: Option<TrackerId>,      // Noneは送信せず、サーバーの既定値にする
    pub status_id: Option<IssueStatusId>,   // 同上
    pub priority_id: Option<PriorityId>,    // 同上
    pub assigned_to_id: Option<UserId>,
    pub target_version_id: Option<TargetVersionId>,
    pub start_date: Option<DateTime<Local>>,
    pub due_date: Option<DateTime<Local>>,
    pub done_ratio: Option<u16>,
    pub estimated_hours: Option<f64>,
    pub category_id: Option<CategoryId>,
    pub attachments: Vec<DraftAttachment>,  // { filename, path }
}
```

- 編集できる属性は、プロジェクトを除いて既存のIssue詳細の編集UIと同じとする。プロジェクトは導線で決まり、トラッカー・対象バージョン・カテゴリの選択肢のもとになるため、下書きでは変えない。
- 選択肢の組み立ては、`issue_popup_options`の`build_*_options`を、IssueのIDではなく現在値とプロジェクトIDを受け取る形に分ける。既存のIssue詳細は、Storeから現在値を読んで呼ぶ。
- 編集popupは既存のものを使う。下書きは`Rc<RefCell<NewIssueDraft>>`で持つ。`NewIssueComponent`が下書きを書き換えるobserverを組み立て、`AppComponent`がそれを渡してpopupを開く。observerはActionをdispatchしない。
- 題名と説明の編集は外部editorを使う。`PendingEditorContext`に新規作成用の文脈を加え、`handle_editor_response`が下書きに書き戻す。題名は1行のため、改行と連続する空白を1つの空白にまとめる。
- 添付ファイルは、既存の`AttachmentInputPopupComponent`でファイル名とパスを受け取り、下書きに積む。ファイルは作成の要求まで読まない。
- 題名が空白だけのときは作成を要求せず、題名が必要なことをtoastで知らせる。それ以外の検証はRedmineの422に任せる。

### 表示中のComponentを切り替える

`AppComponent`は表示中の画面を、Issue詳細と新規作成のどちらか一方として持つ。

```rust
enum MainComponent {
    Issue(IssueComponent),
    NewIssue(NewIssueComponent),
}
```

- 導線1では、Issue選択popupで`n`を押すと`IssueSelectPopupComponent`がフォーカス中のプロジェクトIDを返し、`AppComponent`がpopupを閉じて`NewIssueComponent`に差し替える。
- 導線2では、子一覧の追加行でEnterを押すと`IssueDetailComponent`が表示中のIssueのIDを返す。`AppComponent`はStoreから親のプロジェクトIDを読み、`NewIssueComponent`に差し替える。
- `NewIssueComponent`からもIssue選択popupを開ける。Issueを選んだら`IssueComponent`に差し替え、`NewIssueComponent`と下書きは破棄する。Webで作成完了前に別のIssueを表示したのと同じ扱いとし、確認ダイアログは今は作らない。popupを閉じただけなら下書きに戻る。
- `NewIssueComponent`は作られるたびに、新しい`IssueCreationId`を持つ。作成の要求とその結果のイベントはこのIDを持つ。

### 作成はUsecaseが行い、結果をイベントで返す

`NewIssueComponent`はCtrl+Sで作成の要求を結果として返し、`AppComponent`が`UsecaseRequest::CreateIssue { creation_id, draft }`を`RequestSink`に書く。要求したComponentは作成中の状態になり、編集を受け付けない。

`create_issue` Usecaseは、非同期の処理で次を順に行う。

1. 下書きの添付ファイルを`LocalFileClient`で読み、`upload_file`でtokenを取得する。この処理は既存の添付ファイルの追加と共有する。
2. `create_issue`で`POST /issues.json`を送る。添付ファイルは`uploads`に入れる。
3. 成功したら、イベント`UsecaseEvent::IssueCreated { creation_id, id }`と、後続要求`FetchIssue { id, with_parent: true }`を返す。

いずれかに失敗したら、`UsecaseEvent::Failure(UsecaseFailure::IssueCreate { creation_id, cause })`を返す。tokenは保持せず、再送では添付ファイルを読み直して送る。

```rust
pub enum IssueCreateFailure {
    AttachmentFileRead { filename: String, reason: String },
    AttachmentFileUpload { filename: String, reason: String },
    Create { reason: String },
    CreateOutcomeUnknown { reason: String },
}
```

失敗した段階を種類で分け、通知の文言は`ToastListComponent`が組み立てる（[ADR 18](018.md)）。作成の要求が応答のステータスで拒否されたときは`Create`とする。通信やClientのエラーは、Redmineが作成した後に応答を受け取れなかった場合も含むため、`CreateOutcomeUnknown`とする。このときtoastで、再送すると二重に作成されることがあると知らせる。どちらの場合も、下書きは編集できる状態に戻す。

`AppComponent::handle_usecase_events`は、イベントを次のように扱う。

| イベント | 表示中が同じ`creation_id`の`NewIssueComponent` | それ以外 |
| --- | --- | --- |
| `IssueCreated` | `IssueComponent::new(store, id)`に差し替える | 無視する |
| `Failure(IssueCreate)` | 編集できる状態に戻し、toastを出す | toastだけ出す |

- `IssueCreated`を受けた時点で、作成したIssueはまだ取得していない。`IssueComponent::new`は未取得のIssueでも作れ、後続の`FetchIssue`が取得を始める（[ADR 18](018.md)）。
- `handle_usecase_events`がStoreを読むため、読み取り専用の`&Store`を渡す。
- 作成の失敗はStoreの状態に残さない。下書きは`NewIssueComponent`にあり、再送はComponentから要求し直すためである。

### Clientに作成のAPIを足す

```rust
fn create_issue(
    &self,
    issue: &NewIssue,
) -> impl Future<Output = Result<IssueId, RedmineClientError>> + Send;
```

- `NewIssue`は`IssueUpdate`に近いが、`project_id`・`subject`を必須とし、`parent_issue_id`と`uploads`を持つ。値の解除がないため、外側の`Option`は送信しないことだけを表す。`serialize_clearable`は使わない。
- `DefaultRedmineClient`に、JSONを送ってJSONを受け取る`post_json`ヘルパーを足す。201の`{"issue": {...}}`から`id`だけを読む。
- `DemoRedmineClient`は、memory上のfixtureに新しいIDでIssueを追加する。
- 選択肢の取得には、既存の`/trackers.json`・`/users.json`などを使い、プロジェクトごとの有効なトラッカーやメンバーの取得APIは足さない。

### 親の子一覧は取り直さない

導線2で子Issueを作っても、取得済みの親の子一覧は取り直さない。親を取得済みのまま子を作ると、親をIssue選択から開き直しても、親を保存するまで子一覧に作成した子は出ない。

取得済みのIssueを取り直す仕組みは、子一覧だけでなくIssue全体を取り込むUsecaseとして別に整備する。親の子一覧の取り直しは、その仕組みを使って行う（Future Work）。

## Rationale

下書きをComponentに置くのは、下書きが、Issue選択で別のIssueを選ぶと捨てる一時的な入力であり、他のComponentから読まれないためである。Storeに置くと、まだIDのないIssueを`IssueStore`のどこに置くか、破棄をどのActionで表すかを決める必要がある。focusやcursorと同じく、同期的なUI stateとしてComponentに持つ。

既存の編集popupは、値を確定したときにobserverを呼ぶ形である。observerの書き込み先を下書きに変えれば、popupに手を入れずに使える。下書きを`Rc<RefCell<_>>`にするのは、popupが`AppComponent`のpopup stackにあり、`NewIssueComponent`とは別に生きるためである。

作成の完了をイベントで返すのは、[ADR 18](018.md)で決めたとおり、一度だけ起きたことをStoreの状態として残さないためである。作成の成功はStoreに何も残さず、取得は後続の`FetchIssue`に任せる。

`IssueCreationId`を持たせるのは、作成中に別のIssueへ移り、さらに新しい下書きを開いた場合に、古い作成の結果を新しい下書きに当てないためである。作成中のComponentがもうなければ、結果のイベントを当てる先はない。失敗のtoastは、下書きを捨てた後でも作成が失敗したことを知らせるために出す。

添付ファイルを作成の`uploads`に入れるのは、作成と添付を1回のPOSTで確定できるためである。作成後に`attach_upload`で付ける2段階にすると、作成は成功して添付だけ失敗した状態を扱う必要がある。

親の子一覧を今回は取り直さないのは、取得済みのIssueを取り直す仕組みを、子一覧だけの部分的なものではなくIssue全体のUsecaseとして整備したいためである。取得済みのIssueには未送信の編集やupload中の状態があり、Issue本体を取り込むにはマージ戦略や、どの契機で取り直すかを決める必要がある。これらは新規作成とは別に決める。

## Consequences

- `AppComponent`の`issue_component`は`MainComponent`に変わる。`issue_component`を前提にした処理（入力の振り分け、update、render、cursor位置、競合popupを開く判定）は、`MainComponent::Issue`のときだけ動く。
- `UsecaseEvent`に`IssueCreated`、`UsecaseFailure`に`IssueCreate`が加わる。`ToastListComponent`に作成の失敗の文言を足す。
- `handle_usecase_events`が`&Store`を受け取る。[ADR 18](018.md)で、Storeを読む必要が出たら読み取り専用で渡すとしたとおりである。
- `UsecaseRequest`に`CreateIssue`が加わる。
- `issue_popup_options`の`build_*_options`の引数が変わる。
- `RedmineClient`に`create_issue`が加わり、`DefaultRedmineClient`・`DemoRedmineClient`・テスト用のstubに実装が必要になる。Docker上のRedmineに対するclientテストとE2Eに、作成のケースを足す。
- 作成に失敗すると、uploadしたファイルはどのIssueにも属さないままRedmineに残る。再送ではファイルを送り直すため、失敗するたびに残るファイルが増える。
- ステータスの選択肢は全ステータスで、ワークフローで許されない初期ステータスを選ぶと422になる。
- 作成中に別のIssueへ移って作成が成功した場合、作成したIssueは自動では開かない。
- 導線2で子Issueを作っても、取得済みの親の子一覧には、親を保存して取り直すまで作成した子が出ない。

## Alternatives Considered

- 下書きをStoreに置く: Componentを破棄しても下書きが残り、イベントがなくても完了を検知できる。一方で、IDのないIssueの置き場所と破棄のActionが要り、Issue選択で捨てる一時的な入力をStoreの状態遷移として扱うことになる。採用しない。
- 作成の成功をStoreの状態で表し、`AppComponent::update`で検知する: 競合popupと同じく「すでに反応したか」の判定が要る。[ADR 18](018.md)でイベントを作った理由そのものであり、採用しない。
- 作成成功のActionで、Storeにある親の子一覧に`IssueChild`を1件足す: POSTのレスポンスにある`id`・`tracker`・`subject`で作れ、変更が一番少ない。ただし、別の利用者が同じ親に作った子や、作成時にRedmineが変えた内容は反映されない。サーバーの値を取り直す仕組みで扱う方が、詳細取得と同じ値を持てるため、採用しない。
- 取得済みのIssueの子一覧だけを取り直すUsecaseを足す: 子一覧はローカルで編集しないため、置き換えても編集を失わない。ただし、取得済みのIssueを取り直す仕組みが子一覧だけの部分的なものになる。Issue全体を取り直すUsecaseとして整備したいため、採用しない。
- 作成後に`attach_upload`で添付する: 既存の添付の仕組みをそのまま使えるが、作成だけ成功した中途半端な状態の扱いが要る。採用しない。
- popupの確定値を`EventProcessResult`で返し、`AppComponent`が`NewIssueComponent`に渡す: `Rc<RefCell<_>>`は要らないが、既存のpopupの戻り値をすべて変える必要がある。採用しない。
- `IssueCreationId`を持たず、表示中が`NewIssueComponent`かどうかだけで判定する: 作成中に別のIssueを経由して新しい下書きを開くと、古い作成の結果が新しい下書きに当たる。採用しない。
- プロジェクトごとの有効なトラッカーや担当者候補を取得するAPIを足す: 選択肢の精度は上がるが、既存の編集UIと選択肢が食い違う。編集UIとあわせて別に検討する。

## Future Work

- 取得済みのIssueを取り直すUsecaseを、Issue全体を対象として整備すること。どの契機で取り直すか、編集中・upload中のIssueにどう取り込むか、重複した取り直しの完了をどう扱うかを決める。導線2で子Issueを作ったときの親の子一覧の取り直しは、このUsecaseを使って行う。
- 新規作成中に別のIssueを選んだときの確認ダイアログ。
- プロジェクトで有効なトラッカー、担当者候補、ワークフローで許される初期ステータスへの選択肢の絞り込み。
- 422の`errors`を解析し、属性ごとに表示すること。
